# MCP lifecycle, trust, sampling and elicitation

Status: current
Owner: src/mcp/

McpManager owns configured client lifecycle and dynamic registry entries; restart/shutdown must remove the corresponding tools/catalog. Client transports and SDK usage belong to the client boundary. Per-server `enabledTools` / `disabledTools` drop tools at discovery (`mcp-tool-filter.ts`), so a turned-off tool is absent from the catalog, descriptors, grammar and registry. Per-server trust determines resource classification; an optional per-server `approval` mode (`ask` / `ask_writes` / `auto`, `mcp-approval-mode.ts`) overrides only whether a call prompts, never batching (`ask_writes` trusts `readOnlyHint` from stdio servers only; remote tools always ask); third-party schemas cannot be assumed to share built-in flat shapes.

Resources and prompts are discovery/read tools, while sampling forwards an isolated completion rather than taking the main turn's slot. Stdio transport passes only an allowlist of service variables from the agent environment ([mcp-stdio-env.ts](../mcp-stdio-env.ts): PATH, HOME, locale, temp and XDG dirs, display, SSH agent socket, Docker host, Windows profile/system variables such as SystemRoot, APPDATA, USERPROFILE, ComSpec, PATHEXT and PSModulePath, proxies and CA bundles), matched case-insensitively, then overlays the server's configured `env`, which wins. Provider keys and bot tokens loaded from the state-directory .env are not forwarded; a server that needs a key must list it in its own `env`. This is environment hygiene, not a sandbox: the subprocess still runs as the user and can read files the user can. Preserve credential redaction in stderr/errors and explicit unsupported-operation refusals. Do not add credential-shaped names to the allowlist.

HTTP transports (streamable HTTP and SSE) keep the SDK's default redirect policy: since SDK 1.32 a redirect is followed only within the configured endpoint's origin (an http to https upgrade on the same host is allowed only when both use the default port). A server whose URL redirects to another host or port must be configured with its final URL. We do not set `redirectPolicy: 'follow'`, so a cross-origin redirect fails instead of sending configured headers to another origin.

Elicitation (ATO-704) lets a server ask the person for input in the middle of a call: pick an account, confirm an action, fill a small form. A client advertises `elicitation: {}` (form mode only) only when the host wires an "ask the human" port, `RuntimeEventHandlers.onMcpElicitation`, which reaches McpManager as `elicitationPort`; with no port no client advertises it, and a spec-following server will not send `elicitation/create`. The manager gives every client its own handler ([mcp-elicitation-handler.ts](../mcp-elicitation-handler.ts)) so the person always sees which server is asking. The handler accepts only a flat form of primitive fields ([mcp-elicitation-schema.ts](../mcp-elicitation-schema.ts): string with optional length and email/uri/date/date-time format, number or integer with a range, boolean, single-select and multi-select enums, at most 20 fields); anything else and URL mode are declined without asking. A reply from the port is checked against the form ([mcp-elicitation-answer.ts](../mcp-elicitation-answer.ts)) before it goes back. How long the handler waits depends on the surface the port declares (`McpElicitationPort.surface`, fixed or a function read per request): `interactive` (desktop, TUI, a person at the screen) has no cut-off, the question stays until answered and Esc / Decline is the answer; `remote-chat` (Telegram, Discord) waits 5 minutes, then declines; `none` (cron task, heartbeat, headless or overnight run) is declined at once without asking. A throwing or unknown surface counts as `none`. Even an open-ended wait ends when the server cancels its request or the connection closes: the SDK aborts the handler's signal and the handler aborts the port's. While an elicitation from a server is pending, McpClient holds the deadline (60 s by default) of every in-flight request to that server, and gives each a fresh full window when the last one settles; the SDK's own request timeout is set out of the way so it cannot fail the call first. A call with no elicitation still times out after 60 s, and on our timeout or the caller's abort the SDK request is aborted so the server gets `notifications/cancelled`. Invariants: never auto-accept, since `accept` only comes from the port; the turn never breaks, so a missing surface, an unattended run (surface `none`, or the port answers `unavailable`), a remote-chat timeout, a port error or garbage reply is `decline`, and a server cancel, a closed connection or an answer that does not fit the form is `cancel`; answers never reach logs or traces, because the handler logs only server, action, reason and field count, and validation reasons name fields, not values. Fields whose name or title looks like a credential carry `sensitive: true` so a surface masks them. The port is called outside any turn frame: the host decides whether a person is there. Today no host wires a port (TUI, desktop, Telegram and Discord are follow-ups), so behaviour is unchanged until one does.

## Browser sign-in (OAuth)

Remote servers that only allow OAuth (for example Monid) sign in through the browser, the way Claude Code and Codex do. A Streamable HTTP / SSE transport gets an OAuth provider ([mcp-oauth-provider.ts](../mcp-oauth-provider.ts)) only once a sign-in is saved for it (the provider then refreshes the tokens), and never when its `headers` already carry a credential (`Authorization`, or a name containing api-key, token, secret or password); those servers keep sending their headers exactly as before. With no saved sign-in, a keyless server's 401 becomes `needs_auth` ("Sign in required") only when the server publishes OAuth protected-resource metadata; any other 401 keeps its own error. Connecting never registers a client: only the user's Sign in does. stdio is unchanged. The provider takes one type from the SDK; its `auth()` call is `runMcpOAuth` in the client, so SDK calls stay in mcp-client.ts.

When a connect gets a 401 and no usable token, the client throws `McpAuthRequiredError` and the manager sets the new state `needs_auth` (status `authRequired: true`, `lastError` "Sign in required") instead of `down`. The connect may register the client (dynamic client registration) but never records a verifier or URL, so a restart cannot spoil a sign-in in progress. Saved tokens are sent as `Authorization: Bearer` and refreshed by the SDK.

The sign-in itself is [mcp-oauth-flow.ts](../mcp-oauth-flow.ts), shared by HTTP (`POST /api/mcp/servers/{name}/auth/start` → `{ state: "pending", authUrl }`, `GET .../auth` → `{ state: "signed_out" | "pending" | "signed_in", error? }`, `POST .../auth/signout`) and the TUI (`/mcp auth <name>`, `/mcp signout <name>`). The agent never opens a browser: it may be headless, so the UI that asked opens `authUrl`. The flow opens one loopback listener on 127.0.0.1 for the callback path only, port 47613 first, then the next four, then any free port; the redirect URI is `http://127.0.0.1:<port>/callback`. The client registration is saved with the redirect it used and repeated when the port differs. `state` is random per request and a callback with any other value is refused. After a valid callback the code is exchanged, the browser gets a short "you can close this tab" page and the server is reconnected. A sign-in not finished in 5 minutes expires and the listener closes when none is left.

Credentials live in `<stateDir>/mcp-oauth/<name>.json` ([mcp-oauth-store.ts](../mcp-oauth-store.ts)), mode 0600 in a 0700 folder, written atomically. A record keeps the server URL: a changed URL reads as signed out and the next save replaces the old record. Sign out deletes the file. Tokens never go to logs or errors. An authorization server that refuses dynamic client registration cannot be signed in to yet: there is no field for a pre-registered client id. The desktop agent and the terminal app share these files but each has its own listener: starting a sign-in for the same server in both at once leaves only the later one able to finish.
