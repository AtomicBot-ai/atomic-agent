# CLI frontend

Status: current
Owner: src/cli/

Owns command parsing and terminal entry points. User turns enter runtime.runTurn; preserve exit semantics, state-dir selection and separation from release scripts.

Entry point: [index.ts](index.ts). Read the root instruction route and the underlying domain instructions before cross-domain changes.

Skill list/show/enable/disable accept `--workspace <dir>` for cloud project scope; `skill project on|off --workspace <dir>` controls all project sources. Without the flag enable/disable remain global. See [cloud skill controls](../skills/docs/cloud-workspace.md).

`skill eval <skill> [--tasks <tasks.yaml>] | --all [--check-tasks] [--repeat <n>] [--only with|without] [--max-steps <n>] [--no-approval] [--json] [--keep-workdir] [--judge-url <url>] [--judge-model <id>]` (ATO-1098, [skill-eval-command.ts](skill-eval-command.ts)) runs each task once with the skill in the catalog and once with it hidden, on a fresh temp working folder per run, checks the answers and saves the comparison to `<stateDir>/skill-evals/<skill>/<runId>.json`. The skill is hidden in memory only; `config.json` is not written. Memory is read-only for every run (`memoryReadOnly`), so one variant cannot leave notes or lessons for the other. Approval requests are denied and counted, since nobody answers them; `--no-approval` boots at the top level. `judge` checks are graded by one of the person's own models (ATO-1101): `ATOMIC_AGENT_JUDGE_URL` + `_MODEL`, else `skills.eval.judgeProvider`, else the active cloud provider; with none of them (a local model active) a tasks file with judge checks stops before anything runs. The judge's tokens and cost are printed on their own line and saved as `judgeUsage`. Exit 0 when every planned run finished, 1 when stopped early or on an error, 2 on bad arguments or a missing judge. Without `--tasks` only a packaged starter's `evals/tasks.yaml` is used (ATO-1163); an installed skill's tasks file runs only when named with `--tasks`. `--all` evaluates every starter that has one and `--check-tasks` only prints where it is. Format and result file: [Skill Lab](../skills/eval/README.md).

`run` reads stdin through one line queue ([stdin-line-queue.ts](stdin-line-queue.ts)): every line is kept in arrival order, a line written while a turn runs becomes the next message, and an approval prompt takes its answer from the same queue. A driver can pipe the task, a `y` and the next message at once. The prompt takes only a line shaped like an answer (`y`, `yes`, `n`, `no`, `s`, `a`, or an empty line); any other line denies and stays queued as the next message, so piping "task" and "continue" without an answer loses nothing. EOF before an answer denies, and a prompt that fails denies without stopping later input (ATO-781, ATO-802). Because a piped multi-line prompt still runs one turn per line, the first time a second piped line becomes its own turn `run` prints a one-line notice to stderr; a terminal session gets no notice (ATO-910).

Headless `run` (ATO-2307; precedents `claude -p --output-format stream-json`, `codex exec --json`): `run [flags] "<task>"` runs one turn with the argument (positional words are joined) and reads stdin only for approval answers. `--output-format json` prints one `result` object on stdout; `stream-json` (alias `--json`) prints JSONL, one object per line: `start` (`sessionId`, `cwd`, `resumed`, pinned `providerId`/`model`), `turn_started`, `tool_call`, `tool_result` (both with the `step`), `message` (`progress: true` for a progress note), `error` (`fatal` for a failed turn), `turn_finished`, and last `result` (`isError`, `sessionId`, `status`, `result` = the last reply, `turns`, `steps`, `durationMs`, `lastError`, `usage`). In both JSON formats stdout carries JSON only and the logs stay on stderr; a resume or runtime failure still ends with a `result` that has `isError: true` and `error`. `-m/--model` pins every turn ([run-model-pin.ts](run-model-pin.ts)): a configured provider id, `<provider>:<model>`, or a model id on the active provider; a per-turn model on a local provider exits 2 before boot. `--resume <id|prefix>` and `-c/--continue` (the newest chat of this folder only) go on with a saved chat, which keeps its own folder; neither runs with `--incognito`. `-o/--output-last-message <file>` writes the last reply with its newlines. Exit codes are unchanged. Examples: `atag run --json "count files in src" | jq -c 'select(.type=="result")'`; cron: `atag run -c -o ~/report.txt "summarise today's changes"`.

`config get --with-sha256` prints `{"sha256": "<hex>", "config": {...}}`: the normalised config and the lowercase sha256 of the raw `config.json` bytes it was parsed from, from one read (the empty-string hash when the file is missing). `config set - --expect-sha256 <hex>` writes the stdin payload only while the file still hashes to `<hex>`; otherwise it writes nothing, prints exactly `config changed since it was read` to stderr and exits 3. Without the flag `set -` is unchanged. This is the compare-and-swap the desktop uses since it shares the terminal agent's state dir (ATO-416); see [config-sha256.ts](config-sha256.ts).

`config secrets [status|keychain|env]` shows or switches where saved API keys and tokens live: `<stateDir>/.env` (default) or the OS keychain (opt-in, ATO-474). Switching moves the keys both ways and prints names only; exit 1 when the keychain failed and keys were left where they were. `config secrets set|get|unset <NAME>` (ATO-1639) save, read or remove one `*_KEY`/`*_TOKEN`/`*_SECRET`/`*_PASSWORD` value wherever keys live now, the value on stdin for `set`; the desktop app uses them (and `PUT /api/secrets/{name}` while `atag serve` is up) so both apps read the same key. When the agent's own shell runs any of `secrets get|set|unset|env|keychain` (under any binary name, options between the words skipped; also when `config`, `secrets` or the subcommand is a `$VAR`/`$(...)`, or `xargs`/`find -exec` supplies the subcommand), the shell guard asks every time below full trust (`dangerous.secrets_value_access`, `dangerous.secrets_store_move`, ATO-1647); no `shell` grant covers it. See [config-secrets-command.ts](config-secrets-command.ts) and the [config compatibility notes](../config/docs/compatibility.md).

Before any command runs, the entry reads `network.offline` from config.json without writing it ([offline-from-config.ts](offline-from-config.ts)) and turns offline mode on when it asks for it, so commands that build no runtime (`update`, the skill and plugin hubs) are refused remote hosts too. A missing or malformed file counts as off (ATO-1084, [offline mode](../llm/docs/offline-network.md)).

On a Windows console, startup switches the code page to UTF-8 (65001) so non-ASCII text and the output of console programs the agent runs are not garbled, and restores the original page on exit. It skips a non-TTY stdout (the desktop app reads through pipes), a console already on UTF-8, and macOS and Linux; a failing `chcp` never stops startup. See [windows-console-utf8.ts](windows-console-utf8.ts) (ATO-221).

`doctor [--fix] [--undo] [--json]` (ATO-577) runs a registry of checks ([doctor-checks.ts](doctor-checks.ts)): config.json parses and passes the schema, it is readable by its owner only, and every enabled stdio MCP server's command is installed. A check may offer a bounded fix: an unknown `llm.activeTextProvider` becomes the first configured provider (another schema error in the file stays a reported failure), a missing MCP command turns that server off, a loose file mode becomes 600. Broken JSON and other schema errors are reported, never guessed at. `--fix` copies config.json to `<stateDir>/doctor-backups/config-<time>.json` before it edits the tree; `--undo` restores the newest copy and removes it. The state dir comes from `ATOMIC_AGENT_STATE_DIR` without loading the config, so the command runs when the config is the broken thing. Exit 1 while any check fails. Once the config is valid it also checks the local engine (installed, model on disk, enough memory, server running or its port free; external mode: the server answers) or, when a cloud provider is active, its key with one test token ([doctor-engine-checks.ts](doctor-engine-checks.ts)); these say the command that fixes them.

`id` (ATO-1466, [id-command.ts](id-command.ts)) prints the support ID, the anonymous install id from `~/.atomic-agent-install-id` or `<stateDir>/analytics.json`, so a user can paste it into a bug report. It only reads; with analytics off it still prints the local id. `doctor` ends its text output with the same id.

`usage` (ATO-2352, [usage-command.ts](usage-command.ts)) prints tokens and cloud cost per day over every session, terminal and desktop app together: calls, input, output and cached tokens, the share a local model served, and the priced cloud cost (`+` when some calls had no known price, `n/a` when none had one). `--days N` (default 7, today included), `--all`, `--models` (one line per model and billing kind), `--json`. It only reads `<stateDir>/usage-history.json` ([usage-history.ts](../session/usage-history.ts)).

`policy show [--json]` (ATO-587, [policy-command.ts](policy-command.ts)) prints the organization policy in force and where each part came from; see [../policy/README.md](../policy/README.md).

`data backup|restore|move|reset|path` (ATO-579, [data-command.ts](data-command.ts), [data-archive.ts](data-archive.ts)) acts on the state dir the terminal and the desktop share. `backup <file.tar.gz>` writes an owner-only archive with a manifest; each `*.sqlite` goes in as a snapshot through SQLite's backup API, and `models/` (unless `--with-models`), `browser-profile/` (cookies), WAL/SHM, locks and runtime records stay out. `restore <file> --yes` unpacks into a sibling folder, refuses an archive without the manifest, carries this machine's `models/` over when the backup has none, then swaps folders and keeps the old one as `<stateDir>.before-restore-<time>`. `move <dir>` moves the folder (copy and remove across disks) and leaves a symlink (a junction on Windows) at the old path, so both apps keep finding it. `reset --keep-models --yes` moves everything but `models/` to `<stateDir>.reset-<time>`. Nothing is deleted; close every Atomic Agent first.

`setup export [-o <file>] [--include-memory]` and `setup import <file> [--dry-run] [--force] [--acknowledge-risk]` (ATO-1073, [setup-command.ts](setup-command.ts)) share an agent setup with its keys taken out; the contract is in the [setup-share guide](../setup-share/README.md).

`data export-dataset --out <file.jsonl> [--sessions <n>] [--since <date>]` (ATO-1104, [data-export-dataset.ts](data-export-dataset.ts)) writes the stored chats as a chat fine-tuning file, one `{"messages":[{role, content}, ...]}` line per chat, newest first. Only user messages and the agent's closing answers go in (`SessionStore.listChatLines`); tool calls, tool output and progress notes never do. Every message is scrubbed first ([src/session/dataset-export](../session/dataset-export/scrub-dataset-text.ts)): keys, tokens and passwords become `[redacted:<kind>]`, emails `<email>`, home folders `~`, and the command prints how many of each it replaced. The file is created owner-only, never over an existing one, and nothing is uploaded.


`ideas list|refresh|show|accept <id> [--prompt <text>]|dismiss <id>` (ATO-458, [ideas-command.ts](ideas-command.ts)) shows and decides the suggestions built from local tasks and goals ([contract](../tasks/README.md#suggestions-ideas)). `accept` files a pending task (origin `cli`) that runs on the next drain; a Retry keeps the original task's limits, notify and folder.

`logbook start|stop|pause|resume|status|today|show|clear|exclude|standup` (ATO-2363, [logbook-command.ts](logbook-command.ts)) switches and reads the day journal kept from screenshots described by a local model only; it writes only `<stateDir>/logbook/`. Capture runs only while the terminal app is open, where the top bar shows it; `serve` and the desktop app never capture. `clear --all` asks `[y/N]` in a terminal and, without one, deletes nothing unless `--yes` is given ([logbook-clear-confirm.ts](logbook-clear-confirm.ts), ATO-2770, like `gh repo delete --yes`). Contract: [logbook](../logbook/README.md).

`push on|off|status|test` (ATO-1129, [push-command.ts](push-command.ts)) sets up phone notifications through ntfy (`notifications.push`). `on [--server <url>] [--new-topic]` mints a random topic the first time (kept on later `on`s; a new server mints a new one) and prints the URL to subscribe to in the ntfy app plus the warning that topics on ntfy.sh are public by name; `off` keeps the topic; `test` sends one ping and exits 1 with the reason when it is not delivered. An optional access token is read from `NTFY_TOKEN` in `<stateDir>/.env`.

`composio accounts list [--connected] [--json]|add <app> <name> <account-id> [--default]|remove <app> <name>|default <app> <name>|default <app> --clear` (ATO-1494, [composio-command.ts](composio-command.ts)) edits `composio.accounts` through the ATO-548 helpers: a short local name per Composio connected account and one default per app, which is pinned on the next session. `list --connected` also asks Composio which accounts are signed in, so the `ca_…` id can be copied; `--json` prints `{ accounts, connected? }` for the desktop and scripts. A bad name, a duplicate or an unknown account exits 1 and writes nothing. Changes take effect the next time the agent starts.

`overnight "<task>" [--budget <usd>] [--hours <h>] [--dir <path>] [--notify telegram] [--detach] [--no-approval]` (ATO-1113, [overnight-command.ts](overnight-command.ts)) creates one durable one-shot task (origin `cli`, one attempt) with the task's `maxCostUsd` and `maxDurationMs` (ATO-1108) and runs it. No `--budget` leaves the cap to `agent.task.maxCostUsd`; no `--hours` means 8. `--dir` becomes the runtime's working dir, so the run's session and every tool work there. Foreground prints one line per step to stderr ([overnight-progress.ts](overnight-progress.ts)) and a summary to stdout. Exit 0 when the agent finished on its own; 2 when a limit ended the run (the row is `completed` with a `stopCause`, or `blocked` with `budget_spent:` / `time_spent:`), and the summary then says `overnight stopped (<cause>)`; 1 when it failed or was cancelled (ATO-1323). An approval request is denied and counted, since nobody answers it; `--no-approval` boots at the top level. `--detach` re-runs the same command as a detached child (cwd = `--dir`, output to `<stateDir>/logs/overnight-<id>.log`) under a task id it prints first. A `task cancel` from another terminal is seen within 5 s and aborts the turn. The task carries `agent.task.maxSteps` as its step ceiling, so the per-leg `agent.maxSteps` does not end the run. Ctrl+C (SIGINT) cancels the task; SIGTERM and SIGHUP (shutdown, logout) stop the run the way a runtime shutdown does and leave the task pending to resume. Step lines count what the task spent before this run toward the cap.

[skill-eval-diff-formatter.ts](skill-eval-diff-formatter.ts) (ATO-1100) renders the `skill eval` result: one row per task plus a total, accuracy (passed/total), wall time and tokens in/out as `without -> with` with a delta column (accuracy in percentage points, the rest in percent; `n/a` against a zero baseline), and a verdict line. A task missing one side shows `-` and stays out of the total. Verdict: accuracy moved by 10 points or more decides; otherwise time or tokens down by 20% or more with nothing up by 20% is helped, the mirror is hurt, anything else is no clear difference. Plain text unless the caller passes `color` (`shouldUseColor` honours NO_COLOR and FORCE_COLOR).

`models toolcall-bench [--models a,b] [--tries n] [--json]` (ATO-1092, [models-toolcall-bench.ts](models-toolcall-bench.ts)) sends the fixed prompts of [toolcall-bench](../llm/toolcall-bench/bench-cases.ts) to each model `n` times (default 3, at most 50), one request at a time, and prints per model the share of tries with valid JSON arguments, the right tool and every required argument, plus parse failures, text-only answers, errors and the mean time of a try. A model is `<provider>` (its configured chat model) or `<provider>:<model>`, split at the first colon; no `--models` means the active provider. Only native-tools links are measured: the built-in local link and subscription CLIs use a grammar or their own CLI and are skipped with a note; to bench a local model, add its server as an openai-compatible provider. `models ask "<question>" --models a,b [--json]` sends one question, no tools, to every named model at once and prints the answers one after another under each model's name; exit 1 only when every model failed. `models council "<question>" --models a,b [--judge c] [--json]` (also `models ask --council`, ATO-2232, [models-council-command.ts](models-council-command.ts)) asks the same way, then one judge model (the first listed unless `--judge` names another; a judge outside `--models` only judges) reads the answers under letters, with the model names hidden as in llm-council, and the [council parser](../llm/toolcall-bench/model-council.ts) prints what they agree on, where they disagree and what only one answer said, under the model names; one answer skips the judge (with fewer than two models named it also says how to name them with `--models`), and a failed judge exits 1 after the answers.

## Desktop state merge

`import atomic-desktop --source <dir> [--json]` merges the desktop app's former state dir (`~/.atomic-agent-desktop`) into the current one (`ATOMIC_AGENT_STATE_DIR`, default `~/.atomic-agent`) when the desktop moves onto the shared dir (ATO-416). The desktop runs it once and moves the plain files (config.json, .env, skills, traces, models) itself; this command handles only the databases:

- sessions and tasks keep their ids and are inserted only where the id is absent, so the target wins. A live turn arrives ended as interrupted, a running task arrives pending, and neither carries an owner mark.
- memory notes are added through `MemoryStore` unless the same text is already stored; profile facts through `ProfileStore` unless the target has any row for the key.
- lessons, procedures, votes, note links and embeddings are not copied; the embedding backfill or `memory reindex` rebuilds vectors.

Each source database is read from a private snapshot (a byte copy after a clean close, otherwise SQLite's online backup over a read-only connection), so the source is never written and nothing is deleted. Writes are short transactions that wait on the target's locks, so a TUI or `serve` may keep the target open. A re-run imports nothing new. `--json` prints one object, `{ok, sessions:{imported,skipped}, tasks, notes, profileFacts, warnings, error?}`; exit 0 only when every part imported. Implementation: [atomic-desktop importer](../import/atomic-desktop/atomic-desktop-importer.ts).

Checks: `npx vitest run src/cli` when tests are present; `npm run lint`; `npm run docs:check`.

## Handoff

`handoff --from claude-code|codex [--session latest|<id>] [--cwd <dir>] [--note <text>] [--list] [--json] [--no-open]` continues a Claude Code or Codex session that stopped mid-task (ATO-1154). It reads their transcript through the import readers ([handoff source](../import/handoff/handoff-source.ts)), saves it as a NEW native chat with a fresh `s-` id ([handoff session](../import/handoff/handoff-session.ts)), closes trailing tool calls that never got a result, and opens the TUI on it with `--session <id> --send <continuation message>`. `latest` is the newest session that ran in the current folder, else the newest anywhere. `--list --json` prints `{from, sourceDir, sessions:[{agent,id,mtimeMs,cwd,title,messageCount}]}`; `--json` without `--list` saves the chat without opening it and prints `{ok, sessionId, title, workingDir, from, sourceSessionId, turns, closedCalls, prompt}` (the desktop uses both).

Before saving, the carried history is fitted into a local model's window (ATO-1155, [fit-context](../import/handoff/fit-context.ts)): when it is larger than half the window (`--context <tokens>`, default the managed model's pinned `contextSize`, else 32768; `0` skips this), the head becomes an extractive checkpoint (`SessionCompaction`, `kind: "extractive"`, no model call) cut at a safe boundary, the newest records stay verbatim, and very long tool outputs in that tail are clipped in the middle. `--json` reports it under `context`.

`models rpc-worker [--lan | --host <ip>] [--port <n>] [--cache]` (ATO-2338, [models-rpc-worker.ts](models-rpc-worker.ts)) lends this computer's memory and GPU to a model running on another one: it starts llama.cpp's `rpc-server` (from `ATOMIC_AGENT_RPC_SERVER`, the managed backend folder, or PATH) in the foreground on port 50052, loopback unless `--lan` or `--host`, and prints the `localModels.managed.rpcServers` value to set on the main computer. llama.cpp RPC has no authentication, so opening it to the network prints a warning. ## Share

`share [--session latest|<id>] [--format html|md] [--out <file>] [--gist] [--json]` (ATO-581, [share-command.ts](share-command.ts)) writes one chat to a single file for a colleague. It reads only `SessionStore.listChatLines` (user messages and closing replies), so tool results and reasoning never enter the file, then runs each message and the title through [chat-export redaction](../session/chat-export/chat-export-redact.ts): shared secret detector plus a looser layer, absolute paths to `[path]` (paths under the chat's folder keep their tail as `<project>/...`), emails, IPv4, URL query strings and `<think>` blocks. HTML is self-contained with a `default-src 'none'` CSP and no script; text is escaped before a small Markdown subset is applied. Default file: `<stateDir>/shared-chats/chat-<id>.<ext>`, owner-only. `latest` is the newest chat in the current folder, else the newest anywhere; a unique id prefix works.

`recipe check <file|-|link> [--json]` and `recipe link <file|->` (ATO-1070, [recipe-command.ts](recipe-command.ts)) work on a shared recipe ([recipes](../recipes/README.md)). `check` validates it, runs the content check and prints what opening it will do; exit 0 for ok or caution, 1 for an invalid or dangerous recipe, and `--json` prints `{ok, recipe, verdict, findings, scanId, willDo}` or `{ok:false, error}`. `link` prints the `atomicagent://recipe/open` link the desktop opens, refuses a dangerous recipe and notes a caution on stderr. An `http(s)://` argument is refused without fetching: a v1 recipe travels inside its link.

`--gist` is the only path off the machine ([share-gist.ts](share-gist.ts)). After writing the file it prints a preview (title, message count, what was removed, first messages, who can read a secret gist) and asks `[y/N]` in a terminal; only a typed y/yes uploads, with `gh gist create <file> --desc <title>` (secret, `--public` never passed; the token stays in gh). Without a terminal it refuses and exits 1. With `--gist` and no `--format` the file is Markdown, since GitHub renders Markdown and shows HTML as source. `--gist` cannot be combined with `--json`.


## MCP server

`mcp-server [--allow-write] [--allow-exec] [--tool <name>]... [--cwd <dir>]` (ATO-549) serves the agent's own tools to another MCP client (Claude Code, Codex, Cursor) over stdio, e.g. `claude mcp add atomic-agent -- atag mcp-server`. It boots no runtime and no model: [mcp-server-command.ts](mcp-server-command.ts) opens the memory database and the skill folders, [mcp-server-tools.ts](mcp-server-tools.ts) builds the tools with the runtime's own builders, and [mcp-server-bridge.ts](mcp-server-bridge.ts) answers `tools/list` and `tools/call` through a `ToolRegistry`, so secret masking applies. It exits when the client closes stdin; stdout carries only the protocol.

- Default, read-only: `memory_notes_recall` (keyword recall; embeddings are not attached here), `memory_lessons_recall`, `memory_procedures_recall`, `memory_profile_list` (each only when its `memory.*` family is on), `skills_list` and `skill_view`. Project skills load only from a folder the user trusted, as in the runtime.
- `--allow-write` adds `memory_notes_store` and `memory_profile_set`.
- `--allow-exec` adds `os_shell_run`. Every command still goes through `ApprovalGate` with the user's `agent.approvalLevel` and saved rules; the session (`mcp-server`) runs under a refuse policy, because an MCP client cannot show the approval prompt. So a command that would ask is refused with a message telling the client to ask the user, and only a level or an allow rule lets one run. The hardline shell guard blocks as always.
- `--tool` narrows the set (wire or dotted name); a name the flags do not allow is a usage error (exit 2).

Tool names on the wire use `_` for `.` because several clients accept only `[A-Za-z0-9_-]`. Results carry the whole text (`modelMode: "cloud"`), not the local model's short previews. Not done yet: a session turn or task tools.

Over HTTP, `serve` answers the same read-only set on `/mcp` (MCP Streamable HTTP, spec 2025-03-26 and 2025-06-18): see [route-mcp-endpoint.ts](../http/route-mcp-endpoint.ts). `POST /mcp` takes JSON-RPC and answers JSON or SSE, `initialize` opens a session named by `Mcp-Session-Id`, `GET /mcp` opens the server's SSE stream and `DELETE /mcp` ends the session. It is the SDK's `StreamableHTTPServerTransport` connected to `createMcpServeServer`, behind serve's bearer key and loopback guard, and a foreign `Origin` is refused even with the key (DNS rebinding). Writes and the shell stay on the stdio command.


`handoff --to claude|codex [--out <file>] [--session latest|<id>] [--cwd <dir>]` goes the other way (ATO-1158): it reads one Atomic Agent chat (`latest` = the newest chat in the folder, else the newest anywhere) and writes a Markdown handoff for the other agent ([handoff export](../import/handoff/handoff-export.ts)): the task and the latest request, the agent's last answers as decisions, open items (a turn that did not finish or was stopped), and the files changed by successful `os.fs.write|edit|move` calls and applied `os.fs.patch` calls (shell changes are not tracked). It goes to `--out` (relative to where the command ran) or to stdout. Nothing is written into `~/.claude`, `~/.codex` or the session store: their session formats are undocumented, so the person hands the file over themselves. Serving Atomic Agent to those tools over MCP/ACP is ATO-990, not this command.

## Launch another coding CLI

`launch <claude|codex|opencode> [--model <id>] [--print-env] [-- <args>]` (ATO-2172, [launch-command.ts](launch-command.ts)) starts Claude Code, Codex or OpenCode pointed at `atag serve` on this machine, like `ollama launch`. It finds the binary on PATH (exit 1 with the install command when it is missing), reuses a serve on record that is alive, answers `/health` with its recorded pid, listens on loopback and works in the current folder, else starts `serve --host 127.0.0.1 --port <free> --cwd <folder>` in the background (own process group, log in `<stateDir>/logs/launch-serve-<port>.log`) and waits for it ([launch-serve.ts](launch-serve.ts)). That serve has the launch process as its parent, so its orphan guard stops it when the CLI exits. The key is the one serve uses (`ATOMIC_AGENT_API_KEY`, else `<stateDir>/serve-api.key`), checked against the serve before the CLI starts. Per CLI ([launch-integrations.ts](launch-integrations.ts)): Claude Code gets `ANTHROPIC_BASE_URL`, `ANTHROPIC_AUTH_TOKEN` and an empty `ANTHROPIC_API_KEY` (plus `ANTHROPIC_MODEL` and the small-model names with `--model`); Codex gets `-c` overrides for a `model_providers.atomic` entry with `wire_api = "responses"` and `env_key = ATOMIC_AGENT_TOKEN`, and `-m <model>`; OpenCode gets `OPENCODE_CONFIG_CONTENT` with an `@ai-sdk/openai-compatible` provider whose `apiKey` is `{env:ATOMIC_AGENT_TOKEN}`. The key travels only in the environment; `--print-env` prints the variables and the command with it masked and starts nothing. The CLI runs with the terminal attached, Ctrl+C is its own, and its exit code is the command's. Nothing is written to the CLI's config files. Answers come from the agent turn path of the compat routes ([HTTP guide](../http/README.md)), so the active model answers whatever `--model` says and the CLI's own tool calls are not offered to it. A serve started by launch runs with `--refuse-approvals` ([serve-refuse-approvals.ts](serve-refuse-approvals.ts)): those CLIs never see an approval prompt, so every request that would prompt is denied at once with a reason the agent turns into text, instead of waiting forever; what the approval level, a grant or a rule allows still runs. The banner says so, and for a reused serve points at its `/panel` page.

## ACP server

`acp [--setup]` (ATO-543) serves the agent to Agent Client Protocol clients (Zed `agent_servers`, JetBrains `~/.jetbrains/acp.json`, Neovim plugins) over stdio: newline-delimited JSON-RPC 2.0, one runtime per working folder (`session/new`'s `cwd`), built by `createAgentRuntime` as for the sidecar. [acp-jsonrpc.ts](acp-jsonrpc.ts) is the framing, [acp-translator.ts](acp-translator.ts) the pure mapping, [acp-server.ts](acp-server.ts) the protocol state, [acp-command.ts](acp-command.ts) the entry.

- `initialize` answers protocol version 1, `embeddedContext` prompts, no `loadSession`, and one auth method of type `terminal` (`args: ["--setup"]`, plus the older `_meta["terminal-auth"]` form): the ACP registry's CI requires an `agent` or `terminal` method. `acp --setup` opens the TUI's first-run setup (`--onboarding`). `authenticate` with that id is a no-op.
- `session/prompt` runs one `runTurn` (origin `sidecar`, interactive) and streams `session/update`: reply text and deltas as `agent_message_chunk`, reasoning as `agent_thought_chunk`, each tool call as `tool_call` then `tool_call_update` (`reply`, `finish`, `plan.update`, `ask_user` are not shown as calls), the plan as `plan`. Stop reasons: `end_turn`, `max_turn_requests` (step ceiling), `cancelled`.
- Approvals become `session/request_permission` with the TUI's choices: allow once, for this chat (category grant, when grantable), always (saved rule, when one can be built), deny. An `ask_user` question shows its options as the buttons. A cancelled or unknown answer is an automatic denial. A worker session's approval goes to the one running chat in that folder, else it is denied.
- `session/cancel` aborts the turn and denies its pending approvals.
- stdout carries frames only: `process.stdout.write` is pointed at stderr for the life of the command, and runtime warnings and errors are logged to stderr.
- Not yet: `session/load`, modes, the client's `mcpServers` (logged and ignored), the client's file system and terminals.
