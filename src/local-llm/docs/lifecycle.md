# Managed server ownership

Status: current
Owner: src/local-llm/

External mode connects to an operator-provided llama-server. Managed mode uses model/backend installation, launch records and daemon lifecycle. The server process and model weights remain separate from the TypeScript runtime.

Preserve launch ownership, port checks, records, health/model capability probes, restart behavior and stopOnExit. A live daemon discovered through a record is not necessarily a process this caller may kill. Capability/window/prefix-reuse decisions come from server/GGUF metadata and platform selection. Throughput is measured when available rather than fabricated.

## Atomic Core engine

`localModels.managed.engine` selects `atomic-core` (the default) or `llama-server`, the standalone managed llama.cpp server kept as a support-only fallback. Config v77 moved older files to `atomic-core`, because the choice used to sit behind an opt-in; an explicit choice made since is honoured. Core is the engine: the TUI and desktop composers draw no engine choice. llama.cpp is never offered in the UI; it is reached through `atomic-agent models engine llama-server` or `/model engine llama-server` in the TUI, with local models stopped, for support, and automatically on a computer Core has no build for (below); the desktop's Settings › Models › Advanced shows a way back to Core only while llama.cpp is selected. The same downloaded GGUFs, native completion/grammar protocol, context sizing and optional embedding model remain available, and Fusion uses whichever engine is selected. `models engine status` reports the engine (`choiceEnabled` is always true).

First run installs what is missing: with `atomic-core` selected and Core or its backend absent, `models start`, `models start-embedding`, the TUI start and its launch auto-start install Core and its backend with progress before starting ([ensure-latest-backend.ts](../backend/ensure-latest-backend.ts)). An install of an older pinned Core moves to this build's pin on start when `managed.autoUpdate` allows it: the new pin installs into its own version folder even while the older Core serves models, and the active version switches only when no model runs (the next idle start switches without downloading again). A failure is a `CoreUnavailableError` ([core-errors.ts](../core/core-errors.ts)) with a stage (`download`, `verify`, `backend`, `start`), a fixed reason code and whether a retry can help. A retryable one says what happened and gives one way forward: `models update` (TUI: `R` in Models). A computer Core has no build for (`no_backend`, `unsupported`, e.g. Linux arm64 without NVIDIA) gets a plain sentence instead (Windows on ARM keeps the ATO-252 sentence); `models start`, `start-embedding`, `update` and the TUI start then report `local_engine_failed`, switch `localModels.managed.engine` to `llama-server` once with one line, install llama.cpp and continue in the same call. Retryable failures never switch.

`models update` installs the host-supported Core release and asks Core's backend catalog to select and install the inference binary. `models engine check` checks release metadata without installing. Startup with an installed Core of this build's pin does not download an engine. Readiness is Core's load answer, not a generation; after it, as on the llama-server engine, one short generation on the session's port and key measures single-stream speed, and later starts of the same model, Core backend, device and context within a day carry that figure over instead (`throughputProbe: false` skips both). A newer release outside the supported version list is reported as requiring a newer Agent build. Older pinned versions stay readable so their installs and sessions stop cleanly; once this build's Core is up, an idle daemon of an older pinned version is asked to shut down, once per process.

Downloads are bounded and resumable. The checksum manifest is fetched up to three times with backoff on network errors and 5xx. The binary keeps a stable staging path per version, retries up to three server errors with backoff and network failures until two minutes pass without progress, and resumes its partial with a Range request on every retry and on the next run (restarting when the server ignores Range). Core's backend install call is retried up to three times on a dropped connection or a 5xx. A cancelled operation is never retried.

The host follows Atomic Chat's authenticated control contract: a private, CLI-scoped Core in `<models data dir>/core/versions/<version>/data`, exact version/protocol handshake, client registration with heartbeats, backend catalog/install, model load/unload and download progress events. CLI scope lets a one-shot `models start` leave a warm model available. `models stop` (the desktop quits through it), a failed `models update`/`start-embedding` and every TUI exit ask an idle Core to `/shutdown` without force, bounded to a few seconds; Core refuses while another client is attached, and the agent skips it while any model session remains. Telemetry is disabled for this managed Core, and its environment drops provider keys and other secret-shaped variables ([core-env.ts](../core/core-env.ts)). The public Core API listener is not enabled.

Model inference goes directly to the port and key returned by Core (loads ask Core to offload the vision projector, as the llama-server engine does; a session Core reloaded without its projector is reported as text-only), preserving `/completion`, `/props`, `/apply-template` and `/slots`. The device pick and the context fit ask `--list-devices` of the llama-server Core recorded for its active backend, run with the environment Core runs it with (its directory on the library path, the CUDA runtime directories Core finds; [core-backend-env.ts](../core/core-backend-env.ts), [managed-devices.ts](../backend/managed-devices.ts)); a listing that cannot run is reported as such, not as a machine without a GPU. Session keys stay in owner-only records and are used only for matching loopback endpoints. Core owns its children: normal teardown and cancellation use authenticated control operations rather than sending signals to a recorded model PID. Port clearance recognises Core's llama-server under `<data dir>/core/versions/` as ours: its live session on the port is adopted (or unloaded through Core when it serves another model), never moved. When Core crashed but a session's llama-server lives on, status reports it, its key still works, and the next start or stop starts Core again so the new owner reaps it from its process journal.

Image generation ([core-image.ts](../core/core-image.ts), the `image.generate` tool) always runs on this build's Core pin, since older pins have no cloud media. A computer without that Core gets the Core binary alone (no inference backend) the first time a picture is asked for. Install, start and the client lease happen under the engine operation lock (waiting up to 5 minutes for a model load); the generation itself holds only the lease, so a model load in another window is not blocked for minutes. A cloud job registers the OpenRouter key with `PUT /cloud/providers/openrouter` on every call (never through Core's environment) and sends `target: {provider, model}`; it needs no stable-diffusion engine. A local job first points `PUT /diffusion/config` at Core's own data folder. Jobs are polled (`GET /diffusion/jobs/:id`) and cancelled on abort; the submit is never retried, because a provider would bill twice. A Core the generation started (none was running), or one of this pin beside an older active one, is shut down again when idle: on a cloud route nothing else stops it (quit and idle stops look only at the active version and only for the Atomic Core engine), and in the live check it outlived the app. A Core already running for a model is left alone.

An embedding model whose architecture the TurboQuant fork cannot run (`requiresCoreEmbeddingModule`, EmbeddingGemma 2) runs in Core's own embedding module instead of a model session ([core-embedding.ts](../core/core-embedding.ts)). Start configures the module (`PUT /embedding/config`, text only, the GGUF's own pooling) and loads it; when Core reports no stock llama.cpp build new enough (`EMBEDDING_ENGINE_UNSUPPORTED`), the start installs one from Core's `llamacpp-upstream` catalog, which Core already gates for this hardware (an installed build at or above b11454 that the catalog offers first, then Core's recommendation, then the newest available build), with the same progress, cancel and retries as the backend install, and loads again; a build already installed that Core still refuses is reported, not reinstalled. The module needs this build's Core pin: an older active Core is switched when idle, otherwise the start says to stop models or update. Core owns that process and its port: there is no pid file, the configured embedding port is not cleared, and `core/embedding-module.json` lets status and stop find it without starting Core. Stop turns the module off and then retires an idle Core. It never starts Core for this: with Core down (or refusing the change) the record is marked `disablePending`, and the next Core start turns the module off before anything else uses it. A failed start turns the module off the same way. A record of a model other than the configured one is not reported as its status, and starting another embedding model or switching engines turns a leftover module off first. An idle Core with the module on is neither shut down nor switched to another version. Memory reaches it through `POST /embedding/embed` on the control API, never through the embedding URL, and attaches only when Core reports the module on for that model with the catalog's dimension. On the llama-server engine such a model fails at once with the command that switches engines.

Installations verify GitHub SHA256SUMS and the executable version before activation. Failed or cancelled downloads leave the current install intact. Mutating engine operations are serialized across frontends; start, stop and engine selection wait up to 30 seconds for another frontend's operation, an install never waits, and checks do not acquire the long operation lock. Updates refuse while Core has model sessions. Interrupted operations can recover a dead owner through an exclusive acquisition gate; a crash during that brief gate requires removing the named stale gate with Agent closed.
