# Managed server ownership

Status: current
Owner: src/local-llm/

External mode connects to an operator-provided llama-server. Managed mode uses model/backend installation, launch records and daemon lifecycle. The server process and model weights remain separate from the TypeScript runtime.

Preserve launch ownership, port checks, records, health/model capability probes, restart behavior and stopOnExit. A live daemon discovered through a record is not necessarily a process this caller may kill. Capability/window/prefix-reuse decisions come from server/GGUF metadata and platform selection. Throughput is measured when available rather than fabricated.

## Atomic Core engine

`localModels.managed.engine` selects `atomic-core` (the default) or `llama-server`, the standalone managed llama.cpp server kept as the way back. Config v77 moved older files to `atomic-core`, because the choice used to sit behind an opt-in; an explicit choice made since is honoured. Core is the engine: the TUI and desktop composers draw no engine choice. llama.cpp is offered when Core cannot run (the core failure notice's `L`, the desktop's recovery card) and through `atomic-agent models engine <engine>` or `/model engine <engine>` in the TUI, with local models stopped; the desktop's Settings › Models › Advanced shows a way back to Core only while llama.cpp is selected. The same downloaded GGUFs, native completion/grammar protocol, context sizing and optional embedding model remain available, and Fusion uses whichever engine is selected. `models engine status` reports the engine (`choiceEnabled` is always true; [experimental.ts](../core/experimental.ts) keeps the old export).

First run installs what is missing: with `atomic-core` selected and Core or its backend absent, `models start`, `models start-embedding`, the TUI start and its launch auto-start install Core and its backend with progress before starting ([ensure-latest-backend.ts](../backend/ensure-latest-backend.ts)). An install of an older pinned Core moves to this build's pin on start when `managed.autoUpdate` allows it; otherwise the existing install keeps serving. There is no silent fallback: a failure is a `CoreUnavailableError` ([core-errors.ts](../core/core-errors.ts)) with a stage (`download`, `verify`, `backend`, `start`), a fixed reason code and whether a retry can help. Its message says what happened and gives both ways forward: `models update` (TUI: `R` in Models) or `models engine llama-server` (TUI: `L` in Models, or `/model engine llama-server`).

`models update` installs the host-supported Core release and asks Core's backend catalog to select and install the inference binary. `models engine check` checks release metadata without installing. Startup with an installed Core of this build's pin does not download an engine or run a synthetic generation. A newer release outside the supported version list is reported as requiring a newer Agent build. Older pinned versions stay readable so their installs and sessions stop cleanly; once this build's Core is up, an idle daemon of an older pinned version is asked to shut down, once per process.

Downloads are bounded and resumable. The checksum manifest is fetched up to three times with backoff on network errors and 5xx. The binary keeps a stable staging path per version, retries up to three server errors with backoff and network failures until two minutes pass without progress, and resumes its partial with a Range request on every retry and on the next run (restarting when the server ignores Range). Core's backend install call is retried up to three times on a dropped connection or a 5xx. A cancelled operation is never retried.

The host follows Atomic Chat's authenticated control contract: a private, CLI-scoped Core in `<models data dir>/core/versions/<version>/data`, exact version/protocol handshake, client registration with heartbeats, backend catalog/install, model load/unload and download progress events. CLI scope lets a one-shot `models start` leave a warm model available. On the last TUI session's stopOnExit teardown, after unloading its models, the agent asks an idle Core to `/shutdown` without force; Core refuses while another client is attached, and the agent skips it while any model session remains. Telemetry is disabled for this managed Core, and its environment drops provider keys and other secret-shaped variables ([core-env.ts](../core/core-env.ts)). The public Core API listener is not enabled.

Model inference goes directly to the port and key returned by Core, preserving `/completion`, `/props`, `/apply-template` and `/slots`. Session keys stay in owner-only records and are used only for matching loopback endpoints. Core owns its children: normal teardown and cancellation use authenticated control operations rather than sending signals to a recorded model PID.

Installations verify GitHub SHA256SUMS and the executable version before activation. Failed or cancelled downloads leave the current install intact. Mutating engine operations are serialized across frontends; checks do not acquire the long operation lock. Updates refuse while Core has model sessions. Interrupted operations can recover a dead owner through an exclusive acquisition gate; a crash during that brief gate requires removing the named stale gate with Agent closed.
