## Shared local model (`/raw/v1`)

ATO-2336, after LM Studio's "Serve on Local Network", Jan's Local API Server and Ollama's "Expose". `/v1/chat/completions` runs the agent; `/raw/v1/*` runs only the model. The request goes unchanged to the model server the agent uses now (`localModels.url`: the managed llama-server or Atomic Core), with that server's private key added server-side (`apiKeyForUrl`), and its answer, SSE included, streams back with only `content-type` and `cache-control` copied.

- Off by default. With `localModels.managed.share` not `true` both routes answer the router's 404. The switch is read from the config file on every request, so `atomic-agent models share` (or `--off`) works on a running serve.
- Its own key, `<stateDir>/model-share.key` ([model-share-key.ts](model-share-key.ts), 0600, a state secret). The routes are `requiresAuth: false` and check only this key: the serve key and named tokens get 401 there, and the share key gets 401 on every agent route, since the router never compares against it. Sharing on with no key file: 503. Wrong keys from a network address are throttled like the serve key.
- One request at a time ([raw-model-limit.ts](raw-model-limit.ts)); a second gets 429 `model_busy`, so outside apps cannot take the slots the agent's turns need ([worker-slots.ts](../local-llm/server/worker-slots.ts)).
- Other devices reach it only when serve itself listens beyond loopback (`--host 0.0.0.0`, which already needs an operator key); serve then prints that the traffic is plain http. A body is capped at 1 MiB like every JSON route.

## Ownership and dependencies

The HTTP server owns request handling and connection cancellation; route modules translate transport payloads into runtime operations. Session routes use the existing turn/steering contract, and webhook routes materialize durable tasks. Runtime owns session execution, task storage and approval policy; routes must retain authentication and error mapping. MCP routes use [shared server-config commands](../config/mcp-server-commands.ts) and manager operations, independently of TUI.

[Compaction routes](route-compaction.ts) expose `POST /api/sessions/{id}/compact` and `GET /api/sessions/{id}/compaction`. The POST waits for runtime completion and cancels only its operation on disconnect. See [the shared contract](../runtime/docs/compaction.md). With `x-atomic-extensions: 1`, a chat stream also carries `compaction_started`, `compaction_progress`, `compaction_completed`, `compaction_failed` and `history_trimmed` frames ([mapping](stream-maintenance-frames.ts)): counts and statuses only. It also carries `usage_updated` (ATO-569): the session's spend so far, priced / unpriced / local / plan call counts, and the account's rate-limit windows (used percent, remaining, reset time); the same snapshot is persisted as `sessionUsage` on `GET /api/sessions/{id}`. With `llm.costTracking.showInStatusBar` on or `llm.costTracking.dailyLimitUsd` set, the frame also carries `today: { day, cost_usd, priced_calls, unpriced_calls, limit_usd? }` (ATO-649): what every session spent today, live only and never persisted with a session. `today` is sent only when a configured cloud link has a known price. Once `cost_usd` reaches `limit_usd`, paid cloud links are refused before the request is sent: with `llm.costTracking.onDailyLimit: "stop"` (default) the turn fails with "Daily cloud limit reached: …" (failure cause `daily_limit_reached`); with `"local"` the fallback chain moves on to the local link and a `provider_switched` frame says so. A `tool_disabled` frame (ATO-1417) says a tool was left out of the turn's requests because the server refused its JSON schema: `tool`, `reason` (`schema_rejected`), `step_index` and the chat sentence in `notice`, once per tool per turn. A `loop_stopped` frame (ATO-2004) says the loop guard stopped the turn: `tool`, `step_index` and `detector`; the reply that follows is the summary step's answer or the canned fallback. A `project_instructions` frame (ATO-42) says the local prompt carried the chat's project instructions: `name`, the full text's `tokens`, `truncated` when the block was cut to `max_tokens` (1500), once per turn.

[Turn phases](stream-turn-phase.ts) (ATO-1027): with `x-atomic-extensions: 1`, a chat stream carries `event: turn_phase` on every change of what the turn is doing, `{ object: "atomic.turn_phase", session_id, phase, step_index?, tool?, phase_elapsed_ms, turn_elapsed_ms, progress? }`. `phase` is `starting`, `loading_model` (the local server answered "Loading model"), `waiting_provider`, `processing_prompt` (`progress: { processed, total, cached, fraction }` when llama-server reports prompt progress), `thinking`, `generating`, `running_tool` (`tool` names the call) or `compacting`. A host counts the seconds itself from `phase_elapsed_ms`. Once per turn, when a local model has produced nothing 45 s after the turn began, `event: slow_first_token` carries `{ object: "atomic.slow_first_token", session_id, waited_ms, phase?, model_id?, lighter_model?: { id, name, file_size_gb, downloaded }, cloud_available }` ([hint](slow-first-token-hint.ts)): what the host may offer instead. Nothing is switched. After every model completion, `event: step_speed` carries `{ object: "atomic.step_speed", session_id, step_index?, prompt_tokens, cached_tokens, prefill_ms, decode_ms, decode_tokens_per_second, draft_tokens?, draft_accepted_tokens? }` (ATO-631): whether a slow step was re-reading its prompt or writing slowly. `decode_tokens_per_second` is `null` and the ms fields `0` for a provider that reports no timings (cloud APIs); the draft fields appear only under speculative decoding.

Next-step suggestion (ATO-1093): `GET /api/sessions` rows and `GET /api/sessions/{id}` carry `nextStep`, the suggested next message after the last answered turn, or `null` (setting `tui.nextStepSuggestions` off, nothing stored, a turn running, or a later turn made it stale). `GET /api/sessions/{id}/next-step` answers `200 { sessionId, suggestion }` with the same value (`404` for an unknown id). With the switch off every route serves `null`, also for a suggestion stored while it was on, and `GET /api/sessions/{id}` leaves `metadata.nextStep` out. Read-only; see [session-next-step.ts](../session/session-next-step.ts).

Step labels in history (ATO-1382): `GET /api/sessions/{id}` adds `done_line` to every `assistant_tool_call` row, built from the stored name and args with the same `describeToolCall` the live `tool_progress.done_line` uses, so a reopened chat reads its steps exactly as they read while the turn ran. It is computed per answer and never stored.

Searching past chats (ATO-1149, [session-search.ts](../session/session-search.ts)): `GET /api/sessions/search?q=…` finds words in the user messages and closing replies of stored sessions with SQLite FTS5 (tool calls and tool output are not indexed). It covers the current working directory, or every folder with `scope=all`; `limit` defaults to 10, max 25, at most 3 hits per session. The answer is `200 { query, hits, pending }`: each hit carries `sessionId`, `title`, `workingDir`, `updatedAt`, `line` (index into the session's chat lines), `kind`, `source` (`chat`, `telegram`, `discord`, `webhook`, `task`, `imported`, for a label) and a `snippet` with the matched words in `«` `»`. Task sessions rank below an interactive chat that matches as well; incognito chats, Fusion workers and sessions stamped `metadata.internal` / `metadata.subagent` are never indexed. The index is filled at search time, not on every write: each search reindexes up to 500 sessions changed since they were last indexed, newest first (transcripts read without the write lock, the index written 25 sessions per transaction), and `pending` counts the rest. `400` for an empty or over-500-character `q`, `503` when the index cannot be created.

[Export route](route-session-export.ts) (ATO-1054): `GET /api/sessions/{id}/export?format=markdown|html|docx|pdf[&tools=0]` answers `{ id, format, filename, mimeType, encoding, content }` (`utf8` text, or `base64` for DOCX and PDF), built by [exportChat](../session/chat-export-render.ts). The desktop prints its PDF from the `html` format; `pdf` is the browserless writer (standard fonts, WinAnsi). `400` for another format, `404` for an unknown id.


[Archive route](route-session-archived.ts) (ATO-1150): `POST /api/sessions/{id}/archived` with `{ archived: true | false }` (`400` for anything but a boolean, `404` for an unknown id) archives or unarchives a chat through `SessionStore.setSessionArchived`: `metadata.archived: true`, or no `archived` key once unarchived, stamped with `metadata.archivedSetAt` so a copy read before the change (a turn still running) cannot write the old flag back. `GET /api/sessions` lists `archived` on every row; the desktop's sidebar draws archived chats in their own section and the terminal's rail and session picker leave them out. `updatedAt` is not touched.

[Trash route](route-session-trashed.ts) (ATO-2332): `POST /api/sessions/{id}/trashed` with `{ trashed: true | false }` (`400` for anything but a boolean, `404` for an unknown id) moves a chat to the desktop's Trash or out of it through `SessionStore.setSessionTrashed`: `metadata.trashed: true` and `metadata.trashedSetAt`, stamped like archive so a copy read before the change cannot write the old flag back (`withStoredTrashed`). While it is set, `memory.sessions.search` and its hit read leave the chat out. `updatedAt` is not touched.

[Rename route](route-session-title.ts): `PATCH /api/sessions/{id}` with `{ title }` (trimmed, 1-120 characters, one line; `400` otherwise, `404` for an unknown id) stores the operator's title through `SessionStore.renameSession`. The title is stamped as user-set, so the session namer never replaces it and a turn already running cannot write an older copy back over it.

[Plain completion route](route-complete.ts): `POST /api/complete` with `{ prompt, system?, max_tokens? }` answers `{ text }` from one request to the current model through `runtime.completePlain` (`../runtime/plain-complete.ts`): no tools, no turn, nothing written to a session, its own `complete:` fallback partition, `max_tokens` clamped to 4096 (default 1024), a 60 s deadline. `400` bad body, `501` no plain call in this runtime, `502` model failure or empty answer, `504` deadline. The desktop Studio's "Improve prompt" uses it when present.

[Side question route](route-side-question.ts) (ATO-1152): `POST /api/btw` with `{ question, session_id? }` answers `{ text }` through `runtime.askSideQuestion`, the TUI's `/btw`: a digest of `session_id`'s conversation as read-only context (none for an unknown or absent id), no tools, its own `btw:` fallback partition, 2048 output tokens, a 90 s deadline. Nothing is written to the session, so the answer never reaches later turns; it may run while that chat's turn runs. `400` bad body, blank question or one over 4000 characters (`param` names the field), `501` no side question in this runtime, `502` model failure or empty answer, `504` deadline. A client that disconnects aborts the call. The desktop's `/btw` uses it.

`usage` on `/v1/chat/completions` (the body, the extensions-only `usage` frame) reports the tokens every LLM call of the turn reported, summed by the runtime's turn usage meter (`RunTurnResult.usage`; a local llama-server counts by its timings), and zeros when none did. A streaming request with `stream_options.include_usage: true` gets OpenAI's extra chunk before `data: [DONE]`: empty `choices` and the turn's `usage`; every chunk before it then carries `usage: null`, as OpenAI's do ([builders](openai-chunks.ts)).

[Approval route](route-approval.ts): `POST /api/approval/resolve` with `{ approvalId, decision }` takes `allow-once`, `deny` (aliases `approve`, `reject`) and `allow-in-chat`. `allow-in-chat` approves and records the gate's shape grant for the request's own session: later shell calls of the same binary (`commandShape`, `git`) in that chat run unasked (only calls that run that binary alone: a compound line such as `git status && …`, a pathed `./git`, a shell or a wrapper such as `env` has no shape and still asks), other binaries and other chats still ask, and nothing persists. A request without a shape gets `400` and stays pending. `allow-always` (ATO-1142) approves and saves an allow rule in the approval rules file, built by the gate from the pending request and scoped to its project; the response adds `grant: "always"` and the saved `rule`, and a request where `canGrantAlways` is false gets `400` and stays pending. Each `approval_request` on `GET /api/events` carries `canAlways` and, when true, `alwaysLabel` (`Always allow "git status" in this project`), so a client draws the button only where it works. `GET /api/capabilities` lists the accepted decisions as `agent.approvalDecisions`; a client offers "allow in this chat" only when it is listed.

[Question route](route-question.ts) (ATO-489): a question the agent asks with `ask_user` arrives on `GET /api/events` as an `approval_request` with `category: "user_question"` and a `question` object (`prompt`, `options` of `{ label, description? }`, `multiSelect`, `allowOther`), replayed on reconnect like any pending approval. Answer it with `POST /api/question/answer` `{ approvalId, selected?: labels or 0-based indexes, other?: string }`, or `{ approvalId, skip: true }`. An answer the question does not take is `400` and the question stays open; `/api/approval/resolve` refuses to approve one. `agent.questions: true` on `GET /api/capabilities` says the route exists. A chat client is offered `ask_user` only when its `POST /v1/chat/completions` sends `X-Atomic-Questions: 1` together with `X-Atomic-Extensions: 1`; without it (today's desktop app, which has no question card until ATO-1502) the tool is left out of its turns. The TUI, the CLI and Telegram always get it.

[MCP elicitation route](route-mcp-elicitation.ts) (ATO-1492): an MCP server's question to the person (a plain "confirm?" or a small form) is never an `approval_request`, because the approval ladder can answer those by itself. A client that draws the form opens `GET /api/events?elicitation=1`; only then does `serve` count someone as there. It gets every open question on connect and then `mcp_elicitation` frames (`{ id, askedAt, question: { server, message, fields } }`, a field marked `sensitive` must be masked) and `mcp_elicitation_closed` (`{ id, action, reason }`, never the answer). Answer with `POST /api/mcp/elicitation/answer` `{ id, action: "accept" | "decline" | "cancel", content? }`; an answer that does not fit the form is `400` naming the field and the question stays open, `404` once it is closed. `GET /api/mcp/elicitation` lists the open ones, `agent.mcpElicitation` on `GET /api/capabilities` says the routes are wired. With no client opted in every question is declined at once.

[Local model recheck](route-local-model-recheck.ts) (ATO-873): `POST /api/local-model/recheck`, no body, reads `localModels.url` fresh from the config file, probes it the way saving it does and answers `{ url, verdict, ok, message, portHint }` (`ok`, `loading`, `ollama`, `atomic_chat`, `openai_compat`, `key_rejected`, `not_model_server`, `unreachable`). It never takes a URL from the client and writes nothing. A failed step's and turn's `error` frame carries `code` and plain `advice` for a local server ([fields](failure-reason-frame.ts)): `local_server_not_found` (404/405 at `localModels.url`, the case for a Reconnect button), `local_provider_not_found` (the same at another address), `local_context_exceeded`, `local_tools_unsupported` (a 400 saying the server takes no tool calls: llama-server without `--jinja`, an Ollama model without tool support), `local_request_invalid`, `atomic_chat_key_required` (the `atomic-chat` provider answered 401/403: its API key protection is on, ATO-1274; not reported to Sentry), `local_port_taken` (the managed engine's address answered 401 while our engine's process is not there: another program holds the port, ATO-1277); `local_engine_down` wins over them, and so does `atomic_chat_not_running` (ATO-1278: the Atomic Chat app refused the connection past a short start grace; the user opens it).

MCP browser sign-in ([route-mcp.ts](route-mcp.ts), flow in [mcp-oauth-flow.ts](../mcp/mcp-oauth-flow.ts)): `POST /api/mcp/servers/{name}/auth/start` answers `{ state: "pending", authUrl }` (the client opens `authUrl`; the agent never opens a browser) or `{ state: "signed_in" }` when a saved refresh token was enough. `GET /api/mcp/servers/{name}/auth` answers `{ state: "signed_out" | "pending" | "signed_in", error? }`; `POST .../auth/signout` deletes the saved sign-in, reconnects the server and answers `{ state: "signed_out" }`. Errors are plain sentences: 404 `mcp_auth_not_found`, 409 `mcp_auth_not_remote` (stdio) or `mcp_auth_uses_key` (a key in `headers`), 502 `mcp_auth_failed`. Bearer auth like every `/api` route; the loopback callback listener is separate and answers only `/callback` on 127.0.0.1.

[Telegram pairing routes](route-telegram-pairing.ts) (ATO-859): `POST /api/telegram/pairing` opens a 5-minute window through `TelegramChannel.startPairing` and answers `{ status: "waiting", code, expiresAt, timeoutMs, botUsername, link, instruction }` (`link` is `https://t.me/<bot>?start=<code>`, ATO-516, or `null` while the bot's @username is unknown) with `cache-control: no-store`. That reply is the only place the one-time code leaves the process; it is never logged and never in the `GET`. While an owner is paired the POST answers `409 owner_already_paired` until it is repeated with `{ "replaceOwner": true }`; a channel that is not `up` answers `409 telegram_not_running`. `GET` reports `idle`, `waiting`, `claimed` (with `owner: { userId, username }` and `pairedLine`), `expired`, `cancelled` or `failed`; `DELETE` cancels the window. Bearer auth like every `/api` route.

[Approval rules routes](route-approval-rules.ts) (ATO-1141): `GET /api/approval-rules?workingDir=|sessionId=` returns `{ rules, globalPath, projectPath, projectRules }`: the global file's rules and the folder's project-file ask / deny rules (read-only). `DELETE /api/approval-rules/{id}` removes a global rule (`{ removed: true }`, `404` when there is none). `POST /api/approval-rules` (ATO-1011) adds a rule by hand, like Claude Code's `/permissions`: `{ decision, tool?, category?, commandPrefix?, path?, project?, origin?, note? }`, where `{ decision: "allow", commandPrefix: ["git", "status"] }` is short for an `os.shell.run` / `shell` rule. It is checked by the same parser as the file, saved to the global file through the same store "Allow always" uses, and the gate applies it from the next request. An allow "Allow always" could not save is `400` with the reason: a category that is never granted (`trust_config`, `state_secret`, `shell_dangerous`, ...), a write in the home folder, a per-site browser category, a shell allow without `commandPrefix`, a prefix the shell guard calls dangerous or a wrapper that runs other commands (`sudo`, `env`, `bash`), an HTTP allow without `origin`, a read outside the project without `path`, a non-shell allow without `tool`, an allow with no category, or an allow without `project` (an allow always applies in one folder, as "Allow always" saves it; ask and deny may be global). An unknown field is `400` too. Answers `201 { rule, created: true }`, or `200 { rule, created: false }` when the same rule is already saved. Contract: [approval README](../approval/README.md).

[Project trust routes](route-project-trust.ts) (ATO-298): `GET /api/project-trust` reports the pending trust question for a folder's project skills and instruction files, and `POST /api/project-trust` with `{ answer, questionId }` records it (`{ answer, scope: "all" }` changes the answer for everything the folder ships, the desktop's settings switch); a stale `questionId` gets `409 question_changed` with the fresh status. [Skill routes](route-skills.ts): `POST /api/skills/install` with `{ sourcePath, source?, force?, confirm?, acknowledgeRisk? }` security-scans the folder before copying ([install scan](../skills/docs/skill-format.md#install-security-scan)). A `caution` verdict answers `428` with `error.code: "needs_confirmation"` (`error.param: "confirm"`), `installed: false`, `scan: { verdict, findings[] }`, where each finding is `{ severity, rule, file, line, excerpt }`, and `scanId`; the client shows the findings and repeats the request with `confirm: "<scanId>"`. [Active model route](route-llm-active.ts) (ATO-1021): `POST /api/llm/active` with `{ providerId, model? }` switches the running agent's text provider (and chat model) live, through the same legs and rollback as `/model` in the chat channels ([model-switch.ts](../channels/model-switch.ts)): the config cache is dropped first, the model is pinned, the provider rebuilt and made active, the choice persisted. It answers `{ ok, providerId, model, ms }`; `409 turn_in_progress` while any session has a turn running, `404` for an unknown provider, `400` for a missing key, a provider with no chat model, or a model pin on `llama-server`. The desktop calls it for a cloud model pick instead of restarting `atag serve`.
[Config routes](route-config.ts): `GET /api/config` answers `{ path, config, sha256 }`, the hash of the bytes `config` was parsed from (one read). `PUT /api/config` with `{ config, expectSha256? }` is `atomic-agent config set - [--expect-sha256]` in-process (ATO-1022): validated before the write, a version newer than both this build and the file is refused (`400`), and with `expectSha256` a file that moved since the read answers `409 config_changed` and nothing is written. Like the CLI write it leaves the running agent's config cache alone. The desktop uses both while `atag serve` is up, instead of an `atag config` process per read and write.

[Secrets routes](route-secrets.ts) (ATO-1639): `GET /api/secrets` answers `{ store, keychainKeys }` (names only) and `PUT /api/secrets/{name}` with `{ value: string | null }` saves or removes one `*_KEY`/`*_TOKEN`/`*_SECRET`/`*_PASSWORD` through the agent's dotenv writer, so it lands in `.env` or the opt-in OS keychain (ATO-474) like a key the terminal saves, and sets it in the running agent's environment. No route reads a value back; any other name is `400`; a caller that is not on this machine gets `403 loopback_only` (a loopback request with `cf-connecting-ip`, the `atag pair --remote` tunnel, counts as not on this machine: [isLocalRequest](auth-throttle.ts), also used for the `/health` process fields). The desktop uses it while `atag serve` is up and `atomic-agent config secrets set|get|unset` otherwise.
[Memory embeddings route](route-memory-embeddings.ts) (ATO-1024): `POST /api/memory/embeddings/reconnect` reattaches memory to the embedding model the config file names now (`runtime.reconnectMemoryEmbeddings`, the same call the TUI makes after a model pick), after dropping the config cache. [My files routes](route-files.ts) (ATO-1621): `GET /api/files/folders` → `{ folders: [{ path, name, fileCount, indexedCount, addedAt }] }`; `POST /api/files/folders` `{ path }` → `{ folder }`, or `400 { error: { code, message } }` with `code` one of `not_absolute`, `not_found`, `not_a_directory`, `already_added`, `inside_added`, `too_broad`; `DELETE /api/files/folders` `{ path }` → `{ removed }` (its chunks go too); `GET /api/files/status` → `{ running, found, indexed, failed, skipped, current?, lastError?, updatedAt }`. `501` on a runtime without an index; `/api/capabilities` says `fileIndex: true` when there is one. [Memory edit routes](route-memory.ts) (ATO-1124): the person's own list, edit and delete of what the agent remembers, so the desktop writes through the process that owns `memory.sqlite` and the FTS index and vectors stay in step. `GET /api/memory/notes?limit=1..200&includeArchived=1` → `{ notes }`; `PATCH /api/memory/notes/{id}` `{ text?, disabled? }` → `{ note }` (text replaced, old vectors dropped, a new one written in the background); `DELETE /api/memory/notes/{id}` → `{ removed: true, id }`. `GET /api/memory/profile` → `{ facts }`; `PATCH /api/memory/profile/{key}` `{ value?, disabled? }` → `{ fact }` (a new version, pinned, keywords and the on/off state kept); `DELETE /api/memory/profile/{key}` → `{ removed: true, key }`; `GET /api/memory/profile/{key}/history` → `{ key, versions }`, oldest first. `400` for a bad id or body, `404` for an unknown id or key. No key, loopback only (ATO-1495, [loopback-guard.ts](loopback-guard.ts)): on a server built with `unauthenticated: true` every request is checked before routing. `Host` must name this machine (`localhost`, `127.0.0.0/8`, `[::1]`, `*.localhost`, `os.hostname()`, any port), otherwise `403 host_not_allowed` (DNS rebinding). Taking a turn back (ATO-1298, [route-rollback-last-turn.ts](route-rollback-last-turn.ts)): `POST /api/sessions/{id}/rollback-last-turn` removes the chat's last question and its answer and returns `200 { id, text }`, the question's text. The body may carry `{ expectText, expectPriorQuestions, expectUnanswered }`, the question the client means by its text, by how many questions come before it (steers not counted, questions a cleared transcript hides counted) and, with `expectUnanswered: true`, by the client having seen no answer to it; if the stored last question differs in any (a failed turn the agent never recorded), it answers `409 turn_mismatch` and removes nothing. `expectUnanswered` (ATO-1420) keeps a wrong count from removing a real answer: a failed question on screen never matches a stored one that has a reply. It only removes: the client sends `text` again through `POST /v1/chat/completions`, so a retry runs the same path as a first try and the old answer is no longer in the chat the model reads. It does not reach outside the transcript: what the turn's reflection already wrote to long-term memory stays, and a chat cut back to nothing keeps its title and leaves `GET /api/sessions` (no question in it) until the question is sent again. Only a turn that changed nothing outside the transcript qualifies: a question answered by one reply, or by nothing (a provider error). A stopped turn does not: a stop can cut a tool batch short, and a local turn stores no trace of that step. Nor does a failed turn whose tools had already run (ATO-1476): the step that ran them may never have been stored, so its failure record names them and is marked `toolsRan`, and the rollback answers `turn_has_tools`. Otherwise `409` with `code` `turn_has_tools`, `turn_steered`, `turn_compacted`, `turn_stopped`, `turn_in_progress`, `nothing_to_undo`, `turn_unrecognized` or `turn_mismatch`, and the chat is left as it was. `404 session_not_found` is an unknown chat; an agent without the route answers 404 without that code. The cut itself is [truncateSessionAt](../session/session-truncate.ts).

Rolling a chat back to any question with its files, and forking it (ATO-1056, ATO-1058, [route-session-rewind.ts](route-session-rewind.ts)): `GET /api/sessions/{id}/rewind-points` lists the questions it can go back to (`turnIndex`, `priorQuestions`, `text`, `at`, newest first). `POST /api/sessions/{id}/rewind/preview` and `POST /api/sessions/{id}/rewind` take `{ priorQuestions, expectText }`, the question by its position (questions before it, steers not counted) and its text; a different stored question answers `409 point_mismatch` and nothing changes. The preview answers `{ turnIndex, text, removed: { questions, replies }, files: [{ path, action: "restore" | "delete" }], notRestorable: [{ path, reason }], incomplete, uncovered: [{ tool, count }], filesOnly: true }`: the files that will really change (a saved copy that matches the disk is left out), the ones changed without a copy (`too_large`, `binary`, `not_a_file`, `unreadable`), whether older copies were dropped to stay in bounds, and the shell, git, archive and Fusion calls whose changes stay. [AG-UI route](route-ag-ui.ts) (ATO-694): `POST /api/ag-ui` takes an [AG-UI](https://docs.ag-ui.com) `RunAgentInput` (`{ threadId, runId, messages, state?, tools?, context? }`) and streams the turn as AG-UI events, one `data: <event JSON>` per SSE frame, for web frontends built on AG-UI (CopilotKit, `@ag-ui/client` `HttpAgent`). `threadId` is the session id (a new one starts a chat in the server's folder); the turn's input is the last `user` message, and `tools` / `context` / `state` are accepted but not used. The stream opens with `RUN_STARTED` and ends with `RUN_FINISHED` (`outcome` `success` or `cancelled`, `usage` in tokens) or `RUN_ERROR` (`message`, `code` = the failure category). In between: `STEP_STARTED` / `STEP_FINISHED` per loop step, the reply as `TEXT_MESSAGE_START` / `_CONTENT` / `_END`, reasoning as `REASONING_*`, each tool call as `TOOL_CALL_START` / `_ARGS` (the whole JSON args) / `_END` and its outcome as `TOOL_CALL_RESULT` (`metadata.status`: `ok`, `error`, `denied`, `cancelled`), the plan as `STATE_SNAPSHOT` (`{ plan: { items, updatedAt } }`), and provider waits, switches, long-call progress, fusion workers, steers and retried step errors as `CUSTOM` events named `atomic.<event>` ([mapping](ag-ui-events.ts)). [A2A routes](route-a2a.ts) (ATO-693): off unless `serve --a2a` (or `ATOMIC_AGENT_SERVE_A2A=1`), and serve refuses `--a2a` without an API key. `GET /.well-known/agent-card.json` is the public [A2A v0.3](https://a2a-protocol.org/v0.3.0/specification/) AgentCard (endpoint `url`, `version` from `version.ts`, `capabilities.streaming: false`, `text/plain` in and out, one generic skill, `securitySchemes` for the serve key as a bearer token or `x-api-key`); `ATOMIC_AGENT_A2A_PUBLIC_URL` sets the address it names, else the request's Host. `POST /api/a2a` is the JSON-RPC 2.0 endpoint behind the usual key check: `message/send` files a task (`/api/tasks` machinery) in a session opened with `metadata.source: "a2a"`, whose id is the A2A `contextId`; `configuration.blocking: true` waits up to two minutes for it to settle. `tasks/get` answers the task with that task's own final reply (the reply its run produced, not the session's latest) as status message and artifact, `tasks/cancel` cancels it. The three methods only list and act on tasks in A2A sessions, and an unknown or non-A2A `contextId` starts a new session; that is the only narrowing. There is no separate A2A key: the peer uses the owner's serve key, which opens every other `/api` route as well, and its tasks run with the owner's tools (memory search included), so a peer has owner-level access. In session search A2A sessions are labelled and ranked as task sessions, like `http-task` ones, not as the person's chats. Only text parts are taken; streaming, push notifications, resubscribe, continuing a task by `taskId` and the extended card answer UnsupportedOperationError.

[Webhook route](route-webhooks.ts) (ATO-438): `POST /api/webhooks/{name}` turns a hit on a `webhooks.<name>` binding into a task. The binding's `verify` picks how `secret` is checked, always on top of the global API key: `secret` (the default, unchanged) compares the `x-webhook-secret` header; `github` checks `X-Hub-Signature-256: sha256=<hex HMAC-SHA256 of the raw body>`; `standard-webhooks` (the scheme Composio and Svix sign with) checks `webhook-signature: v1,<base64 HMAC-SHA256 of "<webhook-id>.<webhook-timestamp>.<body>">` with the base64 key of a `whsec_` secret, refuses a `webhook-timestamp` more than 5 minutes off, accepts the same headers under the `svix-id` / `svix-timestamp` / `svix-signature` names that Resend, Clerk and other Svix senders use (one set read whole, `webhook-*` first; ATO-1542), and starts one task per `webhook-id` (a bounded in-memory list per process; a repeat answers `200 { taskId: null, duplicate: true }`). Signatures are computed over the exact request bytes ([readRawBody](request-context.ts), [checks](webhook-signature.ts)), compared in constant time; a failure answers `401` and starts nothing. With a signed scheme the template can use `{{event}}` (`X-GitHub-Event` or the payload `type`), `{{action}}` (GitHub's payload `action`) and `{{delivery}}` (`X-GitHub-Delivery` or `webhook-id`), and `events: ["pull_request.opened", "issues"]` limits which events start a task ([matching](webhook-verify.ts)); an event left out, and GitHub's `ping`, answer `200 { taskId: null, ignored: true }`. Example:

```json
"webhooks": {
  "pr-review": {
    "verify": "github",
    "secret": "<the secret set on the GitHub hook>",
    "events": ["pull_request.opened"],
    "userMessageTemplate": "Review {{event}} {{action}}: {{body.pull_request.html_url}}"
  }
}
```

Not covered here: GitHub cannot send a bearer token, so a server started with `--api-key` still refuses its hits; reaching the agent from the internet needs a tunnel or public address; no Composio subscription and no Slack or calendar presets.

Webhooks from the internet (ATO-625): `verify: "stripe"` checks `Stripe-Signature: t=<unix>,v1=<hex HMAC-SHA256 of "<t>.<body>">` with the endpoint's `whsec_` secret used as text, refuses a `t` more than 5 minutes off, and fills `{{event}}` / `{{delivery}}` from the payload `type` / `id` ([checks](webhook-signature.ts)). `atag serve --tunnel` (or `--tunnel-name <n> --tunnel-hostname <h>` for a named Cloudflare tunnel) runs cloudflared from PATH (never downloaded, `--no-autoupdate`) against a second listener on a random loopback port whose [route table](tunnel-route-table.ts) holds only `POST /api/webhooks/{name}`, with no bearer key: every other path answers 404 there, a binding without a secret answers `403 webhook_secret_required`, and the main API is never the tunnel's origin (there is no option to expose it). On that listener every signed binding (`github`, `standard-webhooks`, `stripe`) gets replay protection: a delivery id already turned into a task (`X-GitHub-Delivery`, `webhook-id`, the Stripe event `id`; the same bounded in-memory list as above) answers `200 { taskId: null, duplicate: true }` and runs nothing, and the timestamped schemes refuse a signature more than 5 minutes old. serve refuses `--tunnel` when cloudflared is missing, tasks are off or no binding has a secret. `GET /api/webhooks` ([list route](route-webhooks-list.ts)) answers `{ tasksEnabled, tunnel: { state, mode, publicUrl, error }, webhooks: [{ name, path, hasSecret, sessionMode, publicUrl }] }`, never the secrets; `publicUrl` is set only while the tunnel is up and only for bindings with a secret. cloudflared is stopped with serve ([wiring](../cli/serve-webhook-tunnel.ts)).

Goal mode (ATO-1040, [route-session-goal.ts](route-session-goal.ts), [chat-goal.ts](chat-goal.ts)): the TUI's `/goal` for other clients. `GET /api/sessions/{id}/goal` answers `{ sessionId, goal, running }`, `goal` being the stored [GoalState](../agent/goal/goal-types.ts) (status, per-criterion marks and reasons, rounds used of `maxRounds`) or `null`; `GET /api/sessions` rows and `GET /api/sessions/{id}` carry the same `goal`. `POST /api/sessions/{id}/goal` takes `{ action: "set", criteria: string[], maxRounds?, workingDir? }` (a new chat is opened in `workingDir`, else the server's folder; the stored goal's shell checks are kept, none are added here), `{ action: "pause" }`, `{ action: "resume" }` or `{ action: "clear" }`, with the TUI's rules: `409` with `code` `turn_in_progress`, `no_goal`, `goal_not_running` or `goal_complete`. `set` and `resume` answer `message`, the text to send next through `POST /v1/chat/completions`; with `x-atomic-extensions: 1`, a chat whose stored goal is active runs that message as goal rounds, and the stream carries `event: goal_progress` `{ object: "atomic.goal_progress", session_id, goal }` after every change. `pause` and `clear` on a goal that is running answer `pending: true` and land after its current round (`runtime.controlGoal`).

[Metrics route](route-metrics.ts) (ATO-646): `GET /metrics` answers the Prometheus text format for a Prometheus or Grafana scrape of `atag serve`: turns (count and duration by origin and outcome), steps, provider failures by category and provider link, tool calls by tool, task and scheduler counters, plus turns running and durable tasks per status read at scrape time. Serve folds the runtime's metric samples in a [PrometheusRegistry](../tracing/prometheus-registry.ts); no label carries a session id. The route is never open without a key: the scrape config sends serve's key (`--api-key`, or `atag serve --print-api-key`) as a bearer token, and a server built with no key at all (`unauthenticated: true`, never `serve`) answers 401 (`metrics_need_api_key`).

Managing bindings (ATO-445): each `GET /api/webhooks` item also carries `verify` (`secret` when unset), `events` (when set), `userMessageTemplate` and `live` (false for a binding saved in `config.json` by hand since start, listed from the file), and the reply adds `presets` (the `verify` values). `POST /api/webhooks` `{ name, verify?, userMessageTemplate, secret?, events?, sessionMode? }` adds a binding ([admin routes](route-webhooks-admin.ts)): the secret is generated unless given (`whsec_<base64>` for `standard-webhooks`, hex otherwise; `stripe` needs the pasted `whsec_` value), the whole file is revalidated and written atomically, the running agent picks it up without a restart, and the reply `201 { webhook, secret }` is the only time the secret is returned. `DELETE /api/webhooks/{name}` removes a binding and its persistent session mapping. Both sit on the main API behind its bearer key; the tunnel listener never serves them.

Named tokens and scopes (ATO-583, first slice): `atag http tokens add <name> --role admin|member|viewer` stores a SHA-256 of a new token in `<stateDir>/http-tokens.json` (0600) and prints the token once; `list` and `remove` manage them, and serve rereads the file when it changes. Every authenticated route needs one scope from [ROUTE_SCOPES](http-scopes.ts) (`read`, `chat` or `admin`; a route missing from the table needs `admin`, and `http-scopes.test.ts` fails for a new route without an entry). `admin` has all three, `member` `read` + `chat`, `viewer` `read`. `POST /api/approval/resolve` is `chat`, so a `member` token can approve the tool calls of turns it starts: shell, file and config tools then run with the agent's own rights. The admin-only routes (`/api/config`, `/api/skills/install`) are therefore not a hard boundary for `member`, which is equivalent to host execution; only give it to people trusted with the machine. `viewer` is the read-only role. The serve key is always `admin`. With a key and at least one named token, any other value is `401`, and a known token without the route's scope is `403` with code `insufficient_scope`. Without named tokens, or without a serve key, auth is unchanged.


MCP over HTTP (ATO-549): [`/mcp`](route-mcp-endpoint.ts) is the MCP Streamable HTTP transport (spec 2025-03-26 and 2025-06-18) for the read-only tool set of `atag mcp-server`, built from the runtime's own stores and skill registry. `POST` carries JSON-RPC, `initialize` without `Mcp-Session-Id` opens a session (at most 32, an hour idle closes one), `GET` opens the server SSE stream and `DELETE` ends the session; a missing id answers 400 and an unknown one 404. It uses the SDK's `StreamableHTTPServerTransport` with the body this router already read, sits behind the bearer key and the loopback guard like every route, and refuses a foreign `Origin` with 403 even when a key is set ([originAllowed](loopback-guard.ts)); `ATOMIC_AGENT_ALLOWED_ORIGINS` adds origins it accepts, the one place serve still reads that variable.
