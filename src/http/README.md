## Ownership and dependencies

The HTTP server owns request handling and connection cancellation; route modules translate transport payloads into runtime operations. Session routes use the existing turn/steering contract, and webhook routes materialize durable tasks. Runtime owns session execution, task storage and approval policy; routes must retain authentication and error mapping. MCP routes use [shared server-config commands](../config/mcp-server-commands.ts) and manager operations, independently of TUI.

[Compaction routes](route-compaction.ts) expose `POST /api/sessions/{id}/compact` and `GET /api/sessions/{id}/compaction`. The POST waits for runtime completion and cancels only its operation on disconnect. See [the shared contract](../runtime/docs/compaction.md). With `x-atomic-extensions: 1`, a chat stream also carries `compaction_started`, `compaction_progress`, `compaction_completed`, `compaction_failed` and `history_trimmed` frames ([mapping](stream-maintenance-frames.ts)): counts and statuses only. It also carries `usage_updated` (ATO-569): the session's spend so far, priced / unpriced / local / plan call counts, and the account's rate-limit windows (used percent, remaining, reset time); the same snapshot is persisted as `sessionUsage` on `GET /api/sessions/{id}`. With `llm.costTracking.showInStatusBar` on or `llm.costTracking.dailyLimitUsd` set, the frame also carries `today: { day, cost_usd, priced_calls, unpriced_calls, limit_usd? }` (ATO-649): what every session spent today, live only and never persisted with a session. `today` is sent only when a configured cloud link has a known price. Once `cost_usd` reaches `limit_usd`, paid cloud links are refused before the request is sent: with `llm.costTracking.onDailyLimit: "stop"` (default) the turn fails with "Daily cloud limit reached: …" (failure cause `daily_limit_reached`); with `"local"` the fallback chain moves on to the local link and a `provider_switched` frame says so. A `tool_disabled` frame (ATO-1417) says a tool was left out of the turn's requests because the server refused its JSON schema: `tool`, `reason` (`schema_rejected`), `step_index` and the chat sentence in `notice`, once per tool per turn.

[Turn phases](stream-turn-phase.ts) (ATO-1027): with `x-atomic-extensions: 1`, a chat stream carries `event: turn_phase` on every change of what the turn is doing, `{ object: "atomic.turn_phase", session_id, phase, step_index?, tool?, phase_elapsed_ms, turn_elapsed_ms, progress? }`. `phase` is `starting`, `loading_model` (the local server answered "Loading model"), `waiting_provider`, `processing_prompt` (`progress: { processed, total, cached, fraction }` when llama-server reports prompt progress), `thinking`, `generating`, `running_tool` (`tool` names the call) or `compacting`. A host counts the seconds itself from `phase_elapsed_ms`. Once per turn, when a local model has produced nothing 45 s after the turn began, `event: slow_first_token` carries `{ object: "atomic.slow_first_token", session_id, waited_ms, phase?, model_id?, lighter_model?: { id, name, file_size_gb, downloaded }, cloud_available }` ([hint](slow-first-token-hint.ts)): what the host may offer instead. Nothing is switched. After every model completion, `event: step_speed` carries `{ object: "atomic.step_speed", session_id, step_index?, prompt_tokens, cached_tokens, prefill_ms, decode_ms, decode_tokens_per_second, draft_tokens?, draft_accepted_tokens? }` (ATO-631): whether a slow step was re-reading its prompt or writing slowly. `decode_tokens_per_second` is `null` and the ms fields `0` for a provider that reports no timings (cloud APIs); the draft fields appear only under speculative decoding.

Next-step suggestion (ATO-1093): `GET /api/sessions` rows and `GET /api/sessions/{id}` carry `nextStep`, the suggested next message after the last answered turn, or `null` (setting `tui.nextStepSuggestions` off, nothing stored, a turn running, or a later turn made it stale). `GET /api/sessions/{id}/next-step` answers `200 { sessionId, suggestion }` with the same value (`404` for an unknown id). With the switch off every route serves `null`, also for a suggestion stored while it was on, and `GET /api/sessions/{id}` leaves `metadata.nextStep` out. Read-only; see [session-next-step.ts](../session/session-next-step.ts).

Step labels in history (ATO-1382): `GET /api/sessions/{id}` adds `done_line` to every `assistant_tool_call` row, built from the stored name and args with the same `describeToolCall` the live `tool_progress.done_line` uses, so a reopened chat reads its steps exactly as they read while the turn ran. It is computed per answer and never stored.

Searching past chats (ATO-1149, [session-search.ts](../session/session-search.ts)): `GET /api/sessions/search?q=…` finds words in the user messages and closing replies of stored sessions with SQLite FTS5 (tool calls and tool output are not indexed). It covers the current working directory, or every folder with `scope=all`; `limit` defaults to 10, max 25, at most 3 hits per session. The answer is `200 { query, hits, pending }`: each hit carries `sessionId`, `title`, `workingDir`, `updatedAt`, `line` (index into the session's chat lines), `kind`, `source` (`chat`, `telegram`, `discord`, `webhook`, `task`, `imported`, for a label) and a `snippet` with the matched words in `«` `»`. Task sessions rank below an interactive chat that matches as well; incognito chats, Fusion workers and sessions stamped `metadata.internal` / `metadata.subagent` are never indexed. The index is filled at search time, not on every write: each search reindexes up to 500 sessions changed since they were last indexed, newest first (transcripts read without the write lock, the index written 25 sessions per transaction), and `pending` counts the rest. `400` for an empty or over-500-character `q`, `503` when the index cannot be created.

[Rename route](route-session-title.ts): `PATCH /api/sessions/{id}` with `{ title }` (trimmed, 1-120 characters, one line; `400` otherwise, `404` for an unknown id) stores the operator's title through `SessionStore.renameSession`. The title is stamped as user-set, so the session namer never replaces it and a turn already running cannot write an older copy back over it.

[Plain completion route](route-complete.ts): `POST /api/complete` with `{ prompt, system?, max_tokens? }` answers `{ text }` from one request to the current model through `runtime.completePlain` (`../runtime/plain-complete.ts`): no tools, no turn, nothing written to a session, its own `complete:` fallback partition, `max_tokens` clamped to 4096 (default 1024), a 60 s deadline. `400` bad body, `501` no plain call in this runtime, `502` model failure or empty answer, `504` deadline. The desktop Studio's "Improve prompt" uses it when present.

`usage` on `/v1/chat/completions` (the body, the extensions-only `usage` frame) reports the tokens every LLM call of the turn reported, summed by the runtime's turn usage meter (`RunTurnResult.usage`; a local llama-server counts by its timings), and zeros when none did. A streaming request with `stream_options.include_usage: true` gets OpenAI's extra chunk before `data: [DONE]`: empty `choices` and the turn's `usage`; every chunk before it then carries `usage: null`, as OpenAI's do ([builders](openai-chunks.ts)).

[Approval route](route-approval.ts): `POST /api/approval/resolve` with `{ approvalId, decision }` takes `allow-once`, `deny` (aliases `approve`, `reject`) and `allow-in-chat`. `allow-in-chat` approves and records the gate's shape grant for the request's own session: later shell calls of the same binary (`commandShape`, `git`) in that chat run unasked (only calls that run that binary alone: a compound line such as `git status && …`, a pathed `./git`, a shell or a wrapper such as `env` has no shape and still asks), other binaries and other chats still ask, and nothing persists. A request without a shape gets `400` and stays pending. `allow-always` (ATO-1142) approves and saves an allow rule in the approval rules file, built by the gate from the pending request and scoped to its project; the response adds `grant: "always"` and the saved `rule`, and a request where `canGrantAlways` is false gets `400` and stays pending. Each `approval_request` on `GET /api/events` carries `canAlways` and, when true, `alwaysLabel` (`Always allow "git status" in this project`), so a client draws the button only where it works. `GET /api/capabilities` lists the accepted decisions as `agent.approvalDecisions`; a client offers "allow in this chat" only when it is listed.

Per-chat folders (ATO-731, [session-working-dir.ts](session-working-dir.ts)): every tool step reads its session's `workingDir`, so `POST /v1/chat/completions` takes `working_dir` (absolute, existing) for a NEW session, `POST /api/sessions/{id}/working-dir` `{ workingDir }` moves one chat (`409 turn_in_progress` only while that chat runs a turn), and `GET /api/sessions?scope=all` lists chats from every folder. Taking a turn back (ATO-1298, [route-rollback-last-turn.ts](route-rollback-last-turn.ts)): `POST /api/sessions/{id}/rollback-last-turn` removes the chat's last question and its answer and returns `200 { id, text }`, the question's text. The body may carry `{ expectText, expectPriorQuestions, expectUnanswered }`, the question the client means by its text, by how many questions come before it (steers not counted, questions a cleared transcript hides counted) and, with `expectUnanswered: true`, by the client having seen no answer to it; if the stored last question differs in any (a failed turn the agent never recorded), it answers `409 turn_mismatch` and removes nothing. `expectUnanswered` (ATO-1420) keeps a wrong count from removing a real answer: a failed question on screen never matches a stored one that has a reply. It only removes: the client sends `text` again through `POST /v1/chat/completions`, so a retry runs the same path as a first try and the old answer is no longer in the chat the model reads. It does not reach outside the transcript: what the turn's reflection already wrote to long-term memory stays, and a chat cut back to nothing keeps its title and leaves `GET /api/sessions` (no question in it) until the question is sent again. Only a turn that changed nothing outside the transcript qualifies: a question answered by one reply, or by nothing (a provider error). A stopped turn does not: a stop can cut a tool batch short, and a local turn stores no trace of that step. Nor does a failed turn whose tools had already run (ATO-1476): the step that ran them may never have been stored, so its failure record names them and is marked `toolsRan`, and the rollback answers `turn_has_tools`. Otherwise `409` with `code` `turn_has_tools`, `turn_steered`, `turn_compacted`, `turn_stopped`, `turn_in_progress`, `nothing_to_undo`, `turn_unrecognized` or `turn_mismatch`, and the chat is left as it was. `404 session_not_found` is an unknown chat; an agent without the route answers 404 without that code. The cut itself is [truncateSessionAt](../session/session-truncate.ts).

[AG-UI route](route-ag-ui.ts) (ATO-694): `POST /api/ag-ui` takes an [AG-UI](https://docs.ag-ui.com) `RunAgentInput` (`{ threadId, runId, messages, state?, tools?, context? }`) and streams the turn as AG-UI events, one `data: <event JSON>` per SSE frame, for web frontends built on AG-UI (CopilotKit, `@ag-ui/client` `HttpAgent`). `threadId` is the session id (a new one starts a chat in the server's folder); the turn's input is the last `user` message, and `tools` / `context` / `state` are accepted but not used. The stream opens with `RUN_STARTED` and ends with `RUN_FINISHED` (`outcome` `success` or `cancelled`, `usage` in tokens) or `RUN_ERROR` (`message`, `code` = the failure category). In between: `STEP_STARTED` / `STEP_FINISHED` per loop step, the reply as `TEXT_MESSAGE_START` / `_CONTENT` / `_END`, reasoning as `REASONING_*`, each tool call as `TOOL_CALL_START` / `_ARGS` (the whole JSON args) / `_END` and its outcome as `TOOL_CALL_RESULT` (`metadata.status`: `ok`, `error`, `denied`, `cancelled`), the plan as `STATE_SNAPSHOT` (`{ plan: { items, updatedAt } }`), and provider waits, switches, long-call progress, fusion workers, steers and retried step errors as `CUSTOM` events named `atomic.<event>` ([mapping](ag-ui-events.ts)). Closing the connection stops the turn. Approvals stay on `GET /api/events` and `POST /api/approval/resolve`. Bearer auth like every `/api` route; `/v1/chat/completions` is unchanged.

[Webhook route](route-webhooks.ts) (ATO-438): `POST /api/webhooks/{name}` turns a hit on a `webhooks.<name>` binding into a task. The binding's `verify` picks how `secret` is checked, always on top of the global API key: `secret` (the default, unchanged) compares the `x-webhook-secret` header; `github` checks `X-Hub-Signature-256: sha256=<hex HMAC-SHA256 of the raw body>`; `standard-webhooks` (the scheme Composio and Svix sign with) checks `webhook-signature: v1,<base64 HMAC-SHA256 of "<webhook-id>.<webhook-timestamp>.<body>">` with the base64 key of a `whsec_` secret, refuses a `webhook-timestamp` more than 5 minutes off, and starts one task per `webhook-id` (a bounded in-memory list per process; a repeat answers `200 { taskId: null, duplicate: true }`). Signatures are computed over the exact request bytes ([readRawBody](request-context.ts), [checks](webhook-signature.ts)), compared in constant time; a failure answers `401` and starts nothing. With a signed scheme the template can use `{{event}}` (`X-GitHub-Event` or the payload `type`), `{{action}}` (GitHub's payload `action`) and `{{delivery}}` (`X-GitHub-Delivery` or `webhook-id`), and `events: ["pull_request.opened", "issues"]` limits which events start a task ([matching](webhook-verify.ts)); an event left out, and GitHub's `ping`, answer `200 { taskId: null, ignored: true }`. Example:

```json
"webhooks": {
  "pr-review": {
    "verify": "github",
    "secret": "<the secret set on the GitHub hook>",
    "events": ["pull_request.opened"],
    "userMessageTemplate": "Review {{event}} {{action}}: {{body.pull_request.html_url}}"
  }
}
```

Not covered here: GitHub cannot send a bearer token, so a server started with `--api-key` still refuses its hits; reaching the agent from the internet needs a tunnel or public address; no Composio subscription and no Slack or calendar presets.

Webhooks from the internet (ATO-625): `verify: "stripe"` checks `Stripe-Signature: t=<unix>,v1=<hex HMAC-SHA256 of "<t>.<body>">` with the endpoint's `whsec_` secret used as text, refuses a `t` more than 5 minutes off, and fills `{{event}}` / `{{delivery}}` from the payload `type` / `id` ([checks](webhook-signature.ts)). `atag serve --tunnel` (or `--tunnel-name <n> --tunnel-hostname <h>` for a named Cloudflare tunnel) runs cloudflared from PATH (never downloaded, `--no-autoupdate`) against a second listener on a random loopback port whose [route table](tunnel-route-table.ts) holds only `POST /api/webhooks/{name}`, with no bearer key: every other path answers 404 there, a binding without a secret answers `403 webhook_secret_required`, and the main API is never the tunnel's origin (there is no option to expose it). On that listener every signed binding (`github`, `standard-webhooks`, `stripe`) gets replay protection: a delivery id already turned into a task (`X-GitHub-Delivery`, `webhook-id`, the Stripe event `id`; the same bounded in-memory list as above) answers `200 { taskId: null, duplicate: true }` and runs nothing, and the timestamped schemes refuse a signature more than 5 minutes old. serve refuses `--tunnel` when cloudflared is missing, tasks are off or no binding has a secret. `GET /api/webhooks` ([list route](route-webhooks-list.ts)) answers `{ tasksEnabled, tunnel: { state, mode, publicUrl, error }, webhooks: [{ name, path, hasSecret, sessionMode, publicUrl }] }`, never the secrets; `publicUrl` is set only while the tunnel is up and only for bindings with a secret. cloudflared is stopped with serve ([wiring](../cli/serve-webhook-tunnel.ts)).

Goal mode (ATO-1040, [route-session-goal.ts](route-session-goal.ts), [chat-goal.ts](chat-goal.ts)): the TUI's `/goal` for other clients. `GET /api/sessions/{id}/goal` answers `{ sessionId, goal, running }`, `goal` being the stored [GoalState](../agent/goal/goal-types.ts) (status, per-criterion marks and reasons, rounds used of `maxRounds`) or `null`; `GET /api/sessions` rows and `GET /api/sessions/{id}` carry the same `goal`. `POST /api/sessions/{id}/goal` takes `{ action: "set", criteria: string[], maxRounds?, workingDir? }` (a new chat is opened in `workingDir`, else the server's folder; the stored goal's shell checks are kept, none are added here), `{ action: "pause" }`, `{ action: "resume" }` or `{ action: "clear" }`, with the TUI's rules: `409` with `code` `turn_in_progress`, `no_goal`, `goal_not_running` or `goal_complete`. `set` and `resume` answer `message`, the text to send next through `POST /v1/chat/completions`; with `x-atomic-extensions: 1`, a chat whose stored goal is active runs that message as goal rounds, and the stream carries `event: goal_progress` `{ object: "atomic.goal_progress", session_id, goal }` after every change. `pause` and `clear` on a goal that is running answer `pending: true` and land after its current round (`runtime.controlGoal`).

[Metrics route](route-metrics.ts) (ATO-646): `GET /metrics` answers the Prometheus text format for a Prometheus or Grafana scrape of `atag serve`: turns (count and duration by origin and outcome), steps, provider failures by category and provider link, tool calls by tool, task and scheduler counters, plus turns running and durable tasks per status read at scrape time. Serve folds the runtime's metric samples in a [PrometheusRegistry](../tracing/prometheus-registry.ts); no label carries a session id. The route works only with `--api-key` and is never open without one: the scrape config sends the key as a bearer token, and a serve started without a key answers 401 (`metrics_need_api_key`), even on loopback.
