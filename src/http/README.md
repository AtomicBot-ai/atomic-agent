## Ownership and dependencies

The HTTP server owns request handling and connection cancellation; route modules translate transport payloads into runtime operations. Session routes use the existing turn/steering contract, and webhook routes materialize durable tasks. Runtime owns session execution, task storage and approval policy; routes must retain authentication and error mapping. MCP routes use [shared server-config commands](../config/mcp-server-commands.ts) and manager operations, independently of TUI.

## Validation

`npx vitest run src/http`; `npm run lint`; `npm run docs:check`. The production typecheck excludes tests; see [development checks](../../docs/development.md).

[Compaction routes](route-compaction.ts) expose `POST /api/sessions/{id}/compact` and `GET /api/sessions/{id}/compaction`. The POST waits for runtime completion and cancels only its operation on disconnect. See [the shared contract](../runtime/docs/compaction.md). With `x-atomic-extensions: 1`, a chat stream also carries `compaction_started`, `compaction_progress`, `compaction_completed`, `compaction_failed` and `history_trimmed` frames ([mapping](stream-maintenance-frames.ts)): counts and statuses only. It also carries `usage_updated` (ATO-569): the session's spend so far, priced / unpriced / local / plan call counts, and the account's rate-limit windows (used percent, remaining, reset time); the same snapshot is persisted as `sessionUsage` on `GET /api/sessions/{id}`. A `tool_disabled` frame (ATO-1417) says a tool was left out of the turn's requests because the server refused its JSON schema: `tool`, `reason` (`schema_rejected`), `step_index` and the chat sentence in `notice`, once per tool per turn.

[Turn phases](stream-turn-phase.ts) (ATO-1027): with `x-atomic-extensions: 1`, a chat stream carries `event: turn_phase` on every change of what the turn is doing, `{ object: "atomic.turn_phase", session_id, phase, step_index?, tool?, phase_elapsed_ms, turn_elapsed_ms, progress? }`. `phase` is `starting`, `loading_model` (the local server answered "Loading model"), `waiting_provider`, `processing_prompt` (`progress: { processed, total, cached, fraction }` when llama-server reports prompt progress), `thinking`, `generating`, `running_tool` (`tool` names the call) or `compacting`. A host counts the seconds itself from `phase_elapsed_ms`. Once per turn, when a local model has produced nothing 45 s after the turn began, `event: slow_first_token` carries `{ object: "atomic.slow_first_token", session_id, waited_ms, phase?, model_id?, lighter_model?: { id, name, file_size_gb, downloaded }, cloud_available }` ([hint](slow-first-token-hint.ts)): what the host may offer instead. Nothing is switched.

Step labels in history (ATO-1382): `GET /api/sessions/{id}` adds `done_line` to every `assistant_tool_call` row, built from the stored name and args with the same `describeToolCall` the live `tool_progress.done_line` uses, so a reopened chat reads its steps exactly as they read while the turn ran. It is computed per answer and never stored.

[Rename route](route-session-title.ts): `PATCH /api/sessions/{id}` with `{ title }` (trimmed, 1-120 characters, one line; `400` otherwise, `404` for an unknown id) stores the operator's title through `SessionStore.renameSession`. The title is stamped as user-set, so the session namer never replaces it and a turn already running cannot write an older copy back over it.

`usage` on `/v1/chat/completions` (the body, the extensions-only `usage` frame) reports the tokens every LLM call of the turn reported, summed by the runtime's turn usage meter (`RunTurnResult.usage`; a local llama-server counts by its timings), and zeros when none did. A streaming request with `stream_options.include_usage: true` gets OpenAI's extra chunk before `data: [DONE]`: empty `choices` and the turn's `usage`; every chunk before it then carries `usage: null`, as OpenAI's do ([builders](openai-chunks.ts)).

[Approval route](route-approval.ts): `POST /api/approval/resolve` with `{ approvalId, decision }` takes `allow-once`, `deny` (aliases `approve`, `reject`) and `allow-in-chat`. `allow-in-chat` approves and records the gate's shape grant for the request's own session: later shell calls of the same binary (`commandShape`, `git`) in that chat run unasked (only calls that run that binary alone: a compound line such as `git status && …`, a pathed `./git`, a shell or a wrapper such as `env` has no shape and still asks), other binaries and other chats still ask, and nothing persists. A request without a shape gets `400` and stays pending. `allow-always` (ATO-1142) approves and saves an allow rule in the approval rules file, built by the gate from the pending request and scoped to its project; the response adds `grant: "always"` and the saved `rule`, and a request where `canGrantAlways` is false gets `400` and stays pending. Each `approval_request` on `GET /api/events` carries `canAlways` and, when true, `alwaysLabel` (`Always allow "git status" in this project`), so a client draws the button only where it works. `GET /api/capabilities` lists the accepted decisions as `agent.approvalDecisions`; a client offers "allow in this chat" only when it is listed.

[Local model recheck](route-local-model-recheck.ts) (ATO-873): `POST /api/local-model/recheck`, no body, reads `localModels.url` fresh from the config file, probes it the way saving it does and answers `{ url, verdict, ok, message, portHint }` (`ok`, `loading`, `ollama`, `atomic_chat`, `openai_compat`, `key_rejected`, `not_model_server`, `unreachable`). It never takes a URL from the client and writes nothing. A failed step's and turn's `error` frame carries `code` and plain `advice` for a local server ([fields](failure-reason-frame.ts)): `local_server_not_found` (404/405 at `localModels.url`, the case for a Reconnect button), `local_provider_not_found` (the same at another address), `local_context_exceeded`, `local_tools_unsupported` (a 400 saying the server takes no tool calls: llama-server without `--jinja`, an Ollama model without tool support), `local_request_invalid`, `atomic_chat_key_required` (the `atomic-chat` provider answered 401/403: its API key protection is on, ATO-1274; not reported to Sentry), `local_port_taken` (the managed engine's address answered 401 while our engine's process is not there: another program holds the port, ATO-1277); `local_engine_down` wins over them, and so does `atomic_chat_not_running` (ATO-1278: the Atomic Chat app refused the connection past a short start grace; the user opens it).

[Telegram pairing routes](route-telegram-pairing.ts) (ATO-859): `POST /api/telegram/pairing` opens a 5-minute window through `TelegramChannel.startPairing` and answers `{ status: "waiting", code, expiresAt, timeoutMs, botUsername, instruction }` with `cache-control: no-store`. That reply is the only place the one-time code leaves the process; it is never logged and never in the `GET`. While an owner is paired the POST answers `409 owner_already_paired` until it is repeated with `{ "replaceOwner": true }`; a channel that is not `up` answers `409 telegram_not_running`. `GET` reports `idle`, `waiting`, `claimed` (with `owner: { userId, username }` and `pairedLine`), `expired`, `cancelled` or `failed`; `DELETE` cancels the window. Bearer auth like every `/api` route.

[Approval rules routes](route-approval-rules.ts) (ATO-1141): `GET /api/approval-rules?workingDir=|sessionId=` returns `{ rules, globalPath, projectPath, projectRules }`: the global file's rules and the folder's project-file ask / deny rules (read-only). `DELETE /api/approval-rules/{id}` removes a global rule (`{ removed: true }`, `404` when there is none). Contract: [approval README](../approval/README.md).

[Project trust routes](route-project-trust.ts) (ATO-298): `GET /api/project-trust` reports the pending trust question for a folder's project skills and instruction files, and `POST /api/project-trust` with `{ answer, questionId }` records it (`{ answer, scope: "all" }` changes the answer for everything the folder ships, the desktop's settings switch); a stale `questionId` gets `409 question_changed` with the fresh status. Without an answer nothing pending loads. Contract: [project folder trust](../skills/docs/project-trust.md).
[Skill routes](route-skills.ts): `POST /api/skills/install` with `{ sourcePath, source?, force?, confirm?, acknowledgeRisk? }` security-scans the folder before copying ([install scan](../skills/docs/skill-format.md#install-security-scan)). A `caution` verdict answers `428` with `error.code: "needs_confirmation"` (`error.param: "confirm"`), `installed: false`, `scan: { verdict, findings[] }`, where each finding is `{ severity, rule, file, line, excerpt }`, and `scanId`; the client shows the findings and repeats the request with `confirm: "<scanId>"`. A `dangerous` verdict answers `403 dangerous_blocked` with the same `scan` and `scanId`, and only `acknowledgeRisk: "<scanId>"` installs it. The id binds the yes to the findings shown: `true`, or the id of an older scan after the folder changed, answers 428/403 again with the new id. A successful install also returns `scan` and `scanId`.
[Active model route](route-llm-active.ts) (ATO-1021): `POST /api/llm/active` with `{ providerId, model? }` switches the running agent's text provider (and chat model) live, through the same legs and rollback as `/model` in the chat channels ([model-switch.ts](../channels/model-switch.ts)): the config cache is dropped first, the model is pinned, the provider rebuilt and made active, the choice persisted. It answers `{ ok, providerId, model, ms }`; `409 turn_in_progress` while any session has a turn running, `404` for an unknown provider, `400` for a missing key, a provider with no chat model, or a model pin on `llama-server`. The desktop calls it for a cloud model pick instead of restarting `atag serve`.
[Config routes](route-config.ts): `GET /api/config` answers `{ path, config, sha256 }`, the hash of the bytes `config` was parsed from (one read). `PUT /api/config` with `{ config, expectSha256? }` is `atomic-agent config set - [--expect-sha256]` in-process (ATO-1022): validated before the write, a version newer than both this build and the file is refused (`400`), and with `expectSha256` a file that moved since the read answers `409 config_changed` and nothing is written. Like the CLI write it leaves the running agent's config cache alone. The desktop uses both while `atag serve` is up, instead of an `atag config` process per read and write.
[Memory embeddings route](route-memory-embeddings.ts) (ATO-1024): `POST /api/memory/embeddings/reconnect` reattaches memory to the embedding model the config file names now (`runtime.reconnectMemoryEmbeddings`, the same call the TUI makes after a model pick), after dropping the config cache. It answers `{ health, modelId, changed?, why? }`, or `501` on a runtime without the switch. The desktop starts `atag serve` without waiting for the embedding server and calls this once that server is up, instead of holding the start back for up to 20 s.
[Telegram channel route](route-telegram-channel.ts) (ATO-758): `GET /api/telegram/channel` answers `{ available, state, lastError, otherPoller }`. `otherPoller` is `{ where: "this_computer", pid }` when another atomic-agent on this computer holds `telegram.lock`, `{ where: "elsewhere" }` when Telegram answers 409 because the bot is polled from somewhere else, `null` otherwise. The desktop's Telegram tab reads it to say why the bot does not answer.

Auth on the network (ATO-1126): the bearer token is compared in constant time ([secret-equal.ts](secret-equal.ts)); an address that sends 10 wrong or missing tokens within a minute gets `429 auth_throttled` with `retry-after` for a minute ([auth-throttle.ts](auth-throttle.ts)); loopback callers are never throttled. `serve` refuses a network host without a key (ATO-760) or with a key shorter than 16 characters, and on `0.0.0.0` / `::` prints the LAN addresses other devices reach it at.

[Phone panel](route-panel.ts) (ATO-1128): `GET /panel` (and `/panel/app.js`) serves a small page for a phone or another computer: the chats, a chat's turns as they land, a message box, and approval requests with Allow once / Deny. The page holds no data and is served without auth; it asks for the API key, keeps it in the browser, and calls the authenticated routes (`/api/sessions`, `/v1/chat/completions`, `/api/events`, `/api/approval/resolve`). Reach it with `atag serve --host 0.0.0.0 --api-key …` (ATO-1126). Over plain `http://` the key crosses the network in clear: use it on a network you trust, or behind TLS (a reverse proxy, Tailscale).

Per-chat folders (ATO-731, [session-working-dir.ts](session-working-dir.ts)): every tool step reads its session's `workingDir`, so `POST /v1/chat/completions` takes `working_dir` (absolute, existing) for a NEW session, `POST /api/sessions/{id}/working-dir` `{ workingDir }` moves one chat (`409 turn_in_progress` only while that chat runs a turn), and `GET /api/sessions?scope=all` lists chats from every folder. None of it restarts `serve`.

Taking a turn back (ATO-1298, [route-rollback-last-turn.ts](route-rollback-last-turn.ts)): `POST /api/sessions/{id}/rollback-last-turn` removes the chat's last question and its answer and returns `200 { id, text }`, the question's text. The body may carry `{ expectText, expectPriorQuestions, expectUnanswered }`, the question the client means by its text, by how many questions come before it (steers not counted, questions a cleared transcript hides counted) and, with `expectUnanswered: true`, by the client having seen no answer to it; if the stored last question differs in any (a failed turn the agent never recorded), it answers `409 turn_mismatch` and removes nothing. `expectUnanswered` (ATO-1420) keeps a wrong count from removing a real answer: a failed question on screen never matches a stored one that has a reply. It only removes: the client sends `text` again through `POST /v1/chat/completions`, so a retry runs the same path as a first try and the old answer is no longer in the chat the model reads. It does not reach outside the transcript: what the turn's reflection already wrote to long-term memory stays, and a chat cut back to nothing keeps its title and leaves `GET /api/sessions` (no question in it) until the question is sent again. Only a turn that changed nothing outside the transcript qualifies: a question answered by one reply, or by nothing (a provider error). A stopped turn does not: a stop can cut a tool batch short, and a local turn stores no trace of that step. Otherwise `409` with `code` `turn_has_tools`, `turn_steered`, `turn_compacted`, `turn_stopped`, `turn_in_progress`, `nothing_to_undo`, `turn_unrecognized` or `turn_mismatch`, and the chat is left as it was. `404 session_not_found` is an unknown chat; an agent without the route answers 404 without that code. The cut itself is [truncateSessionAt](../session/session-truncate.ts).

[Model tiers route](route-model-tiers.ts): `GET /api/model-tiers` returns the Cheap / Balanced / Best picks per provider key (`openrouter`, `aimlapi`, `gemini`, `claude-cli`) from the one data file, [model-tiers.ts](../llm/provider/presets/model-tiers.ts) (ATO-32). The TUI pickers list those models first under the same labels.

Goal mode (ATO-1040, [route-session-goal.ts](route-session-goal.ts), [chat-goal.ts](chat-goal.ts)): the TUI's `/goal` for other clients. `GET /api/sessions/{id}/goal` answers `{ sessionId, goal, running }`, `goal` being the stored [GoalState](../agent/goal/goal-types.ts) (status, per-criterion marks and reasons, rounds used of `maxRounds`) or `null`; `GET /api/sessions` rows and `GET /api/sessions/{id}` carry the same `goal`. `POST /api/sessions/{id}/goal` takes `{ action: "set", criteria: string[], maxRounds?, workingDir? }` (a new chat is opened in `workingDir`, else the server's folder; the stored goal's shell checks are kept, none are added here), `{ action: "pause" }`, `{ action: "resume" }` or `{ action: "clear" }`, with the TUI's rules: `409` with `code` `turn_in_progress`, `no_goal`, `goal_not_running` or `goal_complete`. `set` and `resume` answer `message`, the text to send next through `POST /v1/chat/completions`; with `x-atomic-extensions: 1`, a chat whose stored goal is active runs that message as goal rounds, and the stream carries `event: goal_progress` `{ object: "atomic.goal_progress", session_id, goal }` after every change. `pause` and `clear` on a goal that is running answer `pending: true` and land after its current round (`runtime.controlGoal`).
