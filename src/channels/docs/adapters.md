# Telegram, Discord and Swarm adapters

Status: current
Owner: src/channels/

Channels connect remote messages to the same session/turn runtime. Sender identity, pairing and persisted chat/session pointers must be scoped to the adapter and owner. Approvals are routed to that session's chat surface; invisible fusion workers cannot wait for them. The Telegram approval message shows every line of the preview while it fits in one message; a longer one keeps whole lines from the top and ends with "+N more lines" rather than failing to send. When the preview is cut, every line of the preview (controls and bidi marks escaped as in the prompt) is first sent to the same chat and topic as `full-command.txt`, and the prompt says it was sent, or that it could not be attached so the person knows they have not seen all of it. Under Approve / Deny the Telegram prompt offers the session grants the TUI and CLI offer (GitHub #230, [shared offer](../approval-session-grants.ts), [Telegram buttons](../telegram/approval-grant-buttons.ts)): "Allow <kind> this session" (`appr:<id>:s`) when `canGrantCategory` allows it and "Allow all <shape> this session" (`appr:<id>:a`) when `canGrantShape` does, then "Allow always" when a rule can be saved. A label longer than 60 characters is shortened in the middle of its host, path or command, so "Allow", "Always allow" and the scope ("this session", "in this project") always show ([button-text.ts](../telegram/button-text.ts), ATO-2757); `callback_data` stays inside its own 64-byte limit. A grant goes to `ApprovalGate.resolve` like the TUI's, stays in memory for that session only, never covers a category that is never granted (`trust_config`, dangerous shell, e-mail) and never moves the standing level; a callback for a grant whose button was not sent is dropped. Discord, Slack and Microsoft Teams offer the same grants with the same labels from the same file (ATO-2509): Discord as a second button row (`atomic:approve:session:<id>`, `atomic:approve:shape:<id>`), Slack as buttons after Deny in the prompt's actions block (`atomic_approve:session:<id>`, `atomic_approve:shape:<id>`), Teams as `Action.Submit` actions with `verdict` `session` / `shape`, plus the typed fallback `session <code>` / `all <code>`, which counts only with the code. Each bridge keeps the offer with the pending prompt and refuses a grant click it never offered without settling the request. Such a click (or an unoffered "Allow always") on a prompt that is still waiting leaves the message and its buttons as they are (ATO-2778): Discord acknowledges it with interaction callback type 6, as it does a non-owner's click, and only a request the gate or bridge no longer holds is rewritten to "already expired or was answered elsewhere".

Telegram uses grammy polling with explicit start/stop/reconnect ownership and HTML formatting with safe fallback/chunking. Telegram pairing ([pairing-mode](../telegram/pairing-mode.ts)) opens a 5-minute window with a fresh 6-digit one-time code that only the operator's screen sees (`startPairing` hands it to `onOpened`; it is never logged or put in shared snapshots). Only a private DM `/start <code>` claims it; a wrong code is swallowed, any other DM meets the normal owner check. While an owner is configured, `startPairing` refuses unless the caller passes the operator's confirmation (`replaceOwner`); the TUI asks for it by a second press within 15 seconds. An HTTP client (the desktop) pairs through `POST /api/telegram/pairing`, the only reply that carries the code and its `t.me/<bot>?start=<code>` deep link (Telegram sends `/start <code>` from it, the same claim as typing it), confirms a replacement with `replaceOwner: true` and polls `GET` for the claim ([route](../../http/route-telegram-pairing.ts)). The claim carries the new owner's @username for the confirmation line ([pairing-copy](../telegram/pairing-copy.ts)). Discord owns its gateway transport and output formatting. Discord catches up after a restart or a gateway session it could not resume (ATO-2248): every channel the owner has used keeps the last processed message id in `<stateDir>/discord-session-cursor.json` ([cursor](../discord/discord-message-cursor.ts)); on READY the channel reads the history after it in pages of 100, at most 24 hours back, 5 pages and 20 delivered messages per channel (newest kept), and hands each message oldest first to the live inbound path, so the owner gate, the mention rule and the bot/self filter apply unchanged ([catch-up](../discord/discord-catch-up.ts)). A channel with no cursor is never backfilled; a message seen both live and in the backfill runs once. A RESUMED session needs none of this, Discord replays its events. `@bot stop` and `@bot status` (one word after a mention) act as `/cancel` and `/status` ([mention words](../discord/discord-mention-commands.ts)). Preserve file ingestion/delivery, retries, task-report destination and configured live enable/disable behavior. Task reports, morning digests and the running-tasks part of `/status` are plain-text infrastructure messages that fit one outbound chunk with explicit truncation markers ([report](../telegram/task-report-message.ts), [status](../telegram/task-status-message.ts), [shared format](../telegram/task-report-format.ts)); a digest is never queued by the channel, the task hold keeps it durable and retries; a night with more held reports than one message shows in full goes out as a few numbered digest parts rather than naming the rest by id. `/status` also opens with a status snapshot of the chat's own running turn (plan progress when there is one, what it is doing, the last result in stable words, whether an approval blocks it, elapsed time, steps; [status-snapshot](../../agent/status-snapshot.ts)). On a long turn the progress bubble turns into that snapshot every N steps or M minutes (`ATOMIC_AGENT_STATUS_SNAPSHOT_EVERY_STEPS`, `ATOMIC_AGENT_STATUS_SNAPSHOT_EVERY_MS`; 0 turns a trigger off) and is edited in place; an edit that fails for any reason other than "not modified" or a flood-wait posts a new bubble ([indicator](../telegram/telegram-progress-indicator.ts)). Long reporting tasks get the same: one edited message per task in the owner's DM, deleted when the run ends, none inside quiet hours. Snapshots never echo raw tool output. Agent replies stream while the model writes them ([live reply](../telegram/telegram-live-reply.ts), ATO-634): text deltas grow one plain-text message, posted once and then edited at most about once a second and only after a meaningful amount of new text (a trailing flush shows the tail); past one message's size that message keeps its part and a new one starts; a new step or parse retry restarts the text. When the reply lands, each streamed message is edited into the formatted final chunk (same markdown-to-HTML path and chunking as a normal reply), extra chunks are sent and unneeded messages deleted; an edit that fails sends the rest as new messages. A cancelled turn deletes the streamed text before "Turn cancelled."; a failed turn leaves it above the failure line. Only DMs stream (`telegram.streamReplies`: `private` default or `off`; `ATOMIC_AGENT_TELEGRAM_STREAM_REPLIES` overrides; [mode](../telegram/telegram-stream-mode.ts)). Groups and forum topics never stream: they get the editable progress message (removed when the turn ends, cancelled or failed included) and the final answer as a normal message in the same `message_thread_id`. Flood-waits (429) are waited out and retried with the same text until a three-minute budget per call runs out ([flood-retry](../telegram/flood-retry.ts)); while streaming, a 429 only pauses edits, since the next edit carries all the text. Swarm manages additional bot instances rather than replacing primary channel ownership.

Telegram guests (ATO-2221, [guest access](../telegram/guest-access.ts)): `telegram.allowedUsers` (optional, `[{ userId, role: "guest" }]`, no config version) lists people besides the owner who may address the bot in a group, mention-gated like the owner; they are never heard in a DM, and with no owner configured they are dropped too. Their `[from]` line carries `role=guest` (and the owner's `role=owner` while any guest is configured; without guests the line is unchanged). A guest turn runs with a tool allowlist that is also checked against `readonly` (files, git, web, code search, `reply`/`finish`; not the owner's mail, clipboard, screen, sessions, memory, browser, MCP or GitHub) and with memory read-only; it reads none of the owner's saved memory either: no recalled notes, lessons, procedures or profile facts reach its prompt (ATO-2729, as in an incognito chat). Guests talk to the group's own guest session (chat key `<chat>#guests`, metadata `channelGuest: true`), never the owner's: its own history and none of the owner's grants; the owner's `/cancel` in the group also stops a guest turn. Every filesystem read of a guest session is checked at dispatch ([guest reads](../../tools/read-scope/guest-reads.ts), via `ToolContext.guest`) and refused, at every approval level, outside the working directory, inside a home credential folder or the state directory, on a secret-looking file or folder below it (`.env*`, `.envrc`, private keys, credential data files, `secrets/`, `.ssh/`; [guest secret files](../../tools/read-scope/guest-secret-files.ts), ATO-2703), or for a walk of a folder holding a home credential folder or the state directory; the walking tools (`os.fs.grep`, `os.fs.glob`, `os.fs.code_map`, `os.code.search`, `files.search`) drop nested secret files from a guest's results; git tools are confined by `repo` and paths, refuse `<rev>:<path>` and other `:` arguments, options and globs, and never climb above the working directory (`GIT_CEILING_DIRECTORIES`, repo top checked), `files.search` needs a `folder`, the shell is refused. A guest may run `/start` and `/help`; every other command is refused. While guests are configured, approvals for group sessions go to the owner's DM as a `shared` binding that neither evicts nor is evicted by the DM session's own; an undeliverable DM denies the request. Everyone else is dropped as before.

Every channel implements the shared [`Channel`](../channel.ts) surface: `id`, `state()`, `lastError()`, `start()`, `stop()` (ATO-1169). The runtime keeps all of them in a [`ChannelRegistry`](../channel-registry.ts) at `runtime.channels`; Telegram and Discord are registered there for listing and keep their typed handles and their own shutdown order. A new messenger is a `ChannelDefinition` appended to [channel-catalog.ts](../channel-catalog.ts): it is built at boot (construction must be side-effect free), skipped on platforms outside `platforms`, started when `channels.<id>.enabled` is true, and stopped on shutdown after the primaries. Its settings come from the generic `channels.<id>` block of `config.json` (`enabled`, `ownerIds`, flat `options`; [config](../../config/extra-channel-config.ts)), so a new adapter needs no config version. Secrets stay in `<stateDir>/.env`. An empty `ownerIds` means unpaired and the adapter must refuse every inbound message. A definition that throws while building is logged and skipped without affecting the other channels.

Telegram `/cron` (ATO-21, [command](../telegram/cron-command.ts), [parse](../telegram/cron-command-parse.ts), [service](../telegram/cron-task-service.ts)) lets the owner manage scheduled tasks from the chat: `/cron` lists the recurring tasks that can still fire (waiting, running, paused), `/cron add [--tz <zone>] <cron> <task>` creates one through `TaskRunner.create` with `origin: "telegram"` and `notify: "telegram"` (the result goes to the owner's DM, as every task report does), and `/cron pause|resume|delete <id>` take the id or a unique prefix of at least 4 characters. The cron is checked with the core's `validateSchedule` before anything is written, and an invalid one is answered with the parser's reason. The command checks the owner again on top of the inbound gate. Delete cancels the task (it stays in task history); pause and resume use the task queue's own paused state (ATO-590), so the list shows a paused task as Paused and the desktop and CLI see the same pause. When the scheduler is off, the replies say nothing will run.

`/fork` (ATO-2235, [shared](../channel-fork.ts), [telegram](../telegram/telegram-fork-command.ts), [slack](../slack/slack-fork-command.ts)) copies the chat's session the way the desktop's Fork does (`planFork` at the last question; the working folder is not cloned, the summary is carried as is) and never changes the source; it refuses while a turn runs. On Telegram, in a forum supergroup it opens a topic with `createForumTopic` and maps that topic to the copy; without topics, or when the bot may not manage them, this chat moves to the copy and the source stays in its history for `/switch`; in a forum the reply then says no topic could be opened and that the bot needs the "Manage topics" admin right (ATO-2757). On Slack `!fork` in a channel posts a top-level message and maps its thread to the copy; in a DM the DM moves to the copy. Discord answers that fork is not available yet.

Signal ([signal](../signal/index.ts), ATO-629) talks to a `signal-cli -a <bot number> daemon --http 127.0.0.1:8080` that the operator installs and runs; signal-cli (GPL-3.0, needs Java or Docker) is never bundled. Replies and typing go over JSON-RPC `POST /api/v1/rpc` (`send`, `sendTyping`); messages arrive on the SSE stream `GET /api/v1/events`, reconnected on the shared backoff with `Last-Event-ID` so the daemon replays what was missed. Settings are `channels.signal.options` (`url`, default `http://127.0.0.1:8080`; `account`, the bot number, required, else `disabled`; `allowGroups`, default off) and `ownerIds` as E.164 numbers or UUIDs; there is no secret. A daemon that is not running reads as `down` with "signal-cli daemon not reachable at <url>" and keeps retrying. Each DM partner and each group (only with `allowGroups`, only owner messages) is its own session in `<stateDir>/signal-session.json`; the lock is `<stateDir>/signal.lock`. Approvals are text: the prompt carries a 4-character code and an owner answers `yes <code>` / `no <code>` (`always <code>` when a rule can be saved). Replies are plain text cut at 2000 characters; inbound files are refused with a notice for now.


Slack ([slack-channel](../slack/slack-channel.ts), ATO-499) connects over Socket Mode, so no public URL is needed: `apps.connections.open` with the app-level token (`SLACK_APP_TOKEN`, `xapp-`, `connections:write`) returns a single-use wss URL, every envelope is acknowledged with its `envelope_id` before any work, `disconnect` reconnects with the shared backoff (`link_disabled` and token errors stop and report), and Web API calls use the bot token (`SLACK_BOT_TOKEN`, `xoxb-`), check `ok` and honour HTTP 429 `Retry-After` ([api](../slack/slack-api.ts), [socket](../slack/slack-socket.ts)). Only DMs (`message.im`) and `app_mention` from a member id in `channels.slack.ownerIds` reach the agent; bot posts, subtypes (edits, joins, file shares) and the bot's own `auth.test` user are ignored, and a redelivered event runs once. Each DM is one session; in channels each thread is one session and the reply goes in the thread (`options.threadReplies`, default true; off, top-level mentions share one session per channel). Commands come as the app's slash command `/atomic <command>` (a `slash_commands` envelope, owner-only, a non-owner gets an ephemeral refusal through `response_url`, the reply goes to the channel or DM it was invoked in; [slash](../slack/slack-slash-command.ts)) or as `!new`, `!status`, `!model`, `!cancel`, `!help` typed in a message, which also works inside a thread. A slash command carries no thread, so in a channel it acts on the channel-level conversation, and when the bot is not in that channel (`not_in_channel`, `channel_not_found`) the reply comes back ephemerally through `response_url` with a hint to invite the bot. Text after `/atomic` that is not a command goes to the agent. Replies are converted to mrkdwn with `&`, `<`, `>` escaped so a reply can never ping `<!channel>`, and chunked at 3500 characters. Approvals are Block Kit buttons whose `action_id` carries the approval id; a click from a non-owner gets an ephemeral refusal, a decision rewrites the prompt with `chat.update` ([bridge](../slack/slack-approval-bridge.ts)). Lock `<stateDir>/slack.lock`, sessions `<stateDir>/slack-session.json`. Not yet: inbound and outbound files, a settings screen.


iMessage ([channel](../imessage/imessage-channel.ts), id `imessage`, darwin only, ATO-630) lets the Mac's owner text the agent from Messages on their iPhone. It drives the external [`imsg`](https://github.com/steipete/imsg) CLI (MIT, macOS 14+) that the operator installs (`brew install steipete/tap/imsg`); nothing is bundled. Run the bot under its own Apple ID (or a separate macOS user signed in to one): a message the owner sends from the same Apple ID arrives as the Mac's own (`is_from_me`) and is ignored. Inbound is one long-running `imsg watch --json` child whose NDJSON lines are parsed in one file ([event](../imessage/imsg-event.ts)) so a schema change is a one-file fix; it restarts with the shared backoff and resumes with `--since-rowid` after the last new message ([watch](../imessage/imsg-watch.ts)). Outbound is `imsg send --to <handle>` (or `--chat-id` for a group) through `execFile` with an argument array, never a shell, the text attached as `--text=<text>` so a reply starting with `-` is not read as an option, in chunks of about 2000 characters, never retried because a failed send may still have been delivered ([send](../imessage/imsg-send.ts)). `ownerIds` are phone numbers or Apple ID e-mails, compared exactly after removing spaces, dashes, dots and parentheses (and lower-casing e-mails); logs carry only a masked handle. Only messages carried by iMessage count as the owner: an SMS relayed by Text Message Forwarding (or RCS) has a spoofable caller id and is dropped. imsg does not print a per-message service, so it is read from the chat GUID prefix; when that proves nothing (a newer `any;-;` chat), the channel reads `message.service` for that rowid from `~/Library/Messages/chat.db`, opened read-only with better-sqlite3 and reused until `stop()` ([service check](../imessage/imessage-service-check.ts)). Only `iMessage` passes; a failed lookup refuses the message and is logged once with the Full Disk Access hint. The channel ignores its own messages (`is_from_me`), edits, unsends and tapbacks, and group chats unless `options.allowGroups`. Approvals are text: the prompt carries a 4-digit code and only an owner's `yes <code>` / `no <code>` from the same chat decides ([bridge](../imessage/imessage-approval-bridge.ts)). `imsg` missing is `disabled` with an install hint in `lastError`; a missing Full Disk Access or Automation grant is `down` with the System Settings path to fix it ([errors](../imessage/imsg-errors.ts)). Files are not ingested yet. Options: `binary` (default `imsg` on PATH), `allowGroups` (default false). Lock `<stateDir>/imessage.lock`, sessions `<stateDir>/imessage-session.json`.


Matrix ([channel](../matrix/matrix-channel.ts), ATO-632) talks to the homeserver over the plain Client-Server API with the global `fetch`, no SDK. Settings: `channels.matrix` with `enabled`, `ownerIds` (mxids) and `options.homeserver` (https, or http on loopback only; missing means `disabled`), optional `options.userId` checked against `/account/whoami`; the token is `MATRIX_ACCESS_TOKEN` in `<stateDir>/.env`. Inbound is a `/sync` long poll ([loop](../matrix/matrix-sync-loop.ts)) filtered to `m.room.message` and `m.room.encrypted`; `next_batch` is kept in `<stateDir>/matrix-sync.json` per bot account, and the first sync without one skips the timeline so history never runs as new requests. The bot joins a room only on an owner's invite and rejects other invites; it ignores its own events, `m.notice`, edits and non-owners, strips the reply quote, and keeps one session per room in `<stateDir>/matrix-session.json`. Replies go out as `m.text` with an HTML `formatted_body` (the Telegram converter plus `<br>`), split at 8000 characters; help, status, prompts and errors are `m.notice`. A 429 or `M_LIMIT_EXCEEDED` waits `retry_after_ms` and retries; a dead token stops the loop and reports `down`; anything else backs off with the shared schedule. Approvals have no buttons: the prompt carries a 6-character code and an owner answers `yes <code>`, `no <code>` or `always <code>` in the same room; a bare `yes`/`no` counts only when exactly one prompt is open there ([bridge](../matrix/matrix-approval-bridge.ts)). Encrypted rooms are not supported yet: an encrypted event from an owner gets one plain-text notice per room per 10 minutes. End-to-end encryption needs the native `@matrix-org/matrix-sdk-crypto-nodejs` module and a decision on the SEA and Windows builds. Files in either direction are not supported yet and are answered with a notice.


Google Chat ([channel](../googlechat/googlechat-channel.ts), ATO-506) uses the operator's own Chat app in their own Google Cloud project, configured with a Cloud Pub/Sub connection; we run no relay and the machine needs no public URL. Settings: `channels.googlechat` with `enabled`, `ownerIds` (`users/<id>` resource names, or emails, which Chat only fills in for the same Workspace domain) and `options.subscription` (`projects/<p>/subscriptions/<s>`; missing means `disabled`); `GOOGLE_CHAT_CREDENTIALS` in `<stateDir>/.env` is the *path* to the service-account JSON key, whose contents are never logged. Auth is the JWT bearer flow with `node:crypto` only ([auth](../googlechat/googlechat-auth.ts)): an RS256 assertion for the `pubsub` and `chat.bot` scopes is exchanged at the fixed `oauth2.googleapis.com/token` (a key file's `token_uri` is ignored) and the token is cached until a minute before expiry. Inbound is a `:pull` loop of up to 10 messages ([loop](../googlechat/googlechat-pull-loop.ts)); each message's base64 `data` is a Chat event. Every pulled message is acknowledged once its batch is dispatched, including ignored and undecodable ones, and before the turns finish, so a long turn never outlives the ack deadline and runs twice; redeliveries are dropped by message name. A bad key, a missing subscription or a missing permission stops the loop and reports `down`; anything else backs off with the shared schedule. Events arrive in the classic interaction shape or, for an app built as a Workspace add-on, as `chat.messagePayload` / `chat.addedToSpacePayload` / `chat.user`; [the parser](../googlechat/googlechat-events.ts) reads both into one event. `/whoami` is the one thing anyone may ask: it answers the sender's own `users/<id>` (and email, when present) with a line to add it to `ownerIds`, at most once a minute per sender, and reveals nothing else. The app ignores other apps (`user.type == BOT`), non-owners and `CARD_CLICKED`, answers `ADDED_TO_SPACE` from an owner with the help text, and keeps one session per space in `<stateDir>/googlechat-session.json`. Replies are posted with `spaces.messages.create` into the asking message's thread (`REPLY_MESSAGE_FALLBACK_TO_NEW_THREAD`), split at 4000 characters; a 429 or 5xx waits `Retry-After` or the shared backoff and retries a few times. Approvals are text, like Matrix: the prompt carries a 6-character code and an owner answers `yes <code>`, `no <code>` or `always <code>` in the same space ([bridge](../googlechat/googlechat-approval-bridge.ts)). Files in either direction are not supported yet and are answered with a notice.


Microsoft Teams ([msteams-channel](../msteams/msteams-channel.ts), ATO-506) uses the user's own Azure Bot registration (`MSTEAMS_APP_ID`, `MSTEAMS_APP_PASSWORD`; `options.tenantId` for a single-tenant app) and speaks the Bot Framework REST protocol with built-ins, no SDK and no relay of ours. A `node:http` endpoint on `127.0.0.1:<options.port, default 3978>/api/messages` ([server](../msteams/msteams-server.ts)) is exposed by the user's own tunnel; every request's bearer JWT is checked against the Bot Framework OpenID keys (RS256, key endorsement for the `channelId`, `iss`, `aud` = App ID, `exp`/`nbf` with 5 minutes of skew, `serviceurl` claim equal to the activity's; [jwt](../msteams/msteams-jwt.ts)), anything else is a 401, an accepted activity is answered 200 at once and processed after. Replies use a cached client-credentials token and go only to service URLs seen in authenticated activities ([api](../msteams/msteams-api.ts)). Only `message` activities from an AAD object id in `ownerIds` reach the agent, in personal chats always, in channels and group chats only with an @mention of the bot (stripped). A second message while a turn runs in the same conversation is refused with a hint to `/cancel`. Approvals are Adaptive Cards whose `Action.Submit` data carries the approval id, settled only by an owner in the same conversation, then replaced by the decision; `yes <code>` typed works too ([bridge](../msteams/msteams-approval-bridge.ts)). Setup, manifest and tunnel options: [msteams.md](msteams.md). Not yet: files, proactive task reports, a settings screen.


WhatsApp ([channel](../whatsapp/whatsapp-channel.ts), ATO-502) makes the agent a WhatsApp contact by linking it like WhatsApp Web, over the **unofficial** WhatsApp Web protocol through [`baileys`](https://github.com/WhiskeySockets/Baileys) (MIT); Meta's official Cloud API is not used and is a later option. WhatsApp may restrict or ban a number used this way, so the channel is off by default, says so in the log and in the QR file every time it pairs, and the operator should link a spare number, not their main one. Settings: `channels.whatsapp` with `enabled`, `ownerIds` (phone numbers in any common form such as `+1 555 000 2222`, or JIDs `<digits>@s.whatsapp.net` / privacy ids `<id>@lid`, all normalized and compared without the device suffix) and `options.allowGroups` (default false); there is no secret in `.env`. The session keys live in `<stateDir>/whatsapp-auth/` (baileys' multi-file auth state). Pairing: on the first start the channel is `down` with "Not paired yet. Scan the QR code in `<stateDir>/whatsapp-qr.txt`..."; that file (mode 600) holds the QR drawn as text with `qrcode-terminal` and is rewritten each time WhatsApp rotates the code; scan it from the bot's phone under Settings > Linked devices > Link a device. The file is deleted once linked. A QR nobody scans in time stops with "restart the channel to get a new one" rather than printing codes forever. The restart WhatsApp asks for right after a scan (515) reconnects at once; a logged-out device (401) deletes the stale keys and stays `down` with "pair again"; a session taken over by another WhatsApp Web client (440), a 403 and a damaged session stop with their own line; anything else reconnects with the shared backoff and keeps the keys. baileys sits behind a small connector interface ([transport](../whatsapp/whatsapp-transport.ts), [baileys](../whatsapp/whatsapp-baileys.ts)) and is loaded with a lazy `import()` only when the channel starts; when it cannot be loaded (the single-file binary marks it external and does not ship it yet) the channel is `disabled` with a `lastError` saying so. Only new messages (`messages.upsert` of type `notify`) count; the bot's own messages (`fromMe`), status updates, broadcast lists, channels and non-owners are dropped (ids are never logged), groups too unless `allowGroups`, and then only owner messages, with a `[from]` line that prefers the privacy id over the phone number. A redelivered message id runs once. Each DM partner and each group is its own session in `<stateDir>/whatsapp-session.json`; the lock is `<stateDir>/whatsapp.lock`. Approvals are text like Signal: the prompt carries a 4-character code and an owner answers `yes <code>` / `no <code>` (`always <code>` when a rule can be saved) in the same chat ([bridge](../whatsapp/whatsapp-approval-bridge.ts)). Replies are plain text cut at 2000 characters; photos, voice notes and files are refused with a notice (a caption is still read). Not yet: media in either direction, the official Cloud API, a pairing screen in the desktop app.

Telegram guest sessions and `/new` (ATO-2703, [reset](../telegram/guest-session-reset.ts)): the owner's `/new` in a group also rotates the group's guest session (`<chat>#guests`), so the guests' history starts over with the owner's; the old one is archived in the pointer's history and its approval binding is dropped unless a guest turn is still running (then it drops when the turn settles). A DM has no guest session and is unchanged.

Shared model commands currently import provider persistence from TUI; stage 02 moves that responsibility. Do not describe this boundary as already repaired.
