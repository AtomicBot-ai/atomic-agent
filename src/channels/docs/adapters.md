# Telegram, Discord and Swarm adapters

Status: current
Owner: src/channels/

Channels connect remote messages to the same session/turn runtime. Sender identity, pairing and persisted chat/session pointers must be scoped to the adapter and owner. Approvals are routed to that session's chat surface; invisible fusion workers cannot wait for them. The Telegram approval message shows every line of the preview while it fits in one message; a longer one keeps whole lines from the top and ends with "+N more lines" rather than failing to send. When the preview is cut, every line of the preview (controls and bidi marks escaped as in the prompt) is first sent to the same chat and topic as `full-command.txt`, and the prompt says it was sent, or that it could not be attached so the person knows they have not seen all of it.

Telegram uses grammy polling with explicit start/stop/reconnect ownership and HTML formatting with safe fallback/chunking. Telegram pairing ([pairing-mode](../telegram/pairing-mode.ts)) opens a 5-minute window with a fresh 6-digit one-time code that only the operator's screen sees (`startPairing` hands it to `onOpened`; it is never logged or put in shared snapshots). Only a private DM `/start <code>` claims it; a wrong code is swallowed, any other DM meets the normal owner check. While an owner is configured, `startPairing` refuses unless the caller passes the operator's confirmation (`replaceOwner`); the TUI asks for it by a second press within 15 seconds. An HTTP client (the desktop) pairs through `POST /api/telegram/pairing`, the only reply that carries the code, confirms a replacement with `replaceOwner: true` and polls `GET` for the claim ([route](../../http/route-telegram-pairing.ts)). The claim carries the new owner's @username for the confirmation line ([pairing-copy](../telegram/pairing-copy.ts)). Discord owns its gateway transport and output formatting. Preserve file ingestion/delivery, retries, task-report destination and configured live enable/disable behavior. Task reports, morning digests and the running-tasks part of `/status` are plain-text infrastructure messages that fit one outbound chunk with explicit truncation markers ([report](../telegram/task-report-message.ts), [status](../telegram/task-status-message.ts), [shared format](../telegram/task-report-format.ts)); a digest is never queued by the channel, the task hold keeps it durable and retries; a night with more held reports than one message shows in full goes out as a few numbered digest parts rather than naming the rest by id. `/status` also opens with a status snapshot of the chat's own running turn (plan progress when there is one, what it is doing, the last result in stable words, whether an approval blocks it, elapsed time, steps; [status-snapshot](../../agent/status-snapshot.ts)). On a long turn the progress bubble turns into that snapshot every N steps or M minutes (`ATOMIC_AGENT_STATUS_SNAPSHOT_EVERY_STEPS`, `ATOMIC_AGENT_STATUS_SNAPSHOT_EVERY_MS`; 0 turns a trigger off) and is edited in place; an edit that fails for any reason other than "not modified" or a flood-wait posts a new bubble ([indicator](../telegram/telegram-progress-indicator.ts)). Long reporting tasks get the same: one edited message per task in the owner's DM, deleted when the run ends, none inside quiet hours. Snapshots never echo raw tool output. Agent replies stream while the model writes them ([live reply](../telegram/telegram-live-reply.ts), ATO-634): text deltas grow one plain-text message, posted once and then edited at most about once a second and only after a meaningful amount of new text (a trailing flush shows the tail); past one message's size that message keeps its part and a new one starts; a new step or parse retry restarts the text. When the reply lands, each streamed message is edited into the formatted final chunk (same markdown-to-HTML path and chunking as a normal reply), extra chunks are sent and unneeded messages deleted; an edit that fails sends the rest as new messages. A cancelled turn deletes the streamed text before "Turn cancelled."; a failed turn leaves it above the failure line. Only DMs stream (`telegram.streamReplies`: `private` default or `off`; `ATOMIC_AGENT_TELEGRAM_STREAM_REPLIES` overrides; [mode](../telegram/telegram-stream-mode.ts)). Groups and forum topics never stream: they get the editable progress message (removed when the turn ends, cancelled or failed included) and the final answer as a normal message in the same `message_thread_id`. Flood-waits (429) are waited out and retried with the same text until a three-minute budget per call runs out ([flood-retry](../telegram/flood-retry.ts)); while streaming, a 429 only pauses edits, since the next edit carries all the text. Swarm manages additional bot instances rather than replacing primary channel ownership.

Shared model commands currently import provider persistence from TUI; stage 02 moves that responsibility. Do not describe this boundary as already repaired.
