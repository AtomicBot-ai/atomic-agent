# Telegram, Discord and Swarm adapters

Status: current
Owner: src/channels/

Channels connect remote messages to the same session/turn runtime. Sender identity, pairing and persisted chat/session pointers must be scoped to the adapter and owner. Approvals are routed to that session's chat surface; invisible fusion workers cannot wait for them. The Telegram approval message shows every line of the preview while it fits in one message; a longer one keeps whole lines from the top and ends with "+N more lines" rather than failing to send. When the preview is cut, every line of the preview (controls and bidi marks escaped as in the prompt) is first sent to the same chat and topic as `full-command.txt`, and the prompt says it was sent, or that it could not be attached so the person knows they have not seen all of it.

Telegram uses grammy polling with explicit start/stop/reconnect ownership and HTML formatting with safe fallback/chunking. Telegram pairing ([pairing-mode](../telegram/pairing-mode.ts)) opens a 5-minute window with a fresh 6-digit one-time code that only the operator's screen sees (`startPairing` hands it to `onOpened`; it is never logged or put in shared snapshots). Only a private DM `/start <code>` claims it; a wrong code is swallowed, any other DM meets the normal owner check. While an owner is configured, `startPairing` refuses unless the caller passes the operator's confirmation (`replaceOwner`); the TUI asks for it by a second press within 15 seconds. An HTTP client (the desktop) pairs through `POST /api/telegram/pairing`, the only reply that carries the code, confirms a replacement with `replaceOwner: true` and polls `GET` for the claim ([route](../../http/route-telegram-pairing.ts)). The claim carries the new owner's @username for the confirmation line ([pairing-copy](../telegram/pairing-copy.ts)). Discord owns its gateway transport and output formatting. Preserve file ingestion/delivery, retries, task-report destination and configured live enable/disable behavior. Swarm manages additional bot instances rather than replacing primary channel ownership.

The Telegram approval keyboard can record a session grant (issue #230), pressed only by the paired owner. A shell request gets only a command-shape row (one binary, when `canGrantShape` allows it, like "Allow in this chat" on the desktop); an opaque or compound command gets Approve / Deny only. Any other category gets a row naming it when `canGrantCategory` allows it. This is a threat-model decision, not a missed wire-up: the earlier rule was that only surfaces on the machine (TUI, CLI, desktop) could grant, and a remote chat can now raise trust for the rest of one session. What still holds: a grant is in-memory, keyed by session id, and ends when the chat leaves the session (`/new`, `/switch`, delete, stale sweep, channel stop); it is never offered or recorded for a `trust_config`, `email` or `fusion_fanout` request; it cannot skip a hardline shell-guard block; and the channel has no command that changes the standing level. What does not: a shape grant does not inspect what the command touches, so a granted binary may still write the agent's config or `.env` without asking (tracked in ATO-877 / ATO-1172). The bridge re-checks the scope against the retained request when the button comes back, and the toast reports only a grant the gate kept; a click on an approval the gate no longer holds answers "Already resolved" and removes the keyboard.

Shared model commands currently import provider persistence from TUI; stage 02 moves that responsibility. Do not describe this boundary as already repaired.
