## Entry points

- [coding-mode.ts](coding-mode.ts): shared default/plan/auto/bypass mapping and mode metadata; frontends adapt its policy to their controls.
- [approval-gate.ts](approval-gate.ts)
- [approval-router.ts](approval-router.ts)
- [dangerous-tool.ts](dangerous-tool.ts)
- [read-scope-grants.ts](read-scope-grants.ts)
- [approval-rules.ts](approval-rules.ts): saved allow / ask / deny rules (ATO-1141): parse, validate, `matchRules` (deny > ask > allow; an allow never applies to a category `isGrantableCategory` rejects), and the rule "Allow always" saves (`buildAlwaysRule`, `canGrantAlways`, `describeAlwaysRule`). A rule's optional `origin` matches the request's `grantKey`; an "Allow always" on `os.http.request` saves its target origin there, so it covers one host only (ATO-1471). Pure.
- [manual-approval-rule.ts](manual-approval-rule.ts): a rule added by hand through `POST /api/approval-rules` (ATO-1011). Runs `parseApprovalRule`, then refuses any allow that "Allow always" could not save (`canGrantAlways`): never-granted categories, `fs_write_home`, per-site browser categories, shell without a `commandPrefix` or with a dangerous / wrapper prefix, HTTP without `origin`, reads outside without `path`, a non-shell allow without its `tool`, and any allow without `project` (checked last; ask and deny may be global). Pure.
- [approval-rules-store.ts](approval-rules-store.ts): the files. Global `<stateDir>/approval-rules.json` (allow / ask / deny, optionally `project`-scoped; a write asks as `trust_config`, a read as `state_secret`) and per project `<workdir>/.atomic-agent/approval-rules.json`, where only ask and deny count because the model can write in the workspace. Reloads on a stat change, writes tmp + rename at 0600, and treats a missing or unreadable file as empty (an unreadable one is logged and moved aside before the next save).
- HTTP has two categories (ATO-1462): `http` for reads (GET), quiet from level 3, and `http_write` for requests that send data (POST), quiet from level 4. A grant or allow rule on one never answers the other; a deny or ask rule on `http` also matches `http_write` (`ruleMatches`).
- Organization policy (ATO-587, [../policy/README.md](../policy/README.md)): `ApprovalGate.setOrgPolicy` installs a check that turns the admin policy into a rule match. A policy deny or ask stands above the saved rules (an ask still loses to a saved deny) and reaches every place that reads rules (`request`, `ruleDecisionFor`, `wouldPrompt`); a policy allow never skips a prompt. A check that throws is ignored.
- [approval-workdir.ts](approval-workdir.ts): the dispatching tool call's session folder, so the gate can scope rules to a project without threading it through every tool.
- [risk-review.ts](risk-review.ts): smart approval (`agent.smartApproval`, off by default). Before a grantable request prompts, a model rates it low/medium/high under a grammar or one-field schema; `low` runs it, anything else and every failure prompts with `riskNote`. Fail-closed; never for non-grantable categories, `fs_read_outside` or a session under a refuse policy. Wired by [runtime-risk-review](../runtime/composition/runtime-risk-review.ts).
- [untrusted-taint.ts](untrusted-taint.ts): review after outside content (`agent.taintReview`, off by default, ATO-618). The tool registry reports every tool result that carries outside text (`untrustedOutput`, `externalSource`) to `ApprovalGate.noteUntrustedContent`; the agent loop clears it when a turn starts (not on a steer). While a session is tainted, a request the level or a session grant would approve, of a category `isTaintSensitive` names (it could send data out, act outward or run code), goes to the risk reviewer with the outside sources and an AlignmentCheck question ("does this serve what the user asked for?"); `low` runs it, anything else, a reviewer that is off, and a category the reviewer may not settle put it to the person with `riskNote`. A saved allow rule still answers. A session under a refuse policy is refused. Calls that skip the gate on their own (a GET of `os.http.request` under `http.approvalMode: "writes"`, every `os.web.fetch`) ask `ApprovalGate.holdsForOutsideContent` and, when it says yes, request an `http` approval so the hold decides: their URL alone can carry data out. `http.approvalMode: "never"` and a set `http.hostAllowlist` keep answering for `os.http.request`.
- [guard-rules.ts](guard-rules.ts), [guard-review.ts](guard-review.ts), [guard-check.ts](guard-check.ts): plain-text security rules (ATO-2111, guide: [security-rules.md](../../docs/user/security-rules.md)). On while `<stateDir>/guard.md` or `<workdir>/.atomic-agent/guard.md` exists with rule text (read per call, cached by mtime). Frontmatter `tools:` (default `DEFAULT_GUARD_TOOLS`: shell, skill scripts, HTTP, `os.web.fetch`, file writes, git commit and push; a listed tool in `GUARD_UNREVIEWED_TOOLS`, the reads that never ask, is warned about at load) and `onFailure: ask|block`. Before a listed tool's request goes past the saved deny rule, `ApprovalGate.setGuard`'s reviewer (the smart-approval model plumbing, `resolveRiskReviewProvider`) reads each rule set with the user's request and the call (egress facts included) and answers allow or block under a grammar or one-field schema. Block refuses the call (`automatic`, `Blocked by your security rules: <reason>`) whatever the level, bypass, a grant or an allow rule says. Allow only continues the gate. Every failure (error, 15 s timeout, unreadable or self-contradicting reply) follows `onFailure`: `ask` holds the call for a person like the egress hold (a refuse policy refuses it), `block` refuses. The project file only adds: its tools join the list, its `block` wins, and its rules get their own pass inside an untrusted block, so it cannot relax the person's rules. Both files are trust config. A fan-out scope that settles a shell or file call without the gate asks `guardRefusal` first (`requireGuardOnShortcut`); there a reviewer failure under `onFailure: ask` goes through `requireApproval` so the person is asked, and is refused under a refuse policy. So do the calls that skip the gate on their own: a GET of `os.http.request` under `"writes"` or any request under `"never"`, every `os.web.fetch`, and the shell guard's trusted read-only tools (`gh`, `gog`, `icalBuddy`). Not reviewed: other commands the shell guard deems safe and reads that never ask.
- [egress-scan.ts](egress-scan.ts): where a shell command sends data (ATO-2116, patterns ported from Goose's egress inspector, Apache-2.0). A pure scan of `commandSegments` (so wrappers and `sh -c` are unwrapped) into `{kind, host, direction, label}`, for known programs only (anything else, a script file, a `/dev/tcp` redirect or a DNS lookup is not seen): curl / wget (outbound with a body or file, `-X POST|PUT|PATCH`; a plain GET is inbound), `git push` and `git send-email`, scp / rsync to `host:`, ssh, nc / socat / telnet / ftp, docker / podman push and login, aws s3 / gsutil / gcloud storage, npm / pnpm / yarn / cargo / twine / poetry / gem publishing, and `python -c` / `node -e` code that posts to a URL. Helpers in egress-scan-http.ts, egress-scan-git.ts, egress-scan-tools.ts and egress-host.ts. A push to a remote name reads its URL from the repository's config files without running git ([git-remote-url.ts](git-remote-url.ts)); an `insteadOf` rewrite, an `include`, a `-c remote.*` or a `GIT_*` variable leaves it unresolved, and so does any part of the same call that runs `git remote|config|init|clone`, `git checkout|switch`, `cd` / `pushd`, sets or exports a `GIT_*`, `HOME` or `XDG_CONFIG_HOME` variable (after `env` or `sudo` too), or writes into `.git`; a `git -c alias.*` is an unknown destination. A clear send whose address cannot be read gets `host: null`: an unreadable operand (`3232235777`, `$URL`), a proxy or address override (`-x`, `--proxy`, `--socks*`, `--connect-to`, `--resolve`, a `*_proxy`, `HOME`, `XDG_CONFIG_HOME`, `CURL_HOME` or `*WGETRC` variable, also after `env` or `sudo`, a `source` / `.` in the call, or a write to `.curlrc` / `.wgetrc`), and any curl `-K` / wget `-e` config. `~/.curlrc` and `~/.wgetrc` are trust config. The card line lists unknown destinations first, never folds them into `+N more`, and turns control, bidi and zero-width characters in labels into spaces. The shell tool puts the result in `ApprovalRequest.egress`; the TUI, Telegram and Discord show the outbound part as `sends data to → host` (`formatEgressLine`; a held readable host is tagged `(new)`, and `formatEgressHoldNote` says why the card asked, ATO-2759), the sidecar and `GET /api/events` pass the field on, and the risk reviewer reads it inside the untrusted action block. A publish names the default registry unless the command names one (an `.npmrc` registry is not read).
- [egress-hold.ts](egress-hold.ts): the egress hold (ATO-2116, on always). A request with an outbound destination whose host is not known is put to a person whatever the level, a session grant, a saved allow rule or bypass mode says, and the risk reviewer does not settle it, the way an ask rule stands above them; a fusion worker's fan-out scope does not cover it, so the worker's refuse policy refuses it. Known: loopback, `http.hostAllowlist` (exact or `*.domain`; unset knows nothing), a per-site browser grant or an HTTP origin grant of the session, and the hosts of an earlier command the person answered with a session grant or "Allow always" (in memory, dropped with the session's grants). An unreadable host is never known, and a request marked `commandUnreadable` (a script fed to a shell, also as `/dev/stdin` or `<(...)`, or a line `eval`, `source` or `sh -c` builds at run time) counts as one; the gate marks the held entries `unapproved` for the card. A saved allow rule does not answer it on purpose: "Allow always" on `curl …` saves a `curl` prefix that would cover every host. It only adds prompts; a deny rule, the same-turn refusal and hardline guard rules come first as before.
- [user-question.ts](user-question.ts): the clarifying question `ask_user` asks (ATO-489). It goes through the gate as a `user_question` request carrying `question` (prompt, 2-8 options, `multiSelect`, `allowOther`), so the turn waits like an approval and every surface that gets approvals gets it. No level, grant, allow rule or reviewer answers it (`isAutoApprovedAt` is false at every level); a refuse policy or a deny rule refuses it at once and the model is told to go on with its best guess. The answer comes back in `ApprovalDecision.answer`, checked by `validateUserQuestionAnswer`; a Deny is a skip. Pending questions live in memory like approvals: a reconnecting client gets them back from `/api/events`, a restarted agent does not (its turn ended).
- `browser_take_over` (ATO-508, `../tools/browser/take-over.ts`): the agent hands the browser to the person for a login, a password or a captcha and waits. Allow means "done, carry on", so like `user_question` no level (bypass included), grant, allow rule or reviewer answers it; a refuse policy or a deny rule refuses it at once and the model is told nobody could take over.
- [approval-preview.ts](approval-preview.ts): fits a long preview onto a size-limited surface (TUI modal, Telegram message) by whole lines, with an explicit "+N more lines" note instead of a silent cut, and pages the whole preview (`pagePreview`) for a surface that shows all of it before the decision.

## Ownership and dependencies

Gate order in `ApprovalGate.request`: the same-turn refusal (`declinedInTurn`), a matching deny rule (refused, `automatic`), the security rules review when a guard file covers the tool (block refuses; a failure under `onFailure: ask` holds for a person, see guard-check.ts), a matching ask rule (skips the level and grants and prompts), the egress hold (an outbound host nobody approved: skips the level, grants, allow rules and the reviewer, see egress-hold.ts), the level, the session grant (both held back after outside content when `agent.taintReview` is on, see untrusted-taint.ts), a matching allow rule, the smart review, then the session's refuse policy, the PermissionRequest hooks (`setPromptHooks`, ATO-2462: they can only refuse, `automatic`; never approve) and the prompt, which also fires the Notification hooks. A request marked `askEveryLevel` (a credential read or an encoded shell command, ATO-2126) skips the level, the grants and allow rules, so it prompts even at level 5; a deny rule and a refuse policy still refuse it. `resolve({ grant: "always" })` saves the allow rule built from the pending request, scoped to its project; hardline shell-guard rules fire before the gate and no rule touches them. A fan-out scope returns before the gate, so the tools ask `ruleDecisionFor` first: a deny or ask rule sends the call to the gate. A shell command the guard deems safe never asks either, so `os.shell.run` asks `ruleDecisionFor` for it too: a deny rule sends it to the gate, which refuses it (ATO-1332). Deny and ask rules match every command in `commandSegments`: past wrappers and their value flags (`sudo -u root`, `nice -n 5`, `timeout 5`, `env -u X`, `xargs -n 1`), inside a nested `sh|bash|zsh|dash|ksh|fish|csh|tcsh -c` line, `eval` and `find -exec` (`shellRuleSegments`). A script fed to a bare shell or interpreter through a pipe, a redirect or a heredoc (`printf … | sh`) cannot be read, so the request is marked `commandUnreadable` and any deny or ask command rule matches it. An allow rule still needs `commandArgv`. A worker in a throwaway worktree matches rules against its parent's project (`SessionApprovalPolicy.ruleWorkdir`). `wouldPrompt` (the fan-out's pre-check) follows the same order: a deny or allow rule means no prompt, an ask rule means a prompt whatever the level or a grant (ATO-1270).

ApprovalRouter selects the handler for the owning session; level/grant logic decides whether a dispatch can proceed unattended or needs a decision. Frontends and channel bridges provide interaction, while tools consume the decision. Approval state is separate from offered prompt schemas and from the currently selected UI chat.
