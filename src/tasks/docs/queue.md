# Durable queue, schedules and reports

Status: current
Owner: src/tasks/

TaskStore owns durable pending/running/terminal rows. TaskRunner claims due work, invokes runtime.runTurn and records the actual outcome. Recovering an orphan or retrying eligible work returns running to pending; a recurring completion requeues while preserving its session.

Scheduler owns due polling and avoids re-entry. Stop/drain must settle in-flight work before store closure. Schedule math, webhook wake reasons, session metadata and notification destinations are explicit records; UI is not the scheduling engine.

A task can carry its own budget (ATO-1108): `maxCostUsd` and `maxDurationMs` (`task create --max-cost-usd --max-duration`), stored in nullable columns added outside the numbered migrations like `run_owner`, so an older binary sharing the file keeps working. `null` leaves each to `agent.task.*`. The runner passes them to runTurn and adds each run's `spendUsd` to `spentUsd` and its running time to `elapsedMs`; a retry or a resume (a restart included) gets only what earlier runs left of both, and a task whose budget or time is used up is blocked instead of run again. A recurring task starts each firing with nothing used. Unpriced (local) models count as $0, so a budget never stops local work. Rules: [budget](../task-budget.ts).

Reports (tasks with `notify`) carry a deterministic run summary collected by the harness from the turn's events, not written by the model: files changed with +/- line counts (`os.fs.write`, `os.fs.edit`, `os.fs.patch` details), shell commands with their last exit code and whether a test command passed, tool and turn errors, approvals that stopped a call, unchecked `- [ ]` items and the questions in the final reply. The report card groups them as Done, Failed and Needs you, next to the step count, the turn's `stopCause` and spend when the turn reports `spendUsd`. The runner snapshots the same collector mid-run for `liveStatus` (Telegram `/status`). A long reporting run also sends that live status to `snapshotSink` on its own every N steps or M minutes counted from the last one (`ATOMIC_AGENT_STATUS_SNAPSHOT_EVERY_STEPS` / `_EVERY_MS`; a short run sends none), and `end(taskId)` once the run is over if any went out ([task-snapshot](../task-snapshot.ts)). Only reporting tasks get a collector; others still pay no per-event cost. Its last-step line names each tool of the step with ok/failed and never quotes `step_finished.summary`, the tail of raw tool output, because `/status` lands in Telegram history. Only reporting tasks get a collector; others still pay no per-event cost.

Quiet hours (`ATOMIC_AGENT_TASKS_REPORT_QUIET_HOURS=23:00-08:00`, local time, default off) wrap the report sink: a report finishing inside the window is held in the `held_task_reports` table of tasks.sqlite (created on open, outside the versioned schema) and every held report goes out as one digest when the window ends (split into a few messages when more were held than one message shows in full, so no report is cut down to its id). A restart keeps them; an undelivered digest stays held and retries.
