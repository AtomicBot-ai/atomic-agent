# Fusion workers

Status: current
Owner: src/tools/fusion/

Fusion delegates bounded task waves to worker turns. Contracts carry deliverables, declared inputs and dependencies; completed providers order later waves even when their task failed. Preserve task status attribution and hand-back based on completed-step progress rather than an independent timer.

Workers are ephemeral: no durable session row/reflection/trace; no recursive delegation or invisible interactive approval. `fusion.delegate` tells a worker by its session depth, as `subagent.run` does (`callerDepth` in [fusion-worker-session.ts](../../session/fusion-worker-session.ts), ATO-1740): a caller at depth 1 or more is refused with reason `recursive-delegation`, its depth read from the stamp of a session this process minted (`readSessionMetadata`), and an `s-w-` id counts as depth 1 even with a missing or broken stamp. Hiding the descriptor from workers only keeps it out of their catalog. Provider pins must not fall over to a different billing/model leg. Declared input replacement remains forbidden. A worker's approval-gated call is refused by its session policy. A fan-out's directory covers its writes and ordinary commands there, never a dangerous command (`shell_dangerous`), the agent's own config or secret files (`trust_config`, `state_secret`), mail, passwords or payments: those are refused with `FUSION_WORKER_OPERATOR_ONLY_REFUSED`, and the task comes back `needs_orchestrator` with a note telling the orchestrator to hand the step to the user instead of re-sending it (ATO-1222, ATO-1223). A fan-out whose write scope lies inside the agent's own state directory (`~/.atomic-agent`) is refused before the operator is asked, and the worker brief says an operator-only refusal is reported, not sent back for a re-send (ATO-1267). In auto mode (approval levels 2 and 3) a fan-out whose directories all sit inside the chat's folder is not asked about, as the chat's own writes there are not; its workers then hold no fan-out scope and run under the standing level, so their writes in the folder go through and a command they run is refused with `FUSION_WORKER_COMMAND_NOT_ASKED_REFUSED`, which makes the next fan-out of the turn ask the operator once, as before. The question stays for a contract with checks or provide examples (they run commands), after a refused command this turn, and on a session that read outside content (ATO-1689). Concurrency is resolved from the call, task count and serving slot capability, rather than blindly capturing startup state.

After a local worker is cut off (time limit, queue wait, hand-back or operator cancel), the next local dispatch first asks the server `GET /health` ([local-leg-health.ts](local-leg-health.ts), ATO-917); a server that does not answer fails the task at once with a restart hint instead of letting it wait out its budget. A server that does answer gets the worker on fresh connections: the process's HTTP pool is swapped for a new one first (`renewTransportPool`, ATO-1357), the part of an agent restart that cleared the field case, while requests already in flight keep their sockets. `subagent.run` gets the same check and renewal for a local leg, with its own mark per tool (ATO-2430). A worker that still gets no token while `/slots` shows every slot idle is told the request got stuck on the agent's side, not to restart the server.
Worker spend is priced per completion with the prompt-cache discount (`estimateUsageCostUsd`, ATO-918). With `llm.runMode.fusion.turnBudgetUsd` / `turnTimeBudgetMs` set, [turn-budget.ts](turn-budget.ts) caps a fusion turn (ATO-947): reset at the turn's start, checked before a delegation, before each worker starts and on every worker completion; reaching it stops running workers and returns a plain-words instruction to the orchestrator. Unset, none of it runs.

[failure-breaker.ts](failure-breaker.ts) stops a fan-out that keeps failing the same way (ATO-1406): one blocker (tool-call protocol mismatch, CLI missing or signed out, out of credit) or `REPEAT_FAILURE_STREAK` identical failures in a row on a leg, and no new task starts there; running workers finish. Trips are kept on the turn's `FusionTurnBudget`, and a later delegation is refused on a leg that hit a blocker, or after the same repeat stopped two rounds. The same state counts rounds and tasks against `maxRoundsPerTurn` / `maxTasksPerTurn` (defaults 6 / 48, `0` off), checked before the fan-out's approval; the approval line names the round and the task count. Both need the runtime's per-turn `turnBudget`.

[worker-fit.ts](worker-fit.ts) checks a task's size against its worker's limit (ATO-1363): a task may state `outputTokens` or `outputLines` (optional, bounded; lines count as 10 tokens). On a local worker leg with a measured speed, tokens / tok/s × the workers running at once over the task's time limit puts a `fit:` warning on its row and the task still runs. Nothing is ever refused on an estimate: a task that, even running alone, needs more than the longest limit a task may ask for is dispatched too, with a split-it warning on its row, a note to the planner in the result and its id in `details.oversizedTasks`. Speed unknown: no check. The estimate also sizes the worker's time limit when it is bigger than the per-file guess (`estimateWorkerTimeoutMs`), and every task that carried an estimate gets an "Estimates vs actual" line (tokens out, time) in the result and `details.estimates`. The `### fusion` block states a local worker's step budget and time limit.

[leg-speed.ts](leg-speed.ts) measures what each leg really generated (ATO-1583): a task that ended `ok` contributes its output tokens over the time the model spent producing them (the collector sums, per completion, the server's decode time or else the request's wall time; tool runs and checks between completions do not count; at least 1 s), summed per leg and model for the turn on the turn budget's state (reset at the turn's start). The result closes with "Measured speed this turn: local qwen 6.1 tok/s (2 tasks), cloud … 48 tok/s (1 task)", and the outcome row carries `tokensPerSecond`. It rides the result, not the `### fusion` block: that block is cached stable prefix and must not move per task. Nothing measured: no line.

[cost-estimate.ts](cost-estimate.ts) forecasts a task's cost on a priced leg before it is sent (ATO-1585), from its output estimate, its brief length and the leg's price: each step resends a 4,000-token frame plus the brief and what was written so far, the output takes one step per 800 tokens (1 to 60), the prefix seen once is billed at the input rate and repeats at the cache-read rate. Local legs, unpriced models and tasks without an output estimate get nothing. The row then reads "cost: ≈$0.04 est, $0.05 actual" and `details.costEstimates` holds both numbers. Advisory only: nothing is refused on it.

[critical-path.ts](critical-path.ts) closes every result with the fan-out's critical path (ATO-1586), as Kimi reports it: the longest chain through the contract's `requires → provides` dependencies, each task weighted by its working time (duration minus queue wait); the sum of all tasks' working time; and on a local leg the idle slot time (slots in use × wall time, minus the local tasks' work). "Critical path 14m (tasks a → c → f), total work 31m, idle local slot 6m." Also in `details.criticalPath`. Report only; tasks carried over by a resume are left out.

[escalation.ts](escalation.ts) escalates a stuck worker (ATO-942): with `escalation: "advisor"`, the first stall or cut first answer asks `ResolvedRunMode.escalation` (a configured provider other than the worker leg) for a hint at most `ADVISOR_MAX_OUTPUT_TOKENS` long, refused when its worst case is over `escalationMaxUsd`, and steers the worker with it. A later stall re-runs the task on that model only with `escalationReplace`. `FusionLiveWorkers` exposes the person's stop / escalate / steer per running worker (ATO-66, ATO-568), keyed by parent session and task id; a person's note rides the shared steering inbox under the worker's ephemeral session id and is read at its next step boundary. `src/http/route-fusion-workers.ts` puts the same three calls on HTTP for the desktop. Escalation spend is added to the turn's cap and reported per row and per fan-out.

[contract-example.ts](contract-example.ts) runs a provide's optional `example` (ATO-1362): `{ call, expect, page? }` becomes one more `verify.run` spec after the declared `checks` (a page probe for browser code, else `node` loading `in`), attributed to the provide's task, so a result that does not match what the contract declared fails that task at acceptance. No example, no extra run; one with nowhere to run is a contract warning.

[judge.ts](judge.ts) is the trimmed judge (ATO-944, `judge: "on"`): an acceptance list per task, rendered read-only into its brief (`briefSuffix`); after the waves, facts (check outcomes, provide presence, declared files) decide their items and can only be red or green on their own; a fresh-context judge (no transcript; files, or the reply when no file was declared) rules on the rest, and only a literal `pass: true` passes. A red list re-runs the task once with the findings; the contract is re-evaluated on the retried rows only. Unreadable or impossible judging leaves the task `needs_orchestrator`, never `ok`.

[replan.ts](replan.ts) is automatic replanning (ATO-941, `autoReplan: N`): dependents of a provider that did not close are held (`not started: held for the replan`), attempts per task are counted per turn in `FusionTurnBudget`, and `details.replan` lists pending and exhausted tasks; `src/agent/fusion-replan.ts` holds the planner's next step to `fusion.delegate` while any are pending, for at most two steps without a fan-out.

[role-models.ts](role-models.ts) is models by role and node (ATO-943): `llm.runMode.fusion.roles` maps `plan / build / review / explore / utility` to configured providers, and `llm.runMode.fusion.roleModels` names the model each role asks its provider for, so one entry (an OpenRouter key, say) can serve several roles with a model each. A leg is a provider plus its wire model (`legKey`): two models on one entry run as two legs, each with its own price and group. Without `roleModels` a role runs the model its entry gives it, as before. A task's `model` (must be the worker leg or a role model, else the call is refused) wins over its `role`, which wins over the worker leg. Each leg's tasks run as their own group (cloud cap for a cloud leg, one at a time on a second local server), priced, counted in the turn's cap, and the row carries `model` / `modelRole`. A second llama-server model is used only with `mixLocalModels: true`; otherwise the task runs on the worker leg and its row says so. `review` is the judge's model when `judgeProvider` is unset; `plan` does not switch the orchestrator. The `### fusion` block lists the role models only when some are configured.
[branch-workspace.ts](branch-workspace.ts) and [branch-merge.ts](branch-merge.ts) are branch isolation (ATO-946, `isolation: "worktree"`, default `"off"`): each run of tasks (a wave, a judge's retry) gets a workspace per task plus an untouched base, all from one snapshot of the working directory. In a git repo the snapshot is `git stash create` (HEAD when clean; the working tree, index and stash list are not touched) checked out as a detached `git worktree`, with untracked files copied and ignored directories symlinked; elsewhere it is a folder copy (clonefile on macOS); a tree too large to copy runs in place and every row says so. The worker's session, brief, write scope, declared inputs and declared-file check all point at its workspace (`RunWorkerTasksOptions.taskWorkspace`). After the wave each workspace is merged back in task order, file by file against the base: a file only the task changed is copied in, one the folder also changed is merged with `git merge-file`, anything else is a conflict that leaves the folder's file untouched, saves both sides under `.atomic-agent/fusion-merge/`, turns the row `needs_orchestrator` and returns a `merge-<id>` task in `details.merges` for the planner. A declared input the task removed or cut to under half its lines is refused at merge time. Failed, cancelled, timed-out and queued tasks are not merged. Workspaces are removed (`git worktree remove --force`, `git worktree prune`) in a `finally`, on abort and throw too.
[task-tree.ts](task-tree.ts) is the task tree (ATO-940, `taskTree.enabled`, default off; `maxDepth` 2, hard cap 3; `maxNodes` 24). Workers still never delegate: a worker that may split is told how in its brief and steered once at the half-budget hand-back or a cut first answer (`SPLIT_GRACE_STEPS` more steps), and ends its turn with a fenced `split_proposal`. The delegate validates it with `parseDelegateArgs` plus the depth, node and parent-files caps, namespaces ids as `parent/child`, runs the children through the same runner (turn caps, approval scope, child budgets clamped to the parent's), checks their contract and the parent's declared files, and closes the parent row on them. A refused proposal leaves the task `needs_orchestrator`. `details.taskTree` carries the nodes.
[worker-diffstats.ts](worker-diffstats.ts) is the fan-out's changed files (ATO-1700): each worker keeps the `details.diffstat` of its ok `os.fs.write` / `os.fs.edit` calls on its row (`diffstats`, one row per path, counts summed), a workspace task's paths are rebased to the folder after its merge and keep only what the merge wrote, a split parent sums its children's and a judge's retry keeps the first attempt's. `details.diffstats` sums every row, and the chat's `tool_result` frame carries it as `diffstats` (ATO-1701) for the desktop's "Changed files" card. A finished row's list is kept in the run checkpoint, so a row a resume carries over still lists its files (ATO-1756), and after a judge's retry the row lists both attempts' (ATO-2488); a checkpoint written before that has none and loads as before.
[task-profiles.ts](task-profiles.ts) is subagent profiles (ATO-566): a task's `profile` (built-in `explore` / `review` / `research`, or a trusted project's, the user's, the settings' or a plugin's, see [subagent profiles](../../agent-profiles/README.md)) quotes the profile's instructions into the brief, narrows the worker's tools to its allowlist (`workerToolFilterFor`, ANDed with the worker policy) and, when the task named no `model` or `role`, sets the role or model from the profile's `model`. An unknown name refuses the call; `details.profiles` says what was applied. No task naming a profile, nothing is loaded. `fusion.delegate` and `subagent.run` both call the one `loadAndApplyTaskProfiles` (ATO-1743): load for the call's folder, fall back to the built-ins with a logged warning when the loader throws, log the loader's diagnostics, then `applyTaskProfiles`; only the log prefix (`fusion:` / `subagent:`) and the refusal's tool name differ.
[run-checkpoint.ts](run-checkpoint.ts) and [run-resume.ts](run-resume.ts) let a run survive a restart (ATO-617): one JSON file per run under `<stateDir>/fusion-runs/` (not a table: the session store's schema and turn marks are pinned, and a checkpoint write must never fail a fan-out), written after every finished task (row, spend, side-effect tools as they start) and every wave, deleted on a normal end, kept as `interrupted` when the turn was stopped. A file whose process is gone or stopped is offered (`runtime.fusionRuns`, `/fusion` in the TUI) for 7 days. `fusion.delegate { resume: runId }` replays the checkpoint's own arguments: settled tasks are carried (a `cancelled` row is not settled), the rest run, the spend so far counts toward the turn's cap, and a task whose worker called anything outside the file tools and reads (`toolHasSideEffects`) is not re-run until `confirm: [taskId]`. Desktop has no offer yet.

Privacy Shield (ATO-1083, `privacy.shield.enabled`): masking happens per provider, not per role. The cloud planner, cloud workers, a cloud judge and a cloud advisor go through `OpenAiProvider` and send placeholders (`[EMAIL_1]`); a local worker (llama-server, or a server on this machine or the local network) gets the real text. A worker's ephemeral session uses its chat's vault (`linkPrivacyVault`, set in `createEphemeralSession`), so the planner and its cloud workers share placeholders and "masked N" counts a value once per chat. Placeholders the planner writes into `fusion.delegate` arguments are unmasked before the delegate runs, so every brief carries the real values and each leg decides what leaves the machine ([privacy shield](../../privacy/README.md)).

A later wave's CONTRACT block carries what the waves before it did (`completedWaveNotes` in [contract-waves.ts](contract-waves.ts)); for a delivered task that is its reply's `PROVIDED:` list, the names and paths it really exposed, renamed ones included (ATO-945), else the head of its reply.

[outcome-log.ts](outcome-log.ts) and [outcome-summary.ts](outcome-summary.ts) are the planner's memory of this machine (ATO-949): every finished worker task appends one JSONL row to `<stateDir>/fusion-outcomes.jsonl` with counts and labels only (leg, model, role, a size bucket from brief length and declared files, status, time, steps, writes, output tokens, priced spend). Never the brief, title, task id, paths, errors or reply. Past 512 KB the file is rewritten with its newest rows (at most 2000, at most half the cap). The newest 300 rows are summarized into the `### fusion` block's last line once per session (the first step of each session reads the log; the summary is then held for that session), "Past runs here: …": one fact per (leg, model, size) group with at least 3 judged tasks (`cancelled` and `queued` are not judged), failing groups first, at most 6. Held per session because those bytes sit in the cached stable prefix; a new chat in the same long-lived process sees the rows appended since. `llm.runMode.fusion.outcomeJournal: false` (default `true`) writes no rows and states no summary.

[worker-question.ts](worker-question.ts) is a worker's question (ATO-945): there is no blocking call to the planner (its turn is inside `fusion.delegate`), so a worker that cannot do its task right without an answer ends its own turn with a `NEEDS_INPUT: <question>` line. The task comes back `needs_input` with `question` (at most 300 chars) on its row and a note telling the orchestrator to answer it and send the task again; its declared files are not checked, a failing check does not turn it `failed`, the breaker treats it like a finished task, a dependent is warned it did not deliver, and `autoReplan` keeps it open.

[worker-workspace.ts](worker-workspace.ts) decides whether a worker gets its own workspace view (ATO-1601). A cloud worker always inherits the parent's. A local worker reads the skill registry, built for the folder the agent started in; once the session moved to another folder, it gets a local workspace view instead (`prepareWorkspace(session, cloud = false)`), so its catalog lists that folder's skills, through the same project-trust gate, and no project instruction files.


## Shared runner core and Fusion add-ons

[worker-runner-core.ts](worker-runner-core.ts) splits the runner's dependency and option types in two (ATO-1669). The core (`WorkerRunnerCoreDeps`, `WorkerRunnerCoreOptions`) is what any delegated worker needs: its own ephemeral session and the guard against the parent's id, events and progress into the parent's frame, the approval policy and write scope, step and time limits, the combined cancellation signals, the turn itself, the result row and its statuses, and the stall check with its early hand-back. The add-ons (`FusionWorkerRunnerDepsExtras`, `FusionWorkerRunnerOptionsExtras`) are Fusion's: escalation, slot and queue watchdogs, local server health and connection renewal, contract and declared inputs, the turn's spend and cap, the task tree, worktree isolation, the judge's brief suffix, generation speed limits and the run checkpoint's observers. Every add-on is optional and does nothing when absent, so `runWorkerTasksCore` is `runWorkerTasks` with those fields empty. `WorkerRunnerDeps` and `RunWorkerTasksOptions` stay as core plus add-ons. The worker turn's `origin` comes from the options, default `"fusion"`; `"subagent"` is treated like `"fusion"` by the runtime. [worker-tool-policy.ts](worker-tool-policy.ts) is already shared.

`subagent.run` ([subagent-run.ts](../subagent/subagent-run.ts), ATO-1670) is the first caller of the core outside Fusion: a turn that is not in Fusion hands tasks (at most `SUBAGENT_MAX_CHILDREN_PER_CALL` = 4 per call, `SUBAGENT_MAX_CHILDREN_PER_TURN` = 24 per turn) to worker turns on its own model, under the `subagent` origin, with the worker policy, a profile's allowlist and a session depth one below the caller (`WorkerRunnerCoreOptions.depth`). Only a depth-0 session may call it (`SUBAGENT_MAX_DEPTH` = 1): the depth is read from the caller's session data and a worker id counts as depth 1 even with a broken stamp; both caps go through the task tree's `treeLimitBreach`. The descriptor is hidden while Fusion is effective, and the tool refuses there too. Writes: a task may list `files`; the user is asked once for the call (category `fusion_fanout`), and a yes is a directory grant, not a file list: the subagents may write anywhere in the directories of the listed files and in the working directory (`resolveFanoutScope`, `..` normalised first). The grant holds for the turn it was given in only: the tool drops a grant from another turn before reading it, since outside Fusion nothing clears it at turn start. The gate's turn state (the standing answer and the refused command note) is tied to the turn it belongs to (`FanoutScopeRegistry.enterTurn`, ATO-1759): `fusion.delegate` and `subagent.run` of one turn read the same decision, so a subagent call no longer drops a fan-out's answer or note and sends the next fan-out out quiet, and a fan-out never reads a subagent's answer from an earlier turn. Without `files` a subagent's write is refused with `SUBAGENT_APPROVAL_REFUSED`. Spend: under the agent turn's spend ceiling (`agent.task.maxCostUsd` or the turn's `taskMaxCostUsd`, handed to tools as `ToolContext.turnSpend`; not Fusion's `turnBudgetUsd`), every subagent completion is priced with the same resolver Fusion's workers use (no price, as on a local leg, is $0) and added to the turn's spend; once the ceiling is reached no further subagent starts (`not started: ...`), a running one is stopped through its signal (`stopped by the turn's cap: ...`), and the loop's own check before the next step sees the total. No ceiling set: nothing of this runs. The cap is soft, like Fusion's turn cap: spend is counted as each completion lands, so subagents already running can overshoot it by up to one completion each before they are stopped. A call made once the ceiling is reached is refused up front (reason `cost-ceiling`), before any approval question and without counting toward the per-turn cap; a cloud leg with no price (cloud as the session readout decides it: not `llama-server`, not on a local server URL) says on its rows that the ceiling was not applied to it. The output says work was stopped only when the ceiling cut or held back a subagent; a run that finished with its last completion crossing the ceiling only notes that the budget is now reached.

What `fusion.delegate` and `subagent.run` share today (ATO-1671): the runner (`runWorkerTasks` is `runWorkerTasksCore` with Fusion's add-ons filled in, so a Fusion worker is a subagent turn plus those add-ons), the worker tool policy, the depth guard (`callerDepth`, ATO-1740; a Fusion worker is stamped depth 1 like a subagent), the profile step (`loadAndApplyTaskProfiles`, ATO-1743), and the write question (`resolveFanoutScope`, `scopeInsideStateDir`, `describeFanoutPreview`, category `fusion_fanout`). What stays Fusion's own: the run mode check, contract waves and checks, the judge, role legs and escalation to another model, slot and queue limits, the turn budget, the task tree, worktree isolation and the run checkpoint.
