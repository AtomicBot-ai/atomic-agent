# Video generation tool

Status: current
Owner: src/tools/video/

`video.generate` makes a short clip through Atomic Chat Core's video jobs (`src/local-llm/core/core-video.ts`: `POST /diffusion/video/jobs`, polled, cancelled on abort) on OpenRouter with the user's key (registered with Core per call by `registerOpenRouterMedia`, never through Core's environment), and copies the file into the session's working folder as `video-<timestamp>.mp4`; the agent shows it with `reply.attachments`. The default model is Core's catalog default (`google/veo-3.1-fast`). The tool never switches models on its own (owner decision: prices differ): when the model is busy upstream (429/502, "busy"/"overloaded", nothing billed) the call ends with an error naming up to three catalog models that can take the clip, and the agent asks the user; only a `model` the user names changes it. `image.generate` keeps its one-step fallback. The default length is 4 seconds, because OpenRouter bills video by the second. `image` (a first frame for image-to-video) is read-scoped like any read and checked to be a picture before asking.

It always asks below approval level 3 (`paid_generation`), and the question says that stopping does not cancel the charge: OpenRouter has no cancel for a video, so Esc only stops the waiting. The prompt offers the tool only while an OpenRouter key is configured (`GATED_TOOLS.video`). Progress reaches the tool card as `tool_progress` events, at most one every 20 seconds. Analytics: `video_generated` with model, clip length and outcome only.

## HTML to MP4

`video.render_html` (ATO-1164) records an HTML page to an `.mp4` in the working folder, for free and without the cloud: `path` (an `.html` file in the working folder, read-scoped like any read) or `html` (inline markup), plus `duration` (default 5 s, max 60), `fps` (default 30, max 60), `width` × `height` (default 1280×720, each side 64 to 1920, at most 1920×1080 worth of pixels, odd sides rounded down) and an optional `output` name. At most 1800 frames per call. The parser (`render-html-args.ts`) owns the bounds.

Frames (`render-html-frames.ts`): a headless Chromium-family browser found like `verify.run`'s page runs (`defaultBrowserLauncher`: `browser.executablePath` / `channel`, else the first browser found, else a Playwright-managed Chromium). Playwright's page clock is installed and paused before the page loads, so `Date`, `performance.now`, timers and `requestAnimationFrame` only move when the tool moves them, by one frame (`round(i * 1000 / fps)` ms) before each screenshot. CSS animations, transitions and Web Animations run on the document timeline, which the clock does not touch, so before each screenshot every animation is paused and seeked to the frame's time, counted from the frame it first appeared in. Not controlled: `<video>`, GIFs, and WebGL or canvas code that reads the real time some other way.

Assembly (`render-html-ffmpeg.ts`): the `ffmpeg` binary on PATH, the same one the `ffmpeg` starter skill uses; never downloaded. PNG frames go to its stdin (`image2pipe`), out comes H.264 yuv420p with `+faststart` and `-n` (never overwrite). `ffmpeg -version` is checked before the browser starts; a missing ffmpeg or browser ends the call with how to install it. A failed or cancelled run kills ffmpeg and removes its half-written file (always a new path). The output is a new file inside the working folder, never an existing one, and the call asks like a file write (`categorizeFsMutation("write")`: silent inside the workspace from level 2). It is a `rare` tool, not gated: it is found through `tool.view` / `tool.search`. Progress reaches the tool card as `tool_progress`, at most one every 2 seconds.
