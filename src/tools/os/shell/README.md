# Shell execution and detached jobs

Status: current
Owner: src/tools/os/shell/

This area owns the implementation of `os.shell.run`, including its command, jobs, wait and kill forms. Read the inherited [tool instructions](../../AGENTS.md) and [tool contract](../../docs/contracts.md) before changing dispatch behavior. Registration stays in the [OS registry](../index.ts).

## Code and resource owners

- [shell.ts](shell.ts) validates calls, chooses direct argv or subshell execution, requests approval through the existing guard policy and handles timeout/abort outcomes. [shell-interpretation.ts](shell-interpretation.ts) owns argument coercion, interpretation decisions and the approval preview, which quotes direct-exec argv the way the platform shell would need it and shows a subshell line exactly as it runs; [expand-shell-glob-args.ts](expand-shell-glob-args.ts) expands supported structured argv globs. Shared user-path expansion stays in [expand-home.ts](../expand-home.ts).
- [shell-timeout.ts](shell-timeout.ts) resolves explicit/default timeouts and renders notices. A default timeout can detach a still-running command; an explicit timeout expresses a kill bound. Preserve that distinction when touching orchestration.
- [wait-watching-for-prompt.ts](wait-watching-for-prompt.ts) waits in slices and, through [interactive-prompt.ts](interactive-prompt.ts), catches a command that went quiet at a person-only step (ATO-1252): a sign-in (device code, browser consent) is kept as a job with the link and code in the result; a password or terminal question is stopped. A failed command whose output shows sudo or a missing terminal gets the same "this step needs the user" line. `background: true` watches a command for 3 s and hands it back as a kept job (dev servers, watchers). Both paths run after the guard and approval, never instead of them.
- Commands also get [the toolchain environment](../../../sandbox/command-toolchain-env.ts) on top of the filtered one: fixed non-interactive switches (`HOMEBREW_NO_AUTO_UPDATE`, `DEBIAN_FRONTEND=noninteractive`, `PIP_NO_INPUT`, `npm_config_yes`, `GIT_TERMINAL_PROMPT=0`; never `CI`) and the existing system (`/etc/paths`), Homebrew, nvm, pyenv and cargo folders, appended after the inherited PATH. The login shell is never run for its PATH: it would source rc files the agent can write.
- [shell-jobs.ts](shell-jobs.ts) owns per-session records and ceiling timers around sandbox CommandJob instances. Runtime bootstrap injects its registry and calls endTurn/endSession/endAll; kept jobs survive turn end, but not session/shutdown/ceiling cleanup. Embedders that omit a registry get the documented private-registry behavior.
- [shell-job-calls.ts](shell-job-calls.ts) handles job lookup, wait, kill, collection and detached-result rendering. IDs are scoped to the session that started the job. An unknown id says which ids exist now and not to poll again (ATO-1259).
- Call shapes (ATO-1259): `command` / `cmdline` / `commandLine` / `command_line` are read as `cmd` ([shell-aliases.ts](shell-aliases.ts), through the registry's alias reading, never over a given `cmd`); an argv in `cmd` is program plus arguments; a call with no `cmd` is read back from `args` when unambiguous (`[program, ...]`, or `["-c", line]`; on Windows only a line with no POSIX-only syntax, run under `cmd.exe /c`), otherwise it gets one line with an example built from the keys it sent ([recover-missing-cmd.ts](recover-missing-cmd.ts)). Arguments a provider streams as a JSON object instead of a string are kept (`src/llm/provider/openai/parse-sse-chunk.ts`).
- `until` (ATO-2358, [shell-job-until.ts](shell-job-until.ts), [shell-job-watch.ts](shell-job-watch.ts)): a case-insensitive pattern. `{wait: id, until}` returns at the first unread output line of the job that matches, at its exit, or when the wait ends; the job is never stopped by it. `{cmd, until}` passes the same guard and approval as a `background: true` command, starts it as a kept job and then watches it. A job's watch starts with every line printed so far and consumes lines up to each match, so a match is reported once; at most 2000 unread lines are held and the result says how many older ones were dropped. It reads output through `CommandJob.onOutput`. Waking an idle session on a match, a `/ps` list and plugin `monitors` are follow-ups.
- `tty: true` and `{write: id, text, eof?}` (ATO-2277, [tty-wrap.ts](tty-wrap.ts), [shell-job-write.ts](shell-job-write.ts)): an interactive kept job whose stdin stays open (`CommandJob.write`), on a pseudo-terminal from the system `script(1)` on macOS and Linux (no native module), on plain pipes on Windows or without `script` (the result says so). Each write passes the guard line by line like a command: a hardline line refuses it, a dangerous one asks as `shell_dangerous`, anything else not marked safe asks as `shell`, a saved deny rule still refuses; nothing is remembered by shape. The write returns what the job printed until it went quiet (0.5 s) or the wait ended (default 2 s, at most 60 s), colour codes removed. A line with `!` or starting with `^` is never taken as safe (an interactive shell's history expansion can rewrite it into another command). `tty: true` is refused in Safe Mode (the macOS sandbox has no pty device, and it is not widened for this). A stop also signals every descendant one by one, since the program under `script` runs in a session of its own. Passwords are not typed: the descriptions say to hand that step to the user. A native ConPTY/node-pty backend and the desktop terminal view are follow-ups.
- [shell-result.ts](shell-result.ts) renders output and exit/timeout observations. [node-check-notice.ts](node-check-notice.ts) explains commands whose successful exit does not establish that every named file was checked.
- Every command spawns with [the filtered environment](../../../sandbox/command-env.ts): provider keys, bot tokens and other secret-looking variables are removed, except the names in `tools.shell.envPassthrough` (passed in as `envPassthrough`; omitted means none). A variable the command line sets itself is unaffected. Skill scripts (`skill.run_script`) get the same filtered environment and the same passthrough list.
- Tool secrets (ATO-476, [shell-secrets.ts](shell-secrets.ts)): `{{secret:NAME}}` in `cmd` or `args` names a secret listed in `toolSecrets` of `<stateDir>/secret-sources.json`. An unknown or malformed name fails the call before any question; a placeholder cannot be the program of a direct command. Such a command always asks, as `shell_secret` (ATO-2530; label "command · uses a secret", level 5, never granted; a dangerous one keeps `shell_dangerous`; no grant or shape covers it), with the placeholder in the preview and the names in the reason. Only after approval is the value fetched and put into the argv that is spawned; the result, details, jobs and trace keep the placeholder, and the value is masked in the output by exact text plus its base64, base64url and URL-encoded forms; a transform the command applies itself (`rev`, one character per line) is not hidden, and the approval card says "masked in output (exact value)". If the filled command reads differently to the guard, it is refused. The same contract (shared steps in [tool-secret-use.ts](../../tool-secret-use.ts), ATO-2530) covers `os.http.request` header values, `skill.run_script` args and env, `verify.run` commands and env, and a stdio MCP server's configured `env` (filled in at spawn, no per-call question); see the READMEs of those areas.
- Commands that drive a web browser are refused before the guard, at every level (ATO-1260, [browser-bypass.ts](../shell-command-guard/browser-bypass.ts)): AppleScript/JXA naming a browser, opening a URL or synthesising System Events input; `open`/`xdg-open`/`start` (also under `cmd /c`) handing a URL, a web file or an operand only known at run time (`open "$(python3 x.py)"`, a variable, ATO-1468) to a browser; a browser binary with arguments; DevTools, `webbrowser`, Shortcuts, decoded command lines. Wrappers (`sh -c`, `env`, `xargs`, `find -exec`) and script files the command runs are read too. Quitting or starting a browser app still runs. The browser tool asks before submits and secrets; the shell cannot.
- A command the guard's dangerous layer matched (`dangerous.*`: `rm -rf`, `git reset --hard`, a force push, a push that deletes or mirrors remote branches, `git checkout -f`, `git switch --discard-changes`, `git stash drop`/`clear`, `git clean` with `clean.requireForce` off, `xargs rm`, a git option, subcommand or program only known when the line runs (`--$m`, `$(echo -f)`, `git $S`, `$g push`), a git alias or a command-running key set on the line or saved (`-c alias.*`, `-c core.sshCommand`, a `-c` key from a variable, `--config-env`, `GIT_CONFIG_*` anywhere on the line, `git config alias.* …`; `core.pager` and `core.editor` stay ordinary), `sudo`, `bash -c` anywhere on the line, `eval`; ATO-1263) asks as `shell_dangerous`, with no command shape: silent only at level 5, never granted for the session, so neither a `shell` grant nor an `[a]` grant on `git` covers it (ATO-1220). The TUI's shell grant buttons say "(risky commands still ask)".
- A credential read (`dangerous.read_credentials`: `cat`, `less`, `head`, `tail`, `cp`, `scp`, `tar`, `zip`, `base64`, `curl -F @…` and other readers of a `SECRET_HOME_PATHS` folder such as `~/.ssh`, `~/.aws`, `~/.config/gcloud`, or of a `.env` file; macOS/Linux paths only; a `cd` on the line, variables set on it and globs are followed, and `python -c`, `node -e`, `ssh-keygen`, `openssl`, `dd`, `source`, `ln`, `find` count a literal credential path anywhere on the line) and an encoded command (`dangerous.encoded_exec`: `base64 -d`, `xxd -r`, `openssl … -d` or a run of `\xHH` escapes piped or substituted into `sh`/`bash`/`python`/`node`/`eval`) carry a `confidence` (`arg-scan-finding.ts`, ATO-2126). At or above `ASK_EVERY_LEVEL_CONFIDENCE` (0.7) the verdict sets `askEveryLevel` and the gate asks even at level 5 (bypass), like hardline but asking instead of blocking. A project `.env` and `~/.ssh/config` score 0.6: they ask as ordinary `shell_dangerous` and stay quiet in bypass. Template env files (`.env.example`, `.env.sample`, ...), public keys and `known_hosts` are not findings. Every other `dangerous.*` verdict has confidence 1.
- `verify.run` starts commands too (kind `command`, a service's or a page's `start`), so each one passes the same guard first (`src/tools/verify/verify-run-guard.ts`, ATO-1266): a hardline or policy match refuses the call before anything runs, a `dangerous.*` match asks as `shell_dangerous` and is never covered by a fan-out scope. Its throwaway copy is not a sandbox.
- A command naming one of the agent's own secret files (`.env`, `config.json`, local server keys in the state directory) asks as `state_secret` before it runs, at every level below 5, through [the read-scope wrapper](../../read-scope/state-secrets.ts); a `shell` grant never covers it. Best-effort: a path built at run time is not seen.

The existing [shell-command-guard](../shell-command-guard/index.ts) owns command classification, normalization and policy rules. It is shared with agent verification command classification and remains a separate owner. Approval owns grants and interaction; sandbox owns process execution. This directory does not own runtime shutdown ordering or configuration defaults.
