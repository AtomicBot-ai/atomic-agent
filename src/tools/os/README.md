# OS tools

Status: current
Owner: src/tools/os/

The registry wires filesystem, shell, web, git, process and document tools. Preserve dispatch approval, read scope, declared-input protection, restore manifests and detached shell-job semantics. Paths are resolved relative to workingDir with supported home expansion. Project location resolution searches known project sources; it is not an unrestricted arbitrary-disk scan.

Web search/fetch has provider-specific extraction, challenge detection and HTTP retry/timeout boundaries. Reading a page and browser interaction are different operations; do not silently substitute navigation for text retrieval. SSRF and response limits belong to dispatch/transport guards.

Read [tool instructions](../AGENTS.md), [contracts](../docs/contracts.md), [OS registry](index.ts), [fetch](web/web-fetch.ts), [search](web-search/index.ts), [project location](fs/fs-locate-project.ts), and [shell](shell/shell.ts). Tests live beside each tool; run affected tools/os tests and the resource-class/schema completeness tests for catalog changes.

## Operation owners

- [Filesystem](fs/README.md): operations, input/read/approval guards, restore store and project location.
- [Shell](shell/README.md): execution, timeout/detach and job registry; existing [command guard](shell-command-guard/index.ts) retains policy rules and its adjacent test.
- [Web/HTTP](web/README.md): fetch/extraction/challenges/SSRF and request transports; [web search](web-search/index.ts) retains provider orchestration and consumes shared HTTP helpers.
- [Code map](code-map/code-map-tool.ts): `os.fs.code_map` (ATO-652), a read-only, token-budgeted outline of a project (files ranked by cross-file references, PageRank over identifier mentions) or the skeleton of one file. The default parser is the dependency-free [regex backend](code-map/regex-outline.ts) for TS/JS, Python, Go, Rust and Java; a [tree-sitter backend](code-map/tree-sitter-outline.ts) is used only when `web-tree-sitter` can be imported and `ATOMIC_AGENT_TREE_SITTER_DIR` holds grammar WASMs, and falls back silently otherwise. Outlines are cached per file by mtime and size. The walk reuses `os.fs.glob`'s default ignore list and a walk budget; the path is read-scoped like other reads.
- [Structural code tools](code/index.ts): `os.code.search` and `os.code.rewrite` (ATO-696) run the user's own `ast-grep` CLI ([resolver](code/ast-grep-resolver.ts): `ATOMIC_AGENT_AST_GREP_PATH`, then `ast-grep` on PATH, on Windows only a real `.exe`, following npm's `.cmd` shim to the native binary beside it; nothing is bundled, a missing binary is an error that says how to install it). ast-grep only finds and computes replacements ([its JSON](code/ast-grep-json.ts)); [the rewrite](code/code-rewrite.ts) applies them itself on the file bytes, previews a diff by default and writes through the fs write funnel: one approval, all files or none, masked-secret refusal, stale-read notice, replace guard and parse/content warnings, like `os.fs.patch`. Every run gets `--config` pointing at an empty sgconfig in the temp folder and a cwd outside the project, so a repository's own `sgconfig.yml` (which can name a native `customLanguages` library) is never read. Both paths are read-scoped.
- [Media text](media-text/media-text.ts) (ATO-1051): text out of photos and audio for the [file index](../files/README.md) (ATO-1621). Not a tool; the index calls it per photo or audio file, off unless the caller passes `enabled: true` (the runtime does while `vision.indexFiles` is on, ATO-2501). Photos go to the vision model `vision.describe` uses (`LlmProvider.describeImage`), asked to copy out the visible text; no separate OCR engine. Audio reuses the whisper.cpp pieces of [`audio.transcribe`](../audio/README.md) (binary and ffmpeg lookup, argv, models in `<localModelsDataDir>/whisper/`, default `base`); a model not on disk is fetched only with `allowModelDownload: true`, otherwise the result is `skipped: needs-model-download` with its size and URL. A missing vision model, whisper.cpp or ffmpeg is a `skipped` result with a reason, not an error. [Vision OCR engine](media-text/vision-ocr-engine.ts) (ATO-2205): the `OcrEngine` for scanned PDF pages over the same vision model; each page's largest image is pulled out with pdfjs ([page images](read-document/extractors/pdf-page-images.ts), no canvas), shrunk to 2000 px and sent as PNG with a copy-the-text prompt.
- [Office files](office/index.ts): `os.fs.docx` (create from blocks, append, find-and-replace across split runs in body, headers and footers; OOXML written directly with `jszip`) and `os.fs.xlsx` (create, write rows with `=` formulas, `bold`/`numFmt`, read a range with formulas; on `exceljs`, workbooks saved with `fullCalcOnLoad`). Writes go through the fs approval funnel and the restore store (`office-write.ts`), atomically via a temp file; reads of an existing file are read-scoped (ATO-541). Reading text stays `os.fs.read_document`. An ok write's `details` carry the absolute `path` and `change` (`created` or `updated`, as on disk after the approval), and `os.fs.write_pptx` does the same; the HTTP stream copies them onto the `tool_result` frame as `office_file: {path, change}` ([frame](../../http/office-file-frame.ts), ATO-2518) for the desktop's "Changed files" card, since a .docx has no line counts for a `diffstat`.
- [Language-server navigation](code/code-lsp.ts): `os.code.lsp` (ATO-2373), registered only with `tools.lsp.enabled`, asks the language server of the file's work tree for a definition, references, hover or symbols ([requests and answer parsing](fs/lsp/lsp-navigation.ts)) and answers one `path:line:col: code` line per hit, capped ([format](code/code-lsp-format.ts)); a hit outside the read scope shows no code. It uses the after-edit diagnostics' [server pool](fs/lsp/lsp-server-pool.ts): servers only from PATH, only inside a git work tree, one start question per untrusted work tree. A core tool in tool-search mode while it is on.
- Existing [archive](archive/index.ts), [document reading](read-document/index.ts), [git](git/README.md) and [process tools](proc/index.ts) retain their owners.
- [PowerPoint writing](pptx/index.ts) (`os.fs.write_pptx`) builds an editable deck in-process with JSZip and rides the `os.fs.write` approval funnel; its round-trip test reads the deck back with the PPTX extractor. Each slide gets a [layout](pptx/pptx-layout.ts) (title, bullets, two-column, quote, big-number, image-full, chart, and since ATO-2444 section, comparison, timeline, table), named by the model or picked from its content, and bullets that do not fit move to the speaker notes ([renderers](pptx/pptx-layout-render.ts), [more](pptx/pptx-layout-render-extra.ts)). What fits is measured, not counted ([fit](pptx/pptx-text-fit.ts), [widths](pptx/pptx-text-measure.ts)): each bullet wraps at its layout's text-area width with per-character widths at its level's size and indent, and the paragraphs stack against the area's height; the old bullet counts stay as the upper bound. A comparison fits each side in its own column, its sub-points at the lifted level they are drawn at, and falls back to plain bullets when a side keeps no points. Each slide is reported as it is laid out, before the approval prompt (ATO-2444, [progress](pptx/pptx-slide-progress.ts)): the agent's `tool_progress` event carries `slide` (index, count, layout, clipped title, subtitle and first bullets (both sides of a comparison), visual, moved, theme, accent), the HTTP stream sends it on `tool_update`, the desktop draws a thumbnail per slide and the terminal shows one feed line each.

Root index intentionally composes and exports registrations in the previous order. Clipboard/email/notify/window platform tools and expand-home remain root operations/shared path support; they do not acquire filesystem/shell/web state. Tool names, descriptors, schemas and agent resource classes are unchanged.

## Screen control (macOS; screenshots on Windows and Linux)

[`screen/`](screen/index.ts) owns `os.screen.capture`, `os.screen.click`, `os.screen.type` and `os.screen.key` (ATO-525), plus `os.screen.elements` and `os.screen.press` (ATO-998, ATO-530). They are opt-in: registered, and kept in the prompt, only when `tools.screen.enabled` is `true` (default `false`, read at start) and the host is macOS. On Windows and Linux the same switch registers `os.screen.capture` alone (ATO-527, see below); click, type, key and point stay macOS-only. No new dependency: `screencapture` and `sips` make the picture, one constant JXA program (`osascript -l JavaScript`) posts CoreGraphics mouse and keyboard events. What it acts on travels as JSON in `ATOMIC_SCREEN_PAYLOAD`, never spliced into script source, and the child gets an allow-listed environment.

- Capture saves a JPEG under `<tmp>/atomic-agent-screens/<session>/` (outside the working folder), long side capped at 1280 px, and reports the image-pixel-per-point scale (and region origin). It asks as `screen_capture` (silent from level 3, like `http`; grantable per session), with a preview naming the frontmost app. Tool results are text, so a model sees the picture through `vision.describe` on that path; a model that cannot see gets `vision.describe`'s usual refusal. A Screen Recording grant missing (`CGPreflightScreenCaptureAccess`) or an empty capture returns a message naming the host app and the System Settings pane.
- Click takes the image's pixel x,y; the session's last capture maps them back to points (an explicit `scale` overrides it). Type sends text as Unicode key events or (`via: "paste"`) through the clipboard, restored afterwards; at most 2000 characters per call. Key parses chords such as `cmd+shift+t` into ANSI key codes and refuses app, window and space switchers, Spotlight and Force Quit.
- A window snapshot (ATO-532): `os.screen.capture { app?, window?, text? }` captures one app window instead of the display. The probe lists the on-screen windows front to back (`CGWindowListCopyWindowInfo`, normal layer, at least 40x40 points, up to 60); the first whose app name or bundle id matches `app` (exact before substring) and whose title contains `window` is taken with `screencapture -x -o -l <window id>`, so a covered window comes out whole. No match returns the window list, so the model can ask again or let the user pick. It asks as `screen_capture` with a preview naming the window, saves `window-<stamp>.jpg` in the same folder, and remembers the window frame as the capture geometry, so `os.screen.click` works on that picture. `text: true` also walks the window's Accessibility tree through System Events (depth 12, 800 elements, 20 000 characters; password fields are never read) and saves `window-<stamp>.txt` next to the picture; without the Accessibility grant the picture still comes back with a note. A snapshot only looks, so browser and terminal windows may be captured (the same as a full-display capture shows them); windows of the keychain, login and security prompts and password managers ([`screen-window.ts`](screen/screen-window.ts)) are refused. The result tells the model to show the picture with `reply.attachments`; the desktop shows screenshots from this folder in the chat.
- Every input call first probes Accessibility (`AXIsProcessTrusted`) and the target app: the owner of the topmost window under the click point, otherwise the frontmost app. No grant means an actionable error and no prompt. The target is classed by bundle id on every call ([`screen-protected.ts`](screen/screen-protected.ts)), as Claude's own computer use does: the agent's own terminal or desktop app, System Settings, the keychain and login prompts, password managers, script runners and command launchers (Alfred, Raycast, Hammerspoon, Keyboard Maestro; ⌥ Space is refused) take no input at all (a slash command typed into the agent's own terminal would raise its approval level); web browsers (Safari, Chrome, Arc, Edge, Firefox, Brave, Opera, Vivaldi, Chromium, Orion, DuckDuckGo, … and their web apps) are look-only, so a password or a payment goes through the browser tool's `browser_secret` / `browser_commit`; terminals and IDEs (Terminal, iTerm2, Warp, Ghostty, VS Code, Cursor, JetBrains IDEs, …) take clicks but no typing or keys (`os.shell.run` runs commands). A refused or unidentified target is refused at every level without a prompt, with the tool to use instead. Otherwise it asks as `screen_control` (silent from level 4, like `shell`; grantable per session), with a preview naming the action, the screen point and the target app; typed text is shown in full. The action is pinned to the approved app: the script brings it back to the front if the approval UI took focus, re-checks the click owner, and does nothing rather than post input elsewhere.
- `os.screen.point` (ATO-1018) shows the user where to click: up to 8 arrows, boxes or short labels, optionally numbered, in the pixels of the session's last capture (mapped like a click) or in global screen points (`coords: "points"`, any display). It only draws: it never moves the mouse, clicks or types, asks nothing, and refuses input-shaped arguments. It is registered with `os.screen.capture` when `tools.screen.point` is on (default) on macOS, without `tools.screen.enabled`; capture registered that way runs only for a session whose host draws marks, so a terminal, a channel or a scheduled task still cannot take screenshots without `tools.screen.enabled`. The marks travel on `details.screenMarks`; the HTTP stream copies them into the `tool_result` frame as `screen_marks`, and only a stream opened with `X-Atomic-Screen-Overlay: 1` (the desktop app on its own local agent, [`screen-overlay-hosts.ts`](screen/screen-overlay-hosts.ts)) counts as a host. Anywhere else the tool answers that marks need the desktop app.
- `os.screen.elements { app, window?, maxElements? }` (ATO-998 item 2) gives a small model the window as a numbered list instead of pixels, like the browser tool's ARIA refs: `[n] role "name" value="…" (x,y,w,h) actions`, e.g. `[3] button "Save" (812,440,60,24) press`. The same JXA script walks the window's Accessibility tree through System Events (depth 14, 800 elements looked at, 60 listed by default, at most 200) and keeps only controls: buttons, fields, checkboxes, radio buttons, pop-ups, menu items, links, rows, cells, tabs, sliders, and images, texts or groups that answer `AXPress`; zero-sized (hidden) ones are skipped, and a password field is listed without its value. It only reads and asks as `screen_capture`. It is listed only where a press could act: password and login windows are never read (the window-capture list), the blocked apps are refused, and so are web browsers (`browser.read_aria` is the list there). The list, with each element's child-index path, role and name, is kept per session and app ([`screen-elements.ts`](screen/screen-elements.ts)) for the next call.
- `os.screen.press { app, element, window?, value? }` (ATO-530) acts on element n of that list in the background: `AXPress`, or with `value` it sets a text field's `AXValue`. It posts no mouse or keyboard event and does not bring the app to the front, so the user keeps their cursor and focus. Same rules as click and type: a press is a click (refused in browsers and the blocked apps, fine in terminals), `value` is typing (refused in terminals and IDEs too); it asks as `screen_control`, naming the element, the window and the app, with the whole text shown. At action time the script checks the window's process still belongs to the approved app, finds the same window by its title, walks the stored path again and refuses unless the same role and name are there; a restarted app or a changed window means "list again". It never switches delivery mode on its own (the Hermes cua-driver rule): an element without `AXPress`, or a value that cannot be set, is a refusal naming `os.screen.click` / `os.screen.type`, which move the mouse and bring the app forward under their own approval. If the app raises itself in response to the press, the result says so. Like click and type, both are registered only with `tools.screen.enabled`.
- All of them share one serial resource class, so a batched click and capture run in emitted order. Fusion workers never see them: the desktop stays with the orchestrator's turn.
- Windows and Linux (ATO-527, first slice: look only) live in [`screen-capture-win-linux.ts`](screen/screen-capture-win-linux.ts). `os.screen.capture` with no arguments takes the whole screen, every display, as `screen-<stamp>.png` in the same folder; a region, `app`, `window` or `text` is refused there. The program is chosen before the `screen_capture` prompt, so a missing tool costs no question. Windows runs one constant PowerShell script (`System.Windows.Forms` / `System.Drawing` `CopyFromScreen` of the virtual screen), sent as `-EncodedCommand`, with the output path and the 1280 px cap in `ATOMIC_SCREEN_OUT` / `ATOMIC_SCREEN_MAX_SIDE`; it calls `SetProcessDPIAware` first, so a scaled display is captured in physical pixels, and it fails, with a message saying why, on a locked PC, the UAC prompt or a session without a desktop. Linux finds tools with one constant `sh -c 'command -v …'` loop and tries, in order, `grim` (wlroots Wayland), `gnome-screenshot -f`, `spectacle -b -n -f -o` (KDE), then on X11 only `scrot` and `import -window root` (ImageMagick); the next one is tried when one produces no PNG. The size comes from the PNG header, and `magick` / `convert`, when present, shrink it to 1280 px; without them the picture stays full size with a note. GNOME on Wayland blocks all of these (its screenshot API is private and the desktop portal is not used yet): the message says so and suggests a "GNOME on Xorg" session. No graphical session (SSH, a container) is its own message. A finished picture over 16 MB is refused. Every child gets an allow-listed environment. The geometry is remembered in screen pixels like a macOS capture's, but nothing reads it yet: input on Windows and Linux (SendInput, xdotool / ydotool, or `cua-driver` over MCP) is the next slice and needs checks on real machines.
