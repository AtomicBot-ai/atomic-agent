# OS tools

Status: current
Owner: src/tools/os/

The registry wires filesystem, shell, web, git, process and document tools. Preserve dispatch approval, read scope, declared-input protection, restore manifests and detached shell-job semantics. Paths are resolved relative to workingDir with supported home expansion. Project location resolution searches known project sources; it is not an unrestricted arbitrary-disk scan.

Web search/fetch has provider-specific extraction, challenge detection and HTTP retry/timeout boundaries. Reading a page and browser interaction are different operations; do not silently substitute navigation for text retrieval. SSRF and response limits belong to dispatch/transport guards.

Read [tool instructions](../AGENTS.md), [contracts](../docs/contracts.md), [OS registry](index.ts), [fetch](web/web-fetch.ts), [search](web-search/index.ts), [project location](fs/fs-locate-project.ts), and [shell](shell/shell.ts). Tests live beside each tool; run affected tools/os tests and the resource-class/schema completeness tests for catalog changes.

## Operation owners

- [Filesystem](fs/README.md): operations, input/read/approval guards, restore store and project location.
- [Shell](shell/README.md): execution, timeout/detach and job registry; existing [command guard](shell-command-guard/index.ts) retains policy rules and its adjacent test.
- [Web/HTTP](web/README.md): fetch/extraction/challenges/SSRF and request transports; [web search](web-search/index.ts) retains provider orchestration and consumes shared HTTP helpers.
- [Code map](code-map/code-map-tool.ts): `os.fs.code_map` (ATO-652), a read-only, token-budgeted outline of a project (files ranked by cross-file references, PageRank over identifier mentions) or the skeleton of one file. The default parser is the dependency-free [regex backend](code-map/regex-outline.ts) for TS/JS, Python, Go, Rust and Java; a [tree-sitter backend](code-map/tree-sitter-outline.ts) is used only when `web-tree-sitter` can be imported and `ATOMIC_AGENT_TREE_SITTER_DIR` holds grammar WASMs, and falls back silently otherwise. Outlines are cached per file by mtime and size. The walk reuses `os.fs.glob`'s default ignore list and a walk budget; the path is read-scoped like other reads.
- Existing [archive](archive/index.ts), [document reading](read-document/index.ts), [git](git/README.md) and [process tools](proc/index.ts) retain their owners.
- [PowerPoint writing](pptx/index.ts) (`os.fs.write_pptx`) builds an editable deck in-process with JSZip and rides the `os.fs.write` approval funnel; its round-trip test reads the deck back with the PPTX extractor.

Root index intentionally composes and exports registrations in the previous order. Clipboard/email/notify/window platform tools and expand-home remain root operations/shared path support; they do not acquire filesystem/shell/web state. Tool names, descriptors, schemas and agent resource classes are unchanged.

## Screen control (macOS)

[`screen/`](screen/index.ts) owns `os.screen.capture`, `os.screen.click`, `os.screen.type` and `os.screen.key` (ATO-525). They are opt-in: registered, and kept in the prompt, only when `tools.screen.enabled` is `true` (default `false`, read at start) and the host is macOS; Windows and Linux are ATO-527. No new dependency: `screencapture` and `sips` make the picture, one constant JXA program (`osascript -l JavaScript`) posts CoreGraphics mouse and keyboard events. What it acts on travels as JSON in `ATOMIC_SCREEN_PAYLOAD`, never spliced into script source, and the child gets an allow-listed environment.

- Capture saves a JPEG under `<tmp>/atomic-agent-screens/<session>/` (outside the working folder), long side capped at 1280 px, and reports the image-pixel-per-point scale (and region origin). It asks as `screen_capture` (silent from level 3, like `http`; grantable per session), with a preview naming the frontmost app. Tool results are text, so a model sees the picture through `vision.describe` on that path; a model that cannot see gets `vision.describe`'s usual refusal. A Screen Recording grant missing (`CGPreflightScreenCaptureAccess`) or an empty capture returns a message naming the host app and the System Settings pane.
- Click takes the image's pixel x,y; the session's last capture maps them back to points (an explicit `scale` overrides it). Type sends text as Unicode key events or (`via: "paste"`) through the clipboard, restored afterwards; at most 2000 characters per call. Key parses chords such as `cmd+shift+t` into ANSI key codes and refuses app, window and space switchers, Spotlight and Force Quit.
- A window snapshot (ATO-532): `os.screen.capture { app?, window?, text? }` captures one app window instead of the display. The probe lists the on-screen windows front to back (`CGWindowListCopyWindowInfo`, normal layer, at least 40x40 points, up to 60); the first whose app name or bundle id matches `app` (exact before substring) and whose title contains `window` is taken with `screencapture -x -o -l <window id>`, so a covered window comes out whole. No match returns the window list, so the model can ask again or let the user pick. It asks as `screen_capture` with a preview naming the window, saves `window-<stamp>.jpg` in the same folder, and remembers the window frame as the capture geometry, so `os.screen.click` works on that picture. `text: true` also walks the window's Accessibility tree through System Events (depth 12, 800 elements, 20 000 characters; password fields are never read) and saves `window-<stamp>.txt` next to the picture; without the Accessibility grant the picture still comes back with a note. A snapshot only looks, so browser and terminal windows may be captured (the same as a full-display capture shows them); windows of the keychain, login and security prompts and password managers ([`screen-window.ts`](screen/screen-window.ts)) are refused. The result tells the model to show the picture with `reply.attachments`; the desktop shows screenshots from this folder in the chat.
- Every input call first probes Accessibility (`AXIsProcessTrusted`) and the target app: the owner of the topmost window under the click point, otherwise the frontmost app. No grant means an actionable error and no prompt. The target is classed by bundle id on every call ([`screen-protected.ts`](screen/screen-protected.ts)), as Claude's own computer use does: the agent's own terminal or desktop app, System Settings, the keychain and login prompts, password managers, script runners and command launchers (Alfred, Raycast, Hammerspoon, Keyboard Maestro; ⌥ Space is refused) take no input at all (a slash command typed into the agent's own terminal would raise its approval level); web browsers (Safari, Chrome, Arc, Edge, Firefox, Brave, Opera, Vivaldi, Chromium, Orion, DuckDuckGo, … and their web apps) are look-only, so a password or a payment goes through the browser tool's `browser_secret` / `browser_commit`; terminals and IDEs (Terminal, iTerm2, Warp, Ghostty, VS Code, Cursor, JetBrains IDEs, …) take clicks but no typing or keys (`os.shell.run` runs commands). A refused or unidentified target is refused at every level without a prompt, with the tool to use instead. Otherwise it asks as `screen_control` (silent from level 4, like `shell`; grantable per session), with a preview naming the action, the screen point and the target app; typed text is shown in full. The action is pinned to the approved app: the script brings it back to the front if the approval UI took focus, re-checks the click owner, and does nothing rather than post input elsewhere.
- `os.screen.point` (ATO-1018) shows the user where to click: up to 8 arrows, boxes or short labels, optionally numbered, in the pixels of the session's last capture (mapped like a click) or in global screen points (`coords: "points"`, any display). It only draws: it never moves the mouse, clicks or types, asks nothing, and refuses input-shaped arguments. It is registered with `os.screen.capture` when `tools.screen.point` is on (default) on macOS, without `tools.screen.enabled`; capture registered that way runs only for a session whose host draws marks, so a terminal, a channel or a scheduled task still cannot take screenshots without `tools.screen.enabled`. The marks travel on `details.screenMarks`; the HTTP stream copies them into the `tool_result` frame as `screen_marks`, and only a stream opened with `X-Atomic-Screen-Overlay: 1` (the desktop app on its own local agent, [`screen-overlay-hosts.ts`](screen/screen-overlay-hosts.ts)) counts as a host. Anywhere else the tool answers that marks need the desktop app.
- All four share one serial resource class, so a batched click and capture run in emitted order. Fusion workers never see them: the desktop stays with the orchestrator's turn.
