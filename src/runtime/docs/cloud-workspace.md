# Cloud session workspace

Status: current
Owner: src/runtime/

`session.workingDir` is the cloud environment boundary. [session-workspace.ts](../session-workspace.ts) prepares a per-step snapshot before budgeting and compaction. Prompt capabilities, project instructions, the skill catalog and skill dispatch use this snapshot. The first local-to-cloud fallback prepares it before the provider request, on both unary and streaming paths. No shared current-directory setter is involved.

`getSessionWorkspace(sessionOrId)` exposes the cloud view to interfaces; local sessions return null. Preview builds from the requested session without saving. TUI uses its selected session, sidecar `skill_list` uses its active session, and HTTP skills/capabilities accept optional `sessionId`. Calls without a session retain the legacy boot-workspace catalog.

Cloud Fusion parents pass their working directory into ephemeral session creation and result-file validation. Their local workers discover only Atomic project/global skills in that directory, retaining local catalog budgets. Independent local sessions keep their previous discovery and prompt behavior.

## Project instructions

[project-instructions.ts](../project-instructions.ts) loads root `AGENTS.md`, `AGENT.md`, `CLAUDE.md`, and `.claude/CLAUDE.md` before the first action, plus nested copies inside a Git repository, and root rule files written for Gemini CLI, Cursor and Copilot (below). When the session folder is a subfolder of a Git repository, the same four root names are also read from every folder above it up to the repository top (scopes `..`, `../..`, outermost first, so the session folder's own rules refine them). Folders outside the repository, the home directory and its ancestors, and other agents' home configuration are never searched. Every block identifies its source and scope. A `.claude/CLAUDE.md` applies to the directory containing `.claude`; deeper scopes refine ancestors. For conflicts within one scope, precedence is `AGENTS.md` > `AGENT.md` > `CLAUDE.md` > `.claude/CLAUDE.md` > rules written for other tools. Explicit user/system instructions retain priority. Files do not grant permissions.

Every discovered file (not imports) must be trusted for that folder before it is read; a new file waits for the operator's answer and a trusted file cannot import a withheld one. The loader reports what it found so the trust question can count it. See [project folder trust](../../skills/docs/project-trust.md).

Rules written for other tools load from the workspace root only, with the lowest priority (0) and their own source path: `GEMINI.md`, `.cursorrules`, `.github/copilot-instructions.md`, and the top-level `*.mdc` and `*.md` files in `.cursor/rules`. They are never searched in nested folders and never expand `@path` imports. Cursor rule files are read in name order, at most 16 (later ones leave a diagnostic). A Cursor rule loads with the instructions only when its frontmatter sets `alwaysApply: true` or it has no frontmatter; a rule scoped by `globs` becomes a path rule (below); rules picked by `description` or attached by hand are skipped with a diagnostic, since they are meant for specific requests. These files share the same byte and file budgets and come after the other root files in budget order (nested folders still come after them); a file that resolves to an already loaded rule (for example a symlink to `AGENTS.md`) loads once.

### Path-scoped rules (ATO-2247)

Atomic Agent's own rule files are the top-level `*.md` files in `.atomic-agent/rules` at the workspace root (name order, at most 16). A file without `paths:` in its frontmatter is always on: it loads with the instructions, scope `.`, priority 1. A file with `paths:` (or `globs:`), and a Cursor rule with `globs:` that is not `alwaysApply: true`, is a path rule: [project-path-rules.ts](../project-path-rules.ts) reads its patterns (an inline list, a comma-separated value or a YAML block list) and [project-path-rules-load.ts](../project-path-rules-load.ts) keeps its body (without frontmatter, at most 8 KiB, outside the instruction byte and file budgets). Path rules are asked about by the folder trust question like any other file; an untrusted one is not read. A path rule never enters the prompt at the start of a session. [path-rule-sections.ts](../../prompt/path-rule-sections.ts) checks the paths that `os.fs.read`, `os.fs.read_document`, `os.fs.write`, `os.fs.edit`, `os.fs.move`, `os.fs.patch` (the files named inside an inline patch, both formats, relative to `rootDir`; a `patchPath` file is not opened) and `os.code.rewrite` (its `path`, and the files its result lists) calls named in this session ([path-rule-tool-targets.ts](../../prompt/path-rule-tool-targets.ts), ATO-2443): once one matches, the rule is added as a `project-rule:<path>` entry of the cloud context journal (after the conversation, never in the stable prefix) and stays for the rest of the session. A pattern without `/` matches a file name in any folder (`*.sql`); one with `/` matches from the workspace root (`db/**`). Paths outside the workspace never match.

Path rules also apply to local models (ATO-2443), which get no other project instruction files: [session-workspace.ts](../session-workspace.ts) `createPathRulesLoader` reads them through the same discovery and folder trust, and [build-prompt.ts](../../prompt/build-prompt.ts) puts every attached rule in a `### project-rules` section after the conversation (never in the stable prefix), at most 2048 tokens and 5% of a known window, cut with a marker beyond that. The person's own rules for every project are the top-level `*.md` files with `paths:` (or `globs:`) in `<state dir>/rules` (by default `~/.atomic-agent/rules`, [global-path-rules.ts](../global-path-rules.ts), like Qwen Code's `~/.qwen/rules`): no trust question, their patterns match files of the session folder, and a file there without patterns is skipped. When a rule attaches, the step emits `path_rule_attached` once per rule ([step-path-rules.ts](../../agent/step/step-path-rules.ts)): the TUI shows `rule attached: <rule file>` in the chat, the chat-completions stream sends `event: path_rule_attached` {path, patterns} to extension clients (the desktop draws the same line), and `/context` counts attached rules as the `project rules` row (`tokens.projectRules`, local section or cloud journal entries). The line is live only: a reopened chat does not redraw it.

Nested discovery uses Git only: tracked and nonignored files, skipping `.git` and `node_modules`; root names are checked directly, even if ignored. Outside Git, or when Git refuses the folder or times out, only the root files load and nothing below the root is listed. The home directory, any ancestor of it, and any folder in a repository rooted at home (a dotfiles repository) are always root-only, so launching from `~` never reads unrelated projects or opens privacy-protected folders. Symlink files escaping the workspace are skipped. Git discovery has a five-second timeout and a 1 MiB result bound.

Instruction problems never fail a step: an unreadable, special, binary or oversized (over 1 MiB) file is skipped. The total budget is 48 KiB and 64 files, and when the active model's context window is known it shrinks so instructions take at most 10% of the window (estimated at three bytes per token). Budgets keep the most general and highest-priority files (parent-folder files, then root files, with their imports, first) and drop the deepest scopes first; a parent-folder or root file that does not fit keeps its beginning with a visible truncation marker. Cancellation is the only error that leaves preparation. Every skip, cut or truncation leaves a diagnostic with workspace-relative paths; repeated diagnostics are grouped. Missing optional instruction files are normal. Content is never silently clipped.

The runtime workspace loader caches discovery per workspace and budget. A cached result is reused while every file it looked at (the root, root names in it and in parent folders up to the repository top, discovered files and imports, present or missing) keeps its modification time and size, and for at most 30 seconds; after that discovery runs again, so a new nested file appears within that interval.

CLAUDE files expand `@path` imports relative to the importing file, including nested imports up to four hops. Imported blocks inherit the importing scope and priority. Cycles produce diagnostics; repeated paths in the same scope are loaded once. Fenced, indented and inline code are ignored. External, home, missing and non-file imports, imports deeper than four hops, imports Git ignores (or cannot classify; one batched `git check-ignore` per discovery) and secret-looking files (`.env*`, `.envrc`, `.npmrc`, `.netrc`, `.pgpass`, `.pypirc`, `.git-credentials`, `.htpasswd`, `credentials.json`, `application_default_credentials.json`, `kubeconfig*`, `secrets.*`, JSON files whose name contains `service-account`/`serviceAccount`, anything under `.aws/`, `.ssh/`, `.kube/` or `.gnupg/`, `.docker/config.json`, `id_rsa*` and similar keys, `*.pem`, `*.key`, `*.p12`, `*.pfx`, `*.jks`, `*.keystore`, `*.tfvars`, `*.tfstate`, `*.kdbx`) are skipped with diagnostics. `@name` in prose is often a mention or a package scope rather than an import.

Updates and removals enter the existing cloud context journal. Unchanged bodies are not repeated, and mutable rules never enter the stable prefix. Compaction carries only active state; old messages remain historical evidence.

## Project skills

See [cloud skill discovery and controls](../../skills/docs/cloud-workspace.md). Loaded cloud bodies persist as `cloudLoadedSkills` in session JSON, with workspace, selected manifest path and content fingerprint; no SQL schema change is required. Runtime reconciles them against the current files and policy before budgeting. A changed body is reread; a removed, disabled or source-switched skill is deactivated. Source switches require another `skill.view`. Local `loadedSkills` are separate. Legacy records are checked against current discovery before use.

## Verification

[Instruction tests](../project-instructions.test.ts), [workspace skills tests](../../skills/workspace-skills.test.ts), and [execution seams](../../agent/cloud-workspace-seam.test.ts) cover discovery boundaries, live policy, concurrent sessions, fallback, preview, journaling, resume and compaction. Fusion delegate/factory tests cover inherited paths. These tests use fake models; they do not establish how reliably a real model follows conflicting natural-language rules.
