# Dependency ownership and verification

Status: current
Owner: repository maintainers

## Owners

[Provider commands](../../src/config/llm-provider-commands.ts) own validated provider-block and credential persistence: upsert/remove, active provider pins, default models, fallback edits, dotenv writes and cache invalidation. The module uses concrete config modules, not its own index. Its credential-kind union preserves the six formerly accepted wizard values without importing a wizard type. Channels and UI call this owner; live runtime switching remains with the calling orchestrator. [Persistence tests](../../src/config/llm-provider-commands.test.ts) moved beside it without new type allowances.

[Pick-list geometry](../../src/tui/components/pick-list-geometry.ts) owns the shared viewport calculation and paging constant. [Printable filter input](../../src/tui/input/printable-filter-input.ts) owns the control-character policy. Neither imports a feature. The [shared list view](../../src/tui/components/pick-list.tsx) receives selection, activation and paste callbacks; the [provider adapter](../../src/tui/providers/wizard-pick-list.tsx) binds them to the wizard drawn in that frame. Mouse activation still routes through the keyboard handler, including separately owned onboarding wizards. Paste retains the existing store-backed adapter.

[Wait/jump selectors](../../src/tui/onboarding/wait-or-jump-selectors.ts) own download status and row count used by both rendering and keys. [Composer row contracts](../../src/tui/composer-switch/composer-switch-row-contracts.ts) own row/intent types and common provider/loading selectors; ordinary and worker row builders import them independently. No selector imports its own row builder.

[Providers](../../src/tui/providers/README.md), [LLM/fallback](../../src/tui/llm-panel/README.md) and [health](../../src/tui/llm-health/README.md) now own their views beside state/input/orchestration. Onboarding intentionally composes the provider wizard and its measurement; composer shares LLM activation/preflight and health presentation. These concrete composition dependencies do not justify copying domain operations or banning all feature-to-feature imports.

[Onboarding](../../src/tui/onboarding/README.md) now keeps its specific views, input/effect hooks and timestamp persistence together. Its general backend-readiness check remains shared with TUI commands, and local-models/local-llm retain ownership of running downloads. HF editor/list now belong to [local-models presentation](../../src/tui/local-models/README.md) and serve both flows via callbacks. Their domain types/RAM policy remain explicit; relocation does not reclassify them as generic domain-free primitives. Local-model panel, notification, download-chip and log views also live with their UI state/input/orchestration.

[Memory](../../src/tui/memory/README.md) and [tasks](../../src/tui/tasks/README.md) keep their views beside state/input/orchestration. DebugPane composes the panels; TuiApp retains the separately rendered task-cancel modal. Their refresh timers belong to UI orchestrators, while runtime/domain stores and task execution retain their existing owners. TasksList still uses its own window/columns rather than the separately tested list-fit helper; relocation does not establish complete layout coverage.

[Skills](../../src/tui/skills/README.md) and [import](../../src/tui/import/README.md) also keep presentation with state/input/orchestration. Skills domain owns scan/stage/commit/discard and installed files; import domain owns source-specific conversion. TUI import reuses runtime destination stores and releases only per-run sources. Onboarding composes the existing import operation; it does not acquire those stores from a view.

## Checked graph

[Issue-report](../../src/tui/issue-report/README.md) and [uninstall](../../src/tui/uninstall/README.md) own their modal views and input handlers. Global app-key-bindings imports the handlers as values; their limited AppKeyContext dependency is type-only and creates no runtime cycle. The global router keeps precedence, and report packaging/submission and post-shutdown removal remain with their existing operation owners.

`npm run imports:check` runs [the checker](../../scripts/check-imports.mjs) using installed TypeScript and tsconfig.json resolution. It covers production TS/TSX roots, resolves relative ESM .js specifiers to TS/TSX, and reads static import/export, literal dynamic import and import() type references. Missing local targets and production imports of excluded source files fail. JSON/declaration targets resolve but are not runtime graph vertices. Bare package imports are external. Tests do not create production edges.

Every local edge, including type-only dependencies, participates in ownership rules:

- config, llm (including providers), local-llm, agent, prompt, session, memory, tools, mcp, skills, tasks, approval, tracing and compressor cannot import TUI or channels.
- Channels and HTTP interfaces cannot import TUI. CLI can import TUI only through the exact src/cli/index.ts → src/tui/index.ts composition edge.
- Named shared list/editor/logo/chip/formatting primitives, row-window, input/ and theme/ can use named shared UI owners (input, mouse, context-menu, clipboard, theme and those primitives), but cannot directly import feature or domain implementations, even through types. [The component inventory](../../src/tui/components/README.md) distinguishes them from intentional shell composition; this is not a blanket ban on feature composition or a transitive isolation claim for mouse/context-menu services.
- The shared composer row contract cannot import either concrete row builder.
- The config scalar primitive owner cannot directly import config-schema or config/index, including type-only and literal dynamic imports. Composition can re-export primitives; the primitive owner imports the existing validation error directly. This protects the direct composition boundary, not every possible transitive dependency.
- The session-rail config owner has the same direct composition boundary: it imports the existing validation error, while the schema imports/re-exports its type and parser. Session storage and UI do not become config dependencies.
- The webhook config owner cannot directly import composing schema/config index. Its scalar/error dependencies and TaskSchedule type are explicit; canonical schedule execution and HTTP ingress remain separate. Type-only and literal dynamic references participate in the composition rule.
- Config values and MCP server-config owners cannot directly import composing schema/config index, including types and literal dynamic imports. Values do not depend on MCP configuration; the MCP parser depends inward on values/primitives/error and neutral MCP constants/types. Client lifecycle and interface persistence stay outside these owners.
- The agent execution-config owner cannot directly import composing schema/config index, including types and literal dynamic references. Root composition supplies current defaults explicitly; the owner uses concrete scalar/error dependencies without loading the agent loop or capturing global defaults.
- The web config owner can directly import only the existing scalar and validation-error source owners. Schema/root API, tool execution, providers and network transport stay outside it, including type-only and literal dynamic references. Composition retains early provider preparation and late normalization, with explicit current-default lookups. This source-edge rule does not inspect bare-package dependencies or establish transitive isolation.
- Memory config types cannot import other source owners. Memory defaults can depend only on their type owner; the parser can depend only on those types and the concrete scalar/value/error/subcall-timeout config owners. The direct rules include type-only and literal dynamic references; storage/providers/prompt/runtime execution are outside this config domain. Root composes all three owners with explicit current defaults.
- Local-model config types depend only through type-only edges on the concrete model catalog, backend preference and SWA preference owners. Defaults depend on the owned types and the existing download/Hugging Face constants; parsing depends on owned types and concrete scalar/value/error/custom-model/catalog/backend/SWA/constant helpers. Composition/root API, loading, server lifecycle and download execution are outside these direct allowlists. Type-only and literal dynamic references participate; allowed type targets cannot be loaded at runtime by the types owner. Bare packages and transitive loading are outside this source-edge policy.
- TUI configuration depends only on concrete scalar/error/session-rail owners; channel and integration configuration depend only on scalar/error/shared-value owners. The direct allowlists include type-only and literal dynamic references and prohibit composition/root API, peer frontend config and runtime/service dependencies. Root supplies defaults explicitly, preserving the two compatible TUI wrappers; these config owners do not own connections or UI components. Bare packages and transitive loading remain outside this static boundary.
- The hash contract leaf cannot import any other src owner, including type-only and literal dynamic references. Execution, descriptor/schema maps and agent taxonomy depend inward on the leaf; roles/read-targets remain explicit policy. The current leaf has zero imports, also checked during source acceptance; the static graph rule does not inspect bare-package dependencies.

Runtime strongly connected components, including self-imports, fail without a cycle allowance. Fully type-only declarations/specifiers are excluded from runtime cycle analysis; a mixed declaration retains its value edge. This analysis conservatively treats ordinary imports as runtime dependencies even if the compiler could erase an implicitly type-only binding. Nonliteral dynamic targets, require() and runtime/plugin loading are outside the static graph; zero cycles does not prove all initialization behavior or all architectural boundaries.

[The exception ledger](import-exceptions.json) is empty after stage 03a. MCP persistence now belongs to [config commands](../../src/config/mcp-server-commands.ts); HTTP and the [TUI MCP feature](../../src/tui/mcp/README.md) use that owner without depending on each other. Any future reviewed ownership exception must name one exact source/target, owner and reason; duplicate, unowned, wildcard and stale exceptions fail. There is no automatic capture/rebase command and exceptions never permit a runtime cycle. Review changes to this ledger as changes to architecture.

Run `npm run imports:self-test` for disposable positive and negative projects covering resolution, cycles, typed/mixed dependencies, shared primitives, composition root, excluded tests, JSON and exception maintenance. Both commands run in the default-install PR gate; [local CI](../testing/local-ci.md) lists the full sequence.

[Update UI](../../src/tui/update/README.md) owns specialized presentation and offer keys; the StatusBar composition composes its banner without acquiring installer ownership.

[Chat](../../src/tui/chat/README.md), [context](../../src/tui/context/README.md), [coding-mode](../../src/tui/coding-mode/README.md), [session rail](../../src/tui/session-rail/README.md), [theme chooser](../../src/tui/theme-picker/README.md) and [observe](../../src/tui/observe/README.md) own their specific views/helpers. ## OS and managed-model owners

[OS tools](../../src/tools/os/README.md) compose filesystem, shell and web operation owners while retaining registration/export order and existing archive/document/git/process/search/command-guard owners. [Managed local models](../../src/local-llm/README.md) expose the compatible root API and explicit downloads/server/backend/catalog owners. Root disk layout and source-depth-sensitive chat-template lookup stay at their previous location; no directory-level layering rule is inferred from grouping. The production gate rejects imports of the exact filesystem test helper and catalog GGUF byte fixtures, while ordinary test imports remain allowed.

## Execution and resource configuration owners

The [agent policy](../../src/config/agent/README.md) types depend only on neutral approval and existing execution-policy types, with type-only edges. Its defaults depend on its type owner and execution factories; its parser on those types, scalar/error owners and execution parsers. [HTTP](../../src/config/http-config.ts), [tool](../../src/config/tool-config.ts) and [skills](../../src/config/skills-config.ts) configuration depend only on concrete scalar/value/error owners. [Retention](../../src/config/session-retention-config.ts) and [tracing](../../src/config/tracing-config.ts) use scalar/error owners. The checker applies exact allowlists to static, type and literal dynamic dependencies, prohibits runtime loading of the neutral type owners, and grants no exceptions. Resource execution remains outside these configuration modules.

## Agent execution contracts

The [agent contract](../../src/agent/agent-contract.ts), [step contract](../../src/agent/step/step-contract.ts), [batch contract](../../src/agent/dispatch/batch-contract.ts) and [progress contract](../../src/agent/progress/loop-contract.ts) carry types only. Runtime dependencies, including bare imports, are forbidden there; executor/root imports are forbidden even through types. Turn/step/dispatch/progress/policy leaves cannot load the old orchestration facades. Pure progress constants/fingerprints/notices cannot load ToolLoopTracker. The tracker remains the actual state owner, so its nominal type is an intentional type-only contract dependency. These direct checks do not claim transitive isolation or inspect nonliteral dynamic loading.
